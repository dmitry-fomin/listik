# Listik — трекер задач и память для людей и агентов

Listik — одна очередь задач на все проекты, общая для человека и AI-агентов (Claude Code, Codex,
DeepSeek, Grok и т. п.). Один сервер — локально или на отдельной машине, одна база SQLite, один
API (HTTP и MCP). Кроме задач — журнал
работы по каждой карточке, долговременная память и гибридный поиск (полнотекстовый + векторный)
по всей истории.

Зачем: агентская работа теряется между сессиями, агенты берут одно и то же, вопросы человеку
тонут в чате. В Listik у задачи всегда видно, **кто её держит**, **на каком она этапе**, **жив ли
держатель**, **чего она ждёт** и **что уже решено** — и любая новая сессия восстанавливает
контекст из карточки, а не из переписки.

```
bin/listik     CLI и клиент API (одна программа)
listik/        сервер, база, поиск, эмбеддинги, MCP
web/           доска (Vue 3)
plugins/       плагин для Claude Code со скилом Listik
API.md         контракт данных и эндпоинтов
AGENTS.md      правила работы агента с задачами
```

## Установка и запуск

Нужно: Python 3.11+ (только стандартная библиотека). Для доски — Node.js. Для векторного поиска —
[Ollama](https://ollama.com) с моделью `bge-m3` (необязательно: без неё поиск лексический).

```sh
git clone https://github.com/dmitry-fomin/listik.git && cd listik
cp config.example.toml config.toml   # необязательно: без файла serve создаст конфиг сам
(cd web && npm install && npm run build)   # собрать доску

./bin/listik serve --daemon   # сервер и доска на http://127.0.0.1:8787
./bin/listik token            # ссылка на доску с токеном
./bin/listik status           # сервер, база, поиск
./bin/listik stop
```

- База `listik.db` создаётся сама при первом `serve`/`init`.
- Если в `config.toml` нет токена, `serve` генерирует его и сохраняет конфиг.
- Векторы: `ollama serve` + `ollama pull bge-m3`. Сервер сам досчитывает векторы новых записей
  раз в 45 секунд; без Ollama поиск молча остаётся лексическим. Отключить: `serve --no-embed`.
- CLI работает и без сервера: если сервер не отвечает, команда идёт в базу напрямую (и
  предупреждает об этом). `--json` есть у всех команд.

Кто выполняет команду — актор: флаг `--actor` или `LISTIK_ACTOR` (по умолчанию `$USER`).
Агенты представляются как `agent:<harness>` флагом в каждой команде, например
`--actor agent:claude --harness claude` — от этого зависит, какие связи они могут ставить
(см. «Зависимости»). `export LISTIK_ACTOR` агенту не подходит: каждый его вызов shell — новый
процесс, переменная теряется, и запись уходит от `$USER`, как от человека.

## Как устроена работа

### Задача

У задачи есть проект, заголовок, описание, критерии приёмки, тип (`task`, `bug`, `epic`, …),
приоритет P0–P4 и статус: `open`, `in_progress`, `review`, `done`, `cancelled`
(`blocked` как статус не ставится — блокировка вычисляется, см. ниже).

Главное для совместной работы — четыре вещи:

| | Что это | Как меняется |
|---|---|---|
| **Держатель** (`holder`) | кто работает прямо сейчас | `claim`, передача на `stage --holder`, `release` |
| **Heartbeat** (`holder_at`, `holder_note`) | когда держатель последний раз подал знак и что делает | `heartbeat` |
| **Этап** (`stage`) | где задача в конвейере | `stage` |
| **Нужен человек** (`needs_owner`) | задача ждёт ответа владельца | `needs-owner` |

Одна задача — один держатель. Держатель, который молчит дольше `board.stale_hours` (24 ч),
считается брошенным; задача «в работе» без держателя — тоже.

### Процесс

```
ready → claim → работа + heartbeat → stage … → done
              ↘ needs-owner (вопрос)  ↘ release (отдать)
```

```sh
# агент добавляет к каждой команде: --actor agent:claude --harness claude
./bin/listik ready                                   # что можно брать: без блокеров и держателя
./bin/listik show <id>                               # вся карточка
./bin/listik claim <id> --holder claude --note "беру"
./bin/listik heartbeat <id> --holder claude --note "пишу тесты"   # каждые 10–15 минут
./bin/listik comment <id> "решил хранить X в Y, потому что…" -k journal
./bin/listik stage <id>                              # следующий этап
./bin/listik done <id> -r "что сделано, одной проверяемой строкой"
```

Задачу можно вести напрямую (`claim → heartbeat → done`) или по конвейеру из четырёх этапов:

| Этап | Что делается | Переход дальше |
|---|---|---|
| `s1-spec` | ТЗ и чек-лист приёмки, нарезка на порции | → `s2-review`, **sticky** |
| `s2-review` | независимая критика ТЗ (только `comment -k review`) | → `s3-impl`, **handoff** |
| `s3-impl` | реализация в `worktree`/`branch` задачи | → `s4-judge`, **sticky** |
| `s4-judge` | независимая проверка, вердикт, коммит | → `done`, **handoff** |

- **sticky** — держатель остаётся: та же сессия продолжает, либо передаёт карточку другому
  исполнителю `stage <id> --holder <следующий>`.
- **handoff** — сервер снимает держателя, задача возвращается в `ready`, её берёт следующий.
- **Вердикт.** `comment -k verdict` принимается, только если первая строка — ровно
  `VERDICT: PASS` или `VERDICT: FAIL`, иначе ошибка. `FAIL` требует ниже списка правок; на
  `s4-judge` он возвращает задачу на `s3-impl` (держатель тот же), и этот список исполнитель
  читает в `show`.
- **Окно возврата.** Если после `VERDICT: FAIL` держатель не подал `heartbeat`/`claim` за
  `return_window_hours` (24 ч), сервер снимает его и задача уходит в `ready`.
- Время на этапе считается от перехода; в событии перехода пишется, сколько длился прошлый этап.

**`claim` отказывает** — и печатает причину и варианты — если:
1. у задачи открытый жёсткий блокер (обойти можно `--force`, это остаётся в истории);
2. задачу держит кто-то другой (даже молчащий; `--force` не помогает — нужен `release`);
3. в том же проекте то же рабочее дерево (`worktree`) занято другой пишущей задачей. Пишущие —
   `s3-impl`, `s4-judge` и задачи без этапа; `s1`/`s2` дерево не занимают;
4. этап не разрешён этому исполнителю по маршрутизации проекта (если передан `--harness`).

Учтите поведение, которое сервер **не** проверяет: `heartbeat` перезаписывает держателя без
проверки (не шлите его по чужой задаче), а `done` закрывает задачу, не проверяя блокеры и
открытых детей эпика и не снимая держателя — перед `done` посмотрите `show`.

### Что появляется в задаче во время работы

Всё, что нужно следующей сессии, копится в самой карточке — `listik show <id>` показывает это
целиком:

- **Держатель и heartbeat**: кто держит, сколько молчит, заметка «что делаю»; флаги «ЖДЁТ
  ЧЕЛОВЕКА» и «брошена».
- **Этап** и время на нём; `started_at` при первом взятии, `closed_at`, `result` при закрытии.
- **Комментарии** по видам (`-k`):
  - `journal` — ход работы и решения;
  - `review` — замечания критика;
  - `verdict` — вердикт проверки (`VERDICT: PASS` или `VERDICT: FAIL`);
  - `question` / `answer` — вопрос человеку и ответ (пишутся командой `needs-owner`);
  - `comment` — всё прочее.
- **События** (история): `created`, `claim`, `heartbeat` (не чаще раза в 10 минут), `stage`
  (с длительностью прошлого этапа), `release`, `status`, `question`/`answer`, `comment`, `note`
  (например, взятие с `--force` в обход блокеров), ошибки документов.
- **Документы**: пути к ТЗ, чек-листу, ревью и решению (`--spec`, `--checklist`, `--review`,
  `--decision` у `new` или `set spec_path=…`). Файлы индексируются для поиска по разделам;
  пропавший файл помечается «ФАЙЛ НЕДОСТУПЕН».
- **Рабочее дерево и ветка** — `set <id> worktree=/путь branch=имя`.
- **Связи**: чего задача ждёт, кто ждёт её, предложенные блокеры, мягкие связи.

`listik context <id> --stage <этап>` отдаёт компактный срез карточки под конкретный этап
(ТЗ и чек-лист на `s2`, нужная порция ТЗ на `s3` через `--portion`, последний вердикт и
состояние дерева на `s4`) — его удобно давать агенту вместо карточки целиком.

### Вопросы человеку

```sh
./bin/listik needs-owner <id> "Лимит считать по заказам или по позициям?"
./bin/listik needs-owner <id> --clear "по позициям"     # ответ снимает флаг
./bin/listik inbox                                     # всё, что ждёт человека или брошено
```

Вопрос и ответ остаются в истории карточки и находятся поиском.

### Автостарт задачи

Задачу можно не только завести, но и сразу запустить: сервер сам поднимет процесс по
маршруту из `routes.json` и будет следить за ним.

```sh
./bin/listik new "проба" -p listik --autostart --route low-pipeline
./bin/listik new "проба" -p listik --route low-pipeline    # маршрут сохранён, запуска нет
./bin/listik show <id>                                     # автостарт: low-pipeline · … · код 0
```

- `--autostart` без `--route` — ошибка (код 2), задача не создаётся. `--route` без
  `--autostart` просто запоминает маршрут.
- Саму команду (`command`) маршрут получает из рабочей копии `routes.json` —
  `~/.config/listik/routes.json` (её создаёт сервер при первом старте из `routes.json`
  в корне Listik). Из CLI команду задать нельзя.
- Отказ не отменяет создание задачи: она создаётся, `launch_error` объясняет причину и
  поднимается флаг «нужен человек»; `show` печатает `автостарт: ОШИБКА …`. Так же
  отвечают битый `routes.json`, маршрут без `command`, отсутствие рабочего каталога
  (`worktree` задачи или `path` проекта) и несуществующий бинарник.
- Пока сервер не запущен, CLI работает с базой напрямую и запустить процесс не может:
  задача создаётся с `launch_error = сервер Listik не запущен`.
- Успешный запуск: `show` показывает `автостарт: <маршрут> · запущена listik pid N <время> ·
  код идёт`, после завершения — `код <N>`; лог процесса лежит в `logs/launch-<id>-<время>.log`.
  Запуск не делает claim за агента: этап, держатель и статус не меняются.

## Зависимости: как появляется «блокирует»

«Заблокирована» — не статус, а вычисляемое состояние: задача стоит, пока открыт хоть один её
**жёсткий** блокер, и освобождается сама, когда блокер закрыт.

```sh
./bin/listik dep add <id> <блокер>       # <id> ждёт <блокер>  (на доске: «блокирует» / «ждёт»)
./bin/listik dep rm <id> <блокер>        # снять связь
./bin/listik blocked                     # кто кого ждёт, с держателем и простоем блокера
./bin/listik tree <id>                   # чего ждёт задача и кто ждёт её
./bin/listik cycles                      # циклы в жёстких связях
```

- **Жёсткие** связи (`blocks` — по умолчанию, `blocked-by`, `waits-for`, `conditional-blocks`)
  убирают задачу из `ready` и не дают её взять.
- **Мягкие** (`relates-to`, `parent-child`, `discovered-from`, `duplicates`, `supersedes`, …) —
  «прочитай сначала», работу не запрещают. `dep link <id>` ставит `relates-to` на задачи,
  упомянутые в тексте; `dep suggest <id>` показывает такие упоминания.
- **Кто ставит жёсткую связь.** Человек — сразу. **Агент** (`agent:…`) без `--confirm` получает
  не блокер, а **предложение** `suggested-blocks`: оно видно в `show` («предложены блокеры») и в
  `dep suggested`, но на `ready`/`claim` не влияет. Человек подтверждает `dep confirm <id>
  <блокер>` — связь становится жёсткой — или отклоняет `dep rm`. Так модель не может по догадке
  остановить чужую работу.
- Жёсткая связь, замыкающая цикл, отвергается: `жёсткая зависимость создаёт цикл: A → B → A`.
- На карточке: «ждёт N» — сколько открытых блокеров; «её ждут N» — сколько задач стоят из-за неё.

## Доска

`http://127.0.0.1:8787/?token=…` (ссылка — `listik token`). Вкладки:

- **Доска** — колонки этапов: «Заведена» (без этапа), s1–s4 и «Готово» (закрытые за 7 дней,
  клик открывает список). Колонки сворачиваются в рельсу кликом по заголовку. Над доской —
  «Нужен ты» (вопросы, брошенные и молчащие задачи) и счётчики: брошена, под угрозой, стоят из-за
  других, можно брать.
- **Список** — все задачи с фильтрами, сортировкой и массовой правкой.
- **Метрики** — поток по этапам, темп закрытия, проекты и держатели.

Доска только показывает и помогает ответить: этап меняют команды, перетаскивания нет.

## Поиск и память

```sh
./bin/listik search "как решали X"            # задачи, комментарии, разделы документов
./bin/listik search "X" --mode text|vector    # только лексика / только семантика
./bin/listik remember "факт на будущее" -p <проект>
./bin/listik memory "про что-то"
```

Поиск — FTS5 (BM25) + векторы `bge-m3`, слияние RRF.

## Маршрутизация: кто какой этап ведёт

В `config.toml`, `[routing]`: какие исполнители допущены к каждому этапу, типы переходов и окно
возврата. Проект переопределяет это в `[routing.projects.<slug>]` или командой:

```sh
./bin/listik projects <slug>                                        # действующая таблица
./bin/listik projects <slug> --routing '{"harnesses": {"s3-impl": ["codex"]}}'
./bin/listik ready --harness codex                                  # только разрешённое codex
```

## Подключение агентов

**Плагин для Claude Code** — скил, который учит Claude работать по протоколу Listik:

```
/plugin marketplace add dmitry-fomin/listik
/plugin install listik@listik
```

Скил работает в двух режимах:

- **Listik на этой машине** — скил вызывает установленный `listik`: положите `bin/listik` в
  `PATH` или задайте `LISTIK_BIN=/путь/к/listik/bin/listik`.
- **Listik на другом сервере** — CLI не нужен: подключите удалённый MCP (см. «Listik на другом
  сервере»), и скил будет работать через инструменты `listik_*`.

**MCP** — 30 инструментов `listik_*`: ready, show, claim, heartbeat, stage, comment, needs_owner,
done, release, deps, search, memory, put_document/get_document и др.; полный список с параметрами —
в [API.md](API.md), «MCP по HTTP». Локально:

```sh
claude mcp add listik -- /путь/к/listik/bin/listik mcp
```

Это локальный stdio-транспорт: агент работает на той же машине, где стоит Listik. Для Listik на
другом сервере — MCP по HTTP, см. «Listik на другом сервере».

**Правила в проектах.** `listik init-projects` вписывает протокол работы с Listik
(`docs/harness-protocol.md`) в существующие `AGENTS.md`/`CLAUDE.md` проектов, добавленных через
`listik projects --add <путь>`, — между маркерами `<!-- BEGIN LISTIK -->`/`<!-- END LISTIK -->`,
не трогая остальной текст. `--dry-run` — посмотреть, `--remove` — убрать.

**Переход с beads.** `listik import-beads` разово переносит `.beads`-трекеры из каталога проектов
(старый ID сохраняется в `external_ref`), затем — `docs/beads-migration.md`.

## Listik на другом сервере

Listik можно держать на одном сервере, а агентов подключать к нему по сети. Удалённо доступен
только MCP по HTTP (`POST /mcp`); CLI `bin/listik` остаётся локальным инструментом — удалённого
режима CLI нет.

1. **Поднять Listik на сервере.** Клон репозитория, база, запуск:

   ```sh
   git clone https://github.com/dmitry-fomin/listik.git && cd listik
   ./bin/listik init            # создать базу
   ./bin/listik serve --daemon  # сервер и доска
   ```

   `host` в `config.toml` оставьте `127.0.0.1` (значение по умолчанию): наружу сервер смотрит
   только через обратный прокси на той же машине. Без `config.toml` первый `serve` создаст его
   сам и сгенерирует токен.

2. **Обратный прокси и HTTPS.** Наружу — только HTTPS через прокси на той же машине: токен по
   голому HTTP отдавать нельзя, его перехватят. Caddy (`Caddyfile`):

   ```
   <домен> {
       reverse_proxy 127.0.0.1:8787
   }
   ```

   nginx:

   ```
   location /mcp {
       proxy_pass http://127.0.0.1:8787;
       proxy_read_timeout 120s;
   }
   ```

   `8787` — порт по умолчанию (и порт из примера выше); если в `config.toml` в `[server] port`
   указан другой, замените его и здесь. `proxy_read_timeout` — не меньше 120 с: ответ MCP может
   считаться долго, а короткий таймаут обрывает запрос.

3. **Взять токен.** На сервере: `./bin/listik token` — покажет токен и ссылку на доску. Токен
   один на всё: доска, API и MCP.

4. **Подключить агента на его машине.** Репозиторий и база там не нужны — только URL и токен:

   ```sh
   claude mcp add --transport http listik https://<домен>/mcp --header "Authorization: Bearer <токен>"
   ```

5. **Документы.** Файлов проектов на сервере нет, поэтому ТЗ и чек-лист передаются содержимым:
   `listik_put_document` (MCP) → `PUT /api/tasks/{id}/documents/{kind}`, а читаются
   `listik_get_document` или `listik_context`. Путь в карточке при этом не нужен: документ
   получает виртуальный `listik://<id>/<kind>.md` и дальше читается из базы, а не с диска
   (см. [API.md](API.md), «Документы и чанки»).

6. **Что остаётся только локально:** CLI `bin/listik` (удалённого режима CLI нет),
   администрирование проектов и routing, удаление задач, импорты (`import-beads`,
   `import-writerllm`), пересчёт векторов (`listik embed`) и `listik init-projects`.

## Справочник команд

| Группа | Команды |
|---|---|
| Сервер | `serve [--daemon] [--no-embed]`, `stop`, `status`, `init`, `token`, `mcp` |
| Задачи | `new`, `list`, `show`, `set`, `context`, `board`, `stats`, `timeline` |
| Работа | `ready`, `claim`, `heartbeat`, `stage [--to]`, `release`, `done`, `needs-owner`, `inbox` |
| Журнал | `comment -k comment\|journal\|review\|verdict\|question\|answer` |
| Связи | `dep add\|confirm\|rm\|tree\|cycles\|suggest\|link\|suggested`, `blocked`, `tree`, `cycles` |
