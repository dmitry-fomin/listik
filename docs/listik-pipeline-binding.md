# Конвейер разработки на Листике — связка

Дополнение к [схеме шины](listik-orchestration-scheme.md). Отвечает на один вопрос: как
четырёхэтапный конвейер `feature-pipeline` (плагин `homemade-skills-claude-code`) ложится
на карточки Листика, если ТЗ↔критика и код↔приёмка склеены sticky-переходами.

Согласовано 2026-09-10. Решение по гранулярности: **карточка = порция**.

## Почему связки именно такие

Sticky в этой паре — не соглашение об удобстве, а следствие механики. Обе склейки
воспроизводятся из устройства конвейера, и разорвать их нельзя без потери работы:

| Переход | Тип | Что физически ломается при разрыве |
| --- | --- | --- |
| s1 → s2 | sticky | Решения автора по замечаниям критика возвращаются в `pipeline-spec-writer` через `SendMessage` по agent id. Agent id живёт только внутри разговора: другая сессия автора ТЗ не возобновит и будет перезапускать его с нуля, вкладывая решения строками из журнала |
| s2 → s3 | **handoff** | Ничего. Всё лежит файлами, дерево чистое — единственная честная точка разрыва в конвейере |
| s3 → s4 | sticky | Порция к моменту приёмки **не закоммичена**: коммитит только судья. Дифф собирается из рабочего дерева, и передать это состояние через карточку нечем — `worktree` укажет на дерево, но незакоммиченная правка в нём принадлежит чужой сессии |
| s4 → s3 | sticky с окном | Повтор ведёт тот же holder. Внутри него исполнитель — **новый субагент**: у прежнего в контексте лежит защита собственного кода. Это разные уровни, противоречия здесь нет |
| s4 → done | handoff | Порция закоммичена судьёй, состояние в git |

**Уточнение к s1 → s2 при карточке-порции.** s1 живёт на карточке шага, s2 — на карточках
порций, то есть sticky связывает не две стадии одной задачи, а сессию с группой задач.
Точная формулировка: **сессия, выполнившая s1, проводит s2 по всем порциям шага, не отпуская
их**. Правка ТЗ после критики любой порции идёт в того же живого автора ТЗ, который нарезал
их все. Handoff открывается, когда s2 закрыт по всей группе.

Отсюда же следует, что критика всех порций запускается разом, а решения автора собираются
одним пакетом: сессия всё равно держит группу до конца s2, растягивать это на K
последовательных заходов нечем оправдать.

## Соответствие сущностей

| Конвейер | Листик |
| --- | --- |
| шаг `step-NN` | родительская карточка; на ней живёт s1 и больше ничего |
| порция `step-NN.<X>` | дочерняя карточка (`dep add --dep-type parent-child`), проходит s2 → s3 → s4 → done |
| ТЗ порции | `spec_path` |
| чек-лист приёмки | `acceptance` — путь к `step-NN.check-<X>.md` (отдельного поля нет, см. «Чего не хватает») |
| журнал | `journal_path` + строки `comment -k journal` на каждом переходе |
| дерево и ветка трека | `worktree`, `branch` |
| вердикт судьи | `comment -k verdict`, первым словом `зелёный` или `красный` |
| замечания критика | `comment -k review` плюс файл `step-NN.review-<X>.md` |
| вопрос автору | `needs-owner` |
| зависимость порций | `blocks` |
| трек (независимая часть) | порции, не связанные `blocks`; `ready` отдаёт их одновременно |

**Карточка шага после нарезки ничего не делает и ждёт детей**: порции ставятся ей `blocks`,
`ready` её не отдаёт, `done` она получает, когда закрыта последняя порция. Стадия у неё
остаётся `s1` — это честно, работы на ней больше нет.

## Что это даёт сверх текущего конвейера

Независимость порций сейчас **объявляет автор словами**, и это самое хрупкое место режима
треков: две порции могут не делить ни одного файла и при этом менять две стороны одного
контракта. В Листике независимость перестаёт быть словом и становится графом: `blocks`
проставляет автор ТЗ на этапе s1, `ready` отдаёт то, что никого не ждёт. Параллель едет
на данных, а не на добросовестности формулировки.

Порядок порций внутри шага тоже перестаёт быть нумерацией в файле: `a` больше не значит
«раньше `b`», значит только `blocks`.

## Тест холодного старта: что лежит в карточке перед s2 → s3

Принимающий начинает с `listik show <id>` и ничего больше. Значит на момент перехода
заполнено:

- `spec_path` — файл порции, уже поправленный по принятым замечаниям критика;
- `acceptance` — путь к чек-листу;
- `worktree` и `branch` — если порция идёт в отдельном дереве; пусто = основное дерево;
- `journal_path` — журнал шага;
- `blocks` — проставлены и закрыты все, от которых порция зависит;
- `comment -k journal` последней строкой: сколько замечаний критика принято, поправлено ли ТЗ,
  какие решения автора уже даны — чтобы принимающий не поднимал переписку заново;
- `comment -k review` — сводка критика, если он был.

Пустое поле из этого списка — это не «разберутся на месте», а несделанный переход: принимающий
харнесс начнёт с вопроса автору и потеряет цикл.

## Команды на каждом переходе

Проверено на CLI 2026-09-10; флаги отличаются от черновика схемы (`--dep-type` через дефис,
`--spec`/`--journal` при создании, поля после создания — через `set`).

```sh
L=~/Projects/Listik/bin/listik
export LISTIK_ACTOR=agent:claude

# s1: нарезав порции, завожу карточку на каждую
$L new "step-07.a: <суть порции>" -p <проект> -t task --priority 1 \
   --stage s2-review --spec docs/specs/steps/step-07.a.md \
   --journal docs/specs/steps/step-07.journal.md \
   -a docs/specs/steps/step-07.check-a.md
$L dep add <порция> <шаг> --dep-type parent-child
$L dep add <порция-b> <порция-a> --dep-type blocks     # только если b правда ждёт a
$L set <порция> worktree=../<репо>-billing branch=pipeline-billing   # если трек

# s2 → s3: перед handoff проверяю карточку и отпускаю
$L show <порция>                    # spec_path, acceptance, journal_path, worktree на месте?
$L comment <порция> "критика: N блокирующих, принято M, ТЗ поправлено" -k journal
$L stage <порция> --to s3-impl

# s3 → s4 в той же сессии, без release
$L heartbeat <порция> --holder claude --note "порция a, этап 3"
$L stage <порция> --to s4-judge

# вердикт
$L comment <порция> "зелёный, коммит <hash7>" -k verdict
$L done <порция> -r "<что сделано одной строкой>"
# красный:
$L comment <порция> "красный: <пункты>" -k verdict
$L stage <порция> --to s3-impl      # holder не снимаю: sticky с окном
```

`stage --to` существен: без него `stage` идёт только вперёд по цепочке, а красный вердикт —
это возврат на предыдущую стадию.

## Вход с середины

Сессия, поднятая диспетчером на `s3`, работает так:

1. `listik show <id>` → `claim --holder <харнесс>`;
2. поднять `journal_path` целиком — это память конвейера, а не чужой материал;
3. `worktree` непустой — все команды в этом дереве (`git -C`), путь субагенту абсолютным
   в первой строке задачи; пустой — основное дерево;
4. этап 3, затем **в той же сессии** этап 4: `s3 → s4` sticky;
5. зелёный вердикт — коммит судьи, `comment -k verdict`, `done <id> -r "..."`;
   красный — `stage` назад на `s3`, holder сохраняется, счётчик красных в журнал.

Скилы конвейера сейчас предполагают старт с нуля и собственный журнал-файл как единственную
память. Вход с середины — новый режим для них, и он добавляется в шаг 0: **есть id карточки
в аргументах — поднимайся по карточке, а не по `ls` каталога шагов**.

## Вопросы автору: два канала, выбор по типу сессии

`AskUserQuestion` существует только в интерактивной сессии. Диспетчер запускает харнесс
неинтерактивно, и вопрос, заданный этим инструментом, там просто не прозвучит.

| Сессия | Канал вопроса | Что с holder |
| --- | --- | --- |
| интерактивная | `AskUserQuestion` | остаётся, ответ приходит в том же разговоре |
| запущенная диспетчером | `needs-owner <id> "вопрос"` | остаётся в пределах окна; окно истекло — `release`, задача уходит в `needs_you` |

Окно нужно ровно по причине sticky: пока holder держит задачу, живы agent id субагентов,
и ответ автора можно вернуть в работающий контекст. После release эти id мертвы, и следующая
сессия поднимает вопрос и ответ строками из журнала — поэтому и вопрос, и ответ пишутся
в журнал дословно, а не пересказом.

Это тот же механизм, что схема закрепила за красным вердиктом. Стоит объединить: **sticky
с окном — одно правило на два случая**, вопрос автору и красный вердикт.

## Треки против лока на репозиторий

Схема фиксирует: «`claim` защищает задачу, не дерево: один пишущий агент на репозиторий
(позже — worktree на задачу)». Режим треков в конвейере — это и есть «worktree на задачу»,
уже работающий: оркестратор заводит `git worktree` на каждую независимую часть, и пишущих
агентов в одном репозитории становится несколько.

При буквальном локе на репозиторий треки запрещены, и параллель сводится к одной порции
за раз по всему репо. Развилка:

- **лок на пару (репозиторий, worktree)** — тогда порции с разными `worktree` не конфликтуют,
  а порции с пустым `worktree` конкурируют за основное дерево, как раньше. Это переносит
  «позже — worktree на задачу» вперёд по плану, но объём правки невелик: ключ лока берётся
  из полей карточки, которые уже есть;
- **один claim на группу порций** — оркестратор держит все порции трека одним holder,
  формально лок на репозиторий соблюдён. Работает без правки сервера, но доска показывает
  занятыми задачи, которые ещё не начаты, и `ready` не отдаст их другому харнессу, даже
  когда он свободен.

Первое честнее, второе доступно сегодня.

## Маршрутизация и конфиг конвейера

Таблица `этап → харнессы` из схемы дублирует то, что у конвейера уже лежит
в `.claude/feature-pipeline.yaml`: `executor.primary` → `executor.fallback` → `executor.local`
с правилом «спустился ниже primary — скажи автору и запиши в журнал».

Слить так: **таблица проекта в Листике — источник, конфиг конвейера — фолбэк** на случай,
когда сессия работает без карточки. Цепочка `primary → fallback → local` остаётся в силе
внутри одного этапа: `ready?harness=` отвечает, кому этап разрешён, а живость конкретного
харнесса конвейер по-прежнему проверяет сам (`/grok:check`, `/dsh:dsh-check`) — трекер
о том, что у грока кончилась подписка, не знает.

## Что менять в скилах конвейера

Ни одна из правок не требует переписывать этапы — меняется только обвязка вокруг них.

1. **Шаг 0: два входа.** Аргумент — id карточки: поднимаешься по `listik show`, `claim`,
   работаешь от стадии карточки. Аргумента нет: как сейчас, по каталогу шагов и журналу.
2. **Нарезка порций на s1 создаёт карточки** — по карточке на порцию, `parent-child` к шагу,
   `blocks` между зависимыми, `spec_path` и `acceptance` заполнены сразу.
3. **`blocks` вместо объявленной автором независимости.** Раздел «Треки» перестаёт опираться
   на слово автора там, где есть карточки: параллельны те порции, которые отдал `ready`.
4. **Переходы стадий не молча**: `stage` на каждой границе, `comment -k journal` строкой,
   `comment -k verdict` на вердикте судьи.
5. **Heartbeat раз в 10–15 минут** — у конвейера этапы по 40 минут, без heartbeat задача
   уедет в брошенные.
6. **Вопрос автору выбирает канал** по типу сессии (таблица выше).
7. **Журнал остаётся файлом**, карточка хранит `journal_path`. Дублировать журнал в комментарии
   целиком не надо — в комментарий идёт строка перехода, чтобы холодный старт видел суть,
   не открывая файл.

## Чего не хватает в Листике

Сверх задач, уже выписанных в схеме:

- **поля под чек-лист приёмки.** Сейчас предлагается класть путь в `acceptance`, которое
  задумано под текст критериев. Терпимо, но если чек-лист станет первоклассной сущностью
  (а он у конвейера первоклассная), поле стоит завести;
- **лок на worktree, а не на репозиторий** — см. раздел о треках; без него треки и Листик
  противоречат друг другу;
- **окно ожидания holder — одно на два случая**, вопрос автору и красный вердикт;
- **`release` есть в API и CLI**, но окна ожидания при нём нет — снимает holder сразу;
- **отметка «карточка ведётся конвейером»**, чтобы диспетчер не отдал `s2` порции харнессу,
  который про sticky-группу ничего не знает и разорвёт её на первом же переходе.

Первое и последнее — мелкие; второе меняет семантику `claim` и должно попасть в ту же задачу,
что «Лок „один пишущий агент на репозиторий“».
