# Listik: рабочая спецификация продукта

Статус: draft для реализации в следующей сессии Codex.
Дата: 2026-09-11.

## 1. Цель

Listik должен быть единой очередью, памятью и контрольной панелью для нескольких harnesses:
Claude Code, Codex, dsh/DeepSeek и Grok. Человек запускает Claude в проекте и говорит «пошёл».
Claude читает состояние Listik, выбирает предусмотренный процесс и запускает подходящий harness.
Listik хранит состояние так, чтобы следующий агент мог продолжить работу после холодного старта.

Первая практическая связка:

* Claude/Codex пишут и проверяют ТЗ на этапах `s1-spec` и `s2-review`;
* dsh/DeepSeek выполняет кодинг на `s3-impl`;
* Codex может быть запасным исполнителем кода на terra или luna;
* отдельная проверка кода (`s4-judge`) допускается позже и не блокирует MVP.

## 2. Что считается готовым

Готовый MVP позволяет:

1. Создать задачу с Markdown-ТЗ, критериями приёмки, процессом и допустимыми harnesses.
2. Разбить ТЗ на индексируемые документы и структурные чанки, не теряя исходный файл.
3. Собрать для конкретного этапа компактный контекст через CLI/API.
4. Работать по общему протоколу `ready → claim → heartbeat → stage/comment → done`.
5. Импортировать старые задачи WriterLLM идемпотентно и с сохранением старых ID.
6. Увидеть на desktop/tablet доске состояния из прототипов и открыть полную карточку.
7. Открыть на телефоне короткий список задач и краткую карточку без попытки воспроизвести всю доску.
8. Из Claude вручную запускать Codex для `s1/s2`, сохраняя ID задачи и возможность resume.

## 3. Источники истины

Git остаётся источником истины для Markdown-ТЗ, чек-листов, журнала и кода. SQLite Listik
является источником истины для очереди, связей, держателя, этапа, событий, индекса и ссылок на
файлы. Текст файла не дублируется вручную в карточке: карточка хранит `spec_path`, ревизию и
индексированные чанки. При изменении файла индекс перестраивается по `content_hash`.

Данные, вычисляемые сервером (`ready`, `blocked`, health, stage duration), нельзя вводить в UI
как свободный статус. UI только показывает их и вызывает предусмотренные команды.

## 4. Процесс и гранулярность

Единица работы конвейера — карточка-порция. Родительская карточка шага содержит общее ТЗ и
декомпозицию; дочерние карточки проходят `s2 → s3 → s4 → done`. Порции связываются `blocks`,
если порядок обязателен. Предложенные моделью связи до подтверждения человеком записываются как
мягкие `relates-to` или suggestion.

Переходы по умолчанию:

| Переход | Семантика |
| --- | --- |
| `s1 → s2` | sticky: автор ТЗ продолжает критиковать все порции в одной живой сессии |
| `s2 → s3` | handoff: держатель снимается, следующую задачу берёт разрешённый исполнитель |
| `s3 → s4` | sticky: проверка видит то же рабочее дерево до коммита |
| `s4 → s3` | sticky с окном ожидания при красном вердикте; после окна — release |
| `s4 → done` | handoff после коммита и зелёного вердикта |

Прямая задача без конвейера остаётся допустимой для мелких изменений. Порог выбора процесса
задаётся человеком или оценщиком; автоматическое включение четырёх этапов для любой мелочи не
требуется.

## 5. Общий протокол harness

Каждый harness получает ID задачи и проект, затем:

1. выполняет `listik ready`/`listik show` и проверяет зависимости;
2. делает `claim` с явным holder;
3. оставляет heartbeat каждые 10–15 минут;
4. пишет переходы и решения в `comment -k journal`, review в `-k review`, вердикт в `-k verdict`;
5. ставит `stage` только в момент перехода;
6. задаёт вопрос человеку через `needs-owner`, а не теряет его в консоли;
7. закрывает через `done -r` с кратким результатом.

Полный текст, пригодный для установки в `AGENTS.md`/WriterLLM, находится в шаге 02.

## 6. Архитектурные изменения

### 6.1 Документы и чанки

Добавить сущности `documents` и `document_chunks`:

```text
documents(id, task_id, kind, path, revision, content_hash, title, created_at, updated_at)
document_chunks(id, document_id, ordinal, heading, breadcrumb, text,
                start_line, end_line, token_count, content_hash)
```

`kind` минимум: `spec`, `checklist`, `review`, `decision`. Markdown режется по заголовкам,
крупные разделы дополнительно режутся по размеру с небольшим overlap; в текст каждого чанка
входит breadcrumb заголовков. FTS и embeddings ссылаются на чанки, а поиск агрегируется обратно
к задаче и документу.

Добавить `listik context <id> --stage <stage> [--portion <name>] [--format text|json]`.
Для `s2` контекст содержит всё ТЗ и чек-лист. Для `s3/s4` — карточку, нужную порцию,
критерии, последний review/verdict и релевантные чанки с ограничением размера.

### 6.2 Маршрутизация и зависимости

В конфигурации проекта хранить `stage → harnesses` и типы переходов. `ready --harness X` должен
фильтровать по этой таблице. Декомпозиция и предложения зависимостей создаются агентом на s1,
но hard blocker требует подтверждения человека или явной команды.

### 6.3 Импорт WriterLLM

Сделать отдельную команду с `--dry-run`, журналом и повторяемым ключом
`(project, source, external_ref)`. Повторный импорт не переписывает существующую задачу.
Сохраняются старый ID, статус, описания, acceptance, зависимости, даты, результаты и ссылки на
исходные файлы.

### 6.4 Запуск Codex из Claude

Первый вариант — один тонкий skill/скрипт, а не новый оркестратор. Он получает ID задачи,
собирает `listik context`, запускает `codex exec --model ... --cd ...`, передаёт инструкции
этапа и сохраняет session ID/output в журнал. Для продолжения используется `codex exec resume`.
Claude остаётся ответственным за выбор задачи и переходы.

## 7. UI

Desktop/tablet реализует прототипы `Main`, `BoardLight`, `CardStates`, `TaskPanel`, `NewTask`
в Vue 3 с `@zoloto585/facet`. Компоненты Facet используются по их назначению; ручные аналоги
кнопок, drawer, badge, table и timeline запрещены. Канбан допускает нативный DnD только как
механизм просмотра/локальной навигации, переход этапа всё равно делает серверная команда.

Инварианты интерфейса:

- **Иконка вместо текста, если она экономит место.** Где у значения есть своя иконка (тип,
  приоритет, здоровье и т. п.), в плотных местах — таблице списка, карточке, чипах — выводится
  только иконка, а подпись уходит в `title`/тултип. Текст рядом с иконкой — только там, где места
  достаточно и без подписи значение не опознать (кнопки шапки «иконка + текст», модалки).
- **Повторяющиеся значения — только из справочника.** Тип, приоритет, этап и статус (ключи,
  подписи, иконки, цвета) перечислены в одном месте — `web/src/lib/dictionaries.ts`. Фильтры,
  модалки, глифы, доска и витрина берут списки оттуда; свои копии массивов и словарей подписей
  в компонентах запрещены. Фильтр показывает ровно значения справочника, а не то, что нашлось в базе.

Минимальная ширина доски — 1024 px. При меньшей ширине показывается сокращённый режим: список
задач с проектом, этапом, health, holder и коротким заголовком; детали открываются drawer/page.
Полная мобильная канбан-доска, метрики и drag-and-drop в мобильном MVP не входят.

## 9. Проверки до релиза

* холодный старт: новый harness получает всю нужную информацию из `show/context`;
* повторный импорт не создаёт дубликаты;
* `ready` не отдаёт задачу с незакрытым hard blocker или чужим holder;
* чанки и поиск возвращают правильную задачу и заголовок раздела;
* sticky/handoff сохраняют заявленную непрерывность;
* ширина 1024 px не ломает board layout;
* мобильный режим остаётся коротким просмотром;
* Codex resume продолжает ту же задачу и не теряет журнал.

Подробная критика объёма и решений: [self-critique.md](self-critique.md).
