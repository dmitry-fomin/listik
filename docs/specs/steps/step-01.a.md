# Порция 01.a. Тестовый каркас и правки чанкера

## Контекст

Репозиторий Listik: чистый stdlib-Python-бэкенд без менеджера пакетов, CLI `bin/listik`,
пакет `listik/`. Автоматических Python-тестов в проекте **нет** (`CLAUDE.md` прямо так и
говорит) — эта порция их заводит. Резка Markdown на чанки уже реализована в
`listik/documents.py` (`_split_markdown`, `index_document`, `index_task_documents`); схема
таблиц `documents`, `document_chunks`, `document_chunk_fts` уже есть в `listik/db.py` (`SCHEMA`).

Зачем чанки: карточка задачи хранит только пути (`tasks.spec_path`, `checklist_path`,
`review_path`, `decision_path`, `journal_path`), а текст файлов индексируется в
`document_chunks` по заголовкам Markdown. У каждого чанка есть `heading`, `breadcrumb`
(цепочка заголовков через « / »), `text` (начинается с breadcrumb), `start_line`/`end_line`
(строки исходного файла, с 1), `token_count`, `content_hash`. Раздел длиннее `MAX_CHARS`
(6000 символов) режется на несколько чанков по абзацам с overlap `OVERLAP` (240 символов).
Повторная индексация неизменённого файла ничего не пересчитывает (сравнение `content_hash`);
изменённый файл получает `revision + 1` и полную замену чанков.

Прочитай `listik/documents.py`, `listik/db.py`, `listik/textutil.py` и `listik/store.py`
(функции `create_task`, `update_task`, `event`) перед началом.

## Что сделать

### 1. Каркас тестов

- Создать каталог `tests/` с `tests/__init__.py`, чтобы `python3 -m unittest discover tests`
  находил модули `tests/test_*.py` из корня репозитория.
- Создать `tests/helpers.py` с общей заготовкой: контекст-менеджер или базовый класс, который
  создаёт временную базу через `listik.db.init(<tmp path>)` во временном каталоге
  (`tempfile.TemporaryDirectory`) и удаляет её после теста. Рабочая база `listik.db` в корне
  репозитория тестами **не трогается никогда**: `paths.DB_PATH` не переопределять глобально,
  передавать путь явно в `db.init(db_path=…)`/`db.connect(db_path=…)`.
- Создать `tests/fixtures/` и положить туда минимум три Markdown-фикстуры, сгенерированные
  детерминированно (без случайности во время теста — файлы лежат в репозитории как есть):
  - `long-spec.md` — не короче 25 000 символов; заголовки `#`, `##`, `###` минимум трёх уровней;
    один раздел `##` длиннее 15 000 символов, состоящий из абзацев, в середине которого стоит
    уникальная фраза (например, строка вида `ксилофонный-градиент-42`), не встречающаяся
    больше нигде в фикстурах;
  - `lists.md` — раздел, в котором один маркированный список без пустых строк между пунктами
    длиннее `MAX_CHARS`, чтобы проверить резку по пунктам;
  - `fenced.md` — раздел с блоком кода в тройных обратных кавычках, внутри которого есть строка,
    начинающаяся с `# ` (выглядит как заголовок, но заголовком не является), и после блока —
    настоящий заголовок `## …`.
  - `checklist.md` — короткий чек-лист из нескольких пунктов `- [ ] …`.
- В `CLAUDE.md` заменить фразу о том, что тестового набора нет, на команду
  `python3 -m unittest discover tests` и одну строку о том, что тесты работают на временной
  базе и не требуют сервера и Ollama. Другие разделы `CLAUDE.md` не трогать.

### 2. Правки чанкера в `listik/documents.py`

- Дать резке публичное имя `split_markdown(content, limit=MAX_CHARS)`; `_split_markdown`
  оставить как алиас, чтобы существующие вызовы не сломались.
- **Заголовки внутри code-fence не считаются заголовками.** Строки между открывающей и
  закрывающей `` ``` `` (в том числе с языком: ```` ```python ````) не проверяются регуляркой
  `_HEADING`, и секция не рвётся. Сейчас `# comment` внутри блока кода начинает новую секцию —
  это ошибка.
- **Длинный список режется по пунктам.** Если абзац (группа строк без пустых) длиннее
  `chunk_limit` и его строки начинаются с маркера списка (`-`, `*`, `+`, `N.`, `N)`; возможны
  ведущие пробелы для вложенных пунктов), сначала делить на группы пунктов, не превышающие
  лимит; посимвольная резка (существующий «hard split») остаётся только для одиночного пункта
  или абзаца, который сам по себе длиннее лимита. Границы `start_line`/`end_line` у таких
  чанков должны указывать на реальные строки пунктов.
- **Бюджет накопления учитывает хвост overlap.** Сейчас при переполнении новый накопитель
  собирается как `tail(<= OVERLAP) + "\n\n" + text(<= chunk_limit)`, то есть до
  `chunk_limit + OVERLAP + 2`, и на следующем переполнении уходит в чанк целиком — так чанк
  вырастает до `limit + 242`. Это дефект, его чинить: абзац добавляется к накопителю только если
  `len(накопитель) + 2 + len(text) <= chunk_limit`, где накопитель уже содержит перенесённый
  хвост; если сам `tail + "\n\n" + text` не помещается, хвост укорачивается до
  `chunk_limit - len(text) - 2` символов (вплоть до нуля — тогда overlap у этой пары не будет).
- **Политика overlap** (явная, чтобы не спорить с резкой по пунктам):
  - символьный overlap — перенос последних `OVERLAP` символов предыдущего чанка в начало
    следующего — применяется только (а) между соседними чанками, набранными из абзацев
    обычного текста одной секции, и (б) между кусками hard-split одного абзаца;
  - overlap **не применяется** между группами пунктов списка (граница проходит по целому
    пункту, ничего не повторяется), между чанком и первым куском hard-split следующего
    абзаца, а также между чанками разных секций;
  - следовательно, гарантия overlap — не «у всех соседних чанков», а «в длинном разделе из
    абзацев обычного текста существует хотя бы одна пара соседних чанков с overlap».
- Инвариант: длина `text` каждого чанка не превышает `limit` (включая префикс breadcrumb),
  кроме случая, когда один непрерывный отрезок без пробелов длиннее лимита. После правки
  бюджета выше этот инвариант выполняется и на overlap-хвосте.
- Повторная резка одного и того же текста даёт побайтно одинаковый список чанков
  (детерминизм); порядок — по `start_line`.

### 3. Тесты (все на stdlib `unittest`, без сети, без сервера)

`tests/test_chunking.py`, работает над `split_markdown` без базы:
- каждый заголовок фикстуры `long-spec.md` даёт хотя бы один чанк с этим `heading`, а
  `breadcrumb` для `###` содержит и `#`, и `##` над ним через « / »;
- `text` каждого чанка начинается со своего `breadcrumb`;
- для каждого чанка `1 <= start_line <= end_line <= число строк файла`, и строка
  `start_line` исходного файла принадлежит секции этого заголовка;
- раздел длиннее 15 000 символов даёт не меньше трёх чанков; уникальная фраза из середины
  раздела попадает хотя бы в один чанк, и `heading` этого чанка — заголовок именно этого
  раздела;
- overlap по политике §2: в разделе `long-spec.md` длиннее 15 000 символов (он состоит из
  абзацев обычного текста) существует хотя бы одна пара соседних чанков N, N+1, у которой
  последние `OVERLAP` символов текста чанка N (без префикса breadcrumb) встречаются в начале
  текста чанка N+1 (после префикса breadcrumb);
- `fenced.md`: строка `# …` внутри блока кода не становится `heading` ни одного чанка, а
  настоящий `##` после блока — становится;
- `lists.md` (в фикстуре ни один пункт не длиннее `MAX_CHARS`, поэтому hard-split в ней не
  срабатывает): каждый чанк после префикса breadcrumb начинается с маркера списка, ни один
  пункт не разрезан посередине, overlap между группами пунктов отсутствует (первая строка
  чанка N+1 не встречается в чанке N);
- `len(text) <= MAX_CHARS` для всех чанков всех фикстур, в том числе для чанков, начавшихся с
  overlap-хвоста (тест «переполнение на хвосте»: обычные абзацы, подобранные так, что
  `tail + абзац` превышает лимит; до правки бюджета такой чанк длиннее `MAX_CHARS`);
- два вызова подряд дают равные списки.

`tests/test_index_documents.py`, работает на временной базе:
- создать задачу через `store.create_task(conn, title=…, project=…)` без документов, затем
  `documents.index_document(conn, task_id, <абсолютный путь к копии long-spec.md во временном
  каталоге>, kind="spec")`; проверить, что в `documents` одна строка с `revision == 1`, в
  `document_chunks` и `document_chunk_fts` одинаковое число строк > 0;
- вызвать `index_document` второй раз с тем же файлом: число строк в `documents`,
  `document_chunks`, `document_chunk_fts` не изменилось, `revision` остался 1, `updated_at`
  не изменился, событий (`events` с `kind='document_error'`) нет;
- дописать в файл новый раздел `## …` и вызвать снова: `revision == 2`, число чанков выросло
  ровно на число новых чанков, в `document_chunk_fts` нет строк с `chunk_id`, которых нет в
  `document_chunks`;
- укоротить файл так, чтобы чанков стало меньше: в `document_chunks` и `document_chunk_fts`
  нет строк с ordinal больше нового числа чанков (сирот не осталось);
- `store.create_task(..., spec_path=<путь>, checklist_path=<путь к checklist.md>)`
  индексирует оба документа сам (`kind` = `spec` и `checklist`).

## Границы правки

- Правятся только: `listik/documents.py` (резка и алиас), `tests/**`, `CLAUDE.md` (одна фраза
  о тестах). Ничего больше.
- Не менять схему базы (`listik/db.py`, `alembic/`), `listik/search.py`, `listik/embed.py`,
  `listik/server.py`, `listik/client.py`, `bin/listik`, функцию `documents.context()` —
  это следующие порции.
- Не менять формат и содержимое таблиц `documents`/`document_chunks`/`document_chunk_fts`,
  схему идентификаторов чанков (`<doc_id>:<ordinal>`) и хеши: на них опираются embeddings.
- Не менять `MAX_CHARS`/`OVERLAP` и логику сравнения `content_hash`.
- Не подгонять тесты под текущее поведение: если тест из списка выше падает на текущем коде
  (code-fence, списки, переполнение на overlap-хвосте), чинится код, а не ослабляется тест.
- Не трогать рабочую `listik.db`, `listik.log`, `config.toml`. Не запускать сервер.
- Не добавлять зависимостей (pytest и т.п.) — только stdlib.

## Как проверить

```sh
python3 -m unittest discover tests -v          # все тесты зелёные
python3 -c "from listik import documents; print(documents.split_markdown('# a\n\n```\n# not heading\n```\n\n## b\n\nтекст'))"
```

Второй вызов должен вернуть чанки только для заголовков `a` и `b`.

### Доказательство «красный до правки»

Базовая ревизия чанкера — коммит `b757cf6` (последний до этой порции). Модуль
`listik/documents.py` нельзя запустить вне пакета (относительные импорты), поэтому сравнение
делается через отдельное рабочее дерево **вне репозитория**:

```sh
git worktree add /tmp/listik-base b757cf6
cp -R tests /tmp/listik-base/tests
(cd /tmp/listik-base && python3 -m unittest tests.test_chunking -v) 2>&1 | tail -30
git worktree remove --force /tmp/listik-base
```

В этом прогоне тесты `fenced`, `lists` и «переполнение на хвосте» должны быть красными
(остальные тесты чанкера — зелёные или красные, не важно). Хвост вывода (строки `FAIL:`/`ERROR:`
и итог `FAILED (…)`) сохранить в журнал задачи (`listik comment <id> -k journal`) и в отчёт —
судья сверяет по нему, а не повторяет прогон. `git worktree remove` обязателен: дерево не должно
оставаться в `.git/worktrees`.
