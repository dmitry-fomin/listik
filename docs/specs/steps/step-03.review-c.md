# Ревью порции 03.c (документация импорта WriterLLM)

Проверял по коду: `listik/import_writerllm.py`, `bin/listik` (`cmd_import_writerllm`, `show_task`,
парсер), `tests/test_import_writerllm.py`, фикстуры `tests/fixtures/writerllm/*`, текущие
`README.md`, `API.md`, `CLAUDE.md`, а также `step-03.md` и `step-03.d.md` (границы соседней порции).

## Блокирующие

### 1. Ложная предпосылка: `export.jsonl` даёт код возврата 1, а ТЗ и чек-лист считают её «чистой»

ТЗ §5 требует: «Каждая команда … выполняется на временной базе с фикстурой
`tests/fixtures/writerllm/export.jsonl` **без ошибок**, и её описанный эффект (… код возврата)
сверяется живым вызовом». Чек-лист п.3 прогоняет на этой же фикстуре все четыре команды README, а
п.6 подаёт `exit 1` как признак **сломанной** выгрузки (`broken.jsonl`).

Фактически `export.jsonl` содержит запись `WL-a1.1` со связью на несуществующую `WL-missing`
(`tests/fixtures/writerllm/export.jsonl`, предпоследняя строка issue). Импорт кладёт в отчёт одну
ошибку `where="dependency"` (`listik/import_writerllm.py:611-615`), значит `report["ok"] = False`
(`:643`) и CLI возвращает `1` (`bin/listik:314`) — **на каждом** запуске: dry-run, обычном,
повторном и с `--update`. Это закреплено тестами: `test_23_export_jsonl_exits_1_but_creates_tasks`
(`tests/test_import_writerllm.py:401-411`) и `test_20_ok_reflects_absence_of_errors` (`:356-360`).
Чистая фикстура — `export-v2.jsonl`: `test_24_export_v2_jsonl_on_a_clean_db_exits_0` (`:413-422`).

Последствие: исполнитель либо не сможет выполнить §5 как написано, либо «подгонит» текст README
под exit 1 и опишет нормальный импорт как ошибочный; судья по п.3/п.6 получит противоречивые
показания.

Что изменить: в ТЗ §5 и в чек-листе п.3 назвать фикстуру `export-v2.jsonl` для dry-run / импорта /
повтора (ожидаемый код возврата `0`), а `export.jsonl` оставить там, где нужен ненулевой код
(п.6 — вместе с `broken.jsonl`, с явной оговоркой, что причина — намеренно висящая связь
`WL-missing`, а не битый JSON). В чек-листе п.3 прописать ожидаемый код возврата для каждого из
четырёх вызовов отдельно.

## Существенные

### 2. Чек-лист п.3 проходит при полностью неработающем `--update`

Если все четыре команды README идут по одному и тому же файлу, `обновлено: 0` — ожидаемый
результат и при рабочем `--update`, и при вообще ничего не делающем. README при этом утверждает
(ТЗ §1), что `--update` меняет поля содержания и пишет `[import-writerllm] update:` в журнал.

Что изменить: в п.3 четвёртый вызов проверять на **изменённой** выгрузке — импорт
`export-v2.jsonl`, затем `--update --source tests/fixtures/writerllm/export.jsonl` (или наоборот):
`обновлено: 2`, а `./bin/listik --local show WL-a2` показывает журнальный комментарий,
начинающийся с `[import-writerllm] update:`. Тогда и пример в README будет осмысленным (иначе он
показывает команду, которая в примере ничего не делает).

### 3. Ложная предпосылка про `CLAUDE.md`: фразы «There is no automated Python test suite» в файле нет

ТЗ §4 запрещает править эту фразу и предлагает вынести её актуальность в отчёт. В текущем
`CLAUDE.md` её нет: строки 26-33 уже описывают `python3 -m unittest discover tests` («Python test
suite», временная база, без сервера и Ollama). Похоже, ТЗ писалось по устаревшей копии файла.

Что изменить: убрать абзац про эту фразу из §4 (иначе исполнитель потратит цикл на её поиск и на
строку в отчёте ни о чём). Строка про импортёры, которую §4 действительно правит, существует —
`CLAUDE.md:82-83`, и её текст «imported tasks carry `source=beads`» и правда врёт про WriterLLM.

### 4. §4 не говорит, что `CLAUDE.md` — англоязычный файл

Весь `CLAUDE.md` написан по-английски, а §4 диктует содержание правки по-русски. Исполнителю
ничто не мешает вставить русское предложение в середину английского раздела «Architecture».

Что изменить: добавить в §4 «на английском, в стиле соседних пунктов», а в п.12 чек-листа —
проверку языка вставки.

### 5. В README не запланирована фраза «работает с базой напрямую, сервер не нужен»

В Контексте ТЗ это сказано («Команда работает с базой напрямую, как `import-beads`»), но в «Что
сделать» §1 такого пункта нет и в чек-листе нет проверки. При этом на `./bin/listik
import-writerllm --help` этой подсказки не видно: она задана как `help=` подпарсера
(`bin/listik:1018-1019`) и печатается только в общем списке команд `./bin/listik --help`. То есть
README остаётся единственным местом, где пользователь это узнает, — и именно оно рискует
потеряться.

Что изменить: добавить в §1 буллет «команда работает с базой напрямую, `--local` и запущенный
сервер не нужны, HTTP-эндпоинта и MCP-инструмента у импорта нет», и соответствующий пункт
чек-листа.

### 6. Ни порция c, ни порция d не впишут в README реальные числа — это надо сказать явно

Соседний раздел «Импорт из beads» (`README.md:210-212`) содержит фактические числа живого импорта
(«2909 задач из 26 проектов»). Исполнитель по аналогии напишет «777 задач» — на момент порции c
это ложь (импорт ещё не делался), а порция d поправить не сможет: её границы —
«Порция **не меняет ни одного файла репозитория**» (`step-03.d.md:108`).

Что изменить: в §1 или в «Границы правки» прямо запретить числа живого импорта в README (либо, если
автор их хочет, расширить границы порции d правкой одной строки README — но это решение автора).

### 7. Чек-лист сознательно не проверяет заявление README про поиск по старому ID

П.7 ограничивается видом ID в примере. Но README будет утверждать, что старая задача находится
через `search … --mode text` по старому ID. Это проверяемо на фикстуре: `store._index_task` кладёт
`external_ref` в тело FTS, так что после импорта `./bin/listik --local search WL-a1 --mode text`
обязан вернуть задачу.

Что изменить: добавить в п.7 живой прогон `search` по фикстурному ID (и `show WL-a1`, если хочется
одной командой) — иначе единственное функциональное обещание раздела остаётся на слово автора.

### 8. Ни в ТЗ, ни в чек-листе нет предупреждений (`warnings`) и подстановок по умолчанию

CLI печатает отдельную строку `предупреждений: N (подробности в --json)` (`bin/listik:310-311`), а
неизвестный статус тихо становится `open`, неизвестный приоритет — `2`
(`listik/import_writerllm.py:152-179`; в фикстуре это `WL-a9` со `status="weird"`, `priority="x"`).
На живой выгрузке (порция d) исполнитель увидит эту строку и не найдёт ей объяснения в README,
который по ТЗ описывает только счётчики, ошибки и код возврата.

Что изменить: в §1 (буллет «Отчёт») добавить фразу про предупреждения и про то, что незнакомые
статус/приоритет не роняют импорт, а заменяются значениями по умолчанию; в чек-лист — пункт на
наличие этой фразы.

## Заметки

9. **Оба условных пункта §2 разрешаются в «ничего не делать»** — стоит написать это прямо, чтобы
   исполнитель не искал: в «Агентам: MCP и CLI» (`README.md:247-263`) перечня CLI-команд с
   `import-beads` нет (только MCP-инструменты), в «Структура базы» (`README.md:265-269`) поле
   `source` не упоминается. А вот в `API.md` строка `source` есть (`| source | str | native \|
   beads (импортированные задачи) |`), так что §3 можно формулировать утвердительно, без «если
   есть».

10. **Альтернатива, которую ТЗ выбирает молча**: вместо второго раздела можно было слить оба в
    «## Импорт старых трекеров» с двумя подразделами — источник данных у них один (beads),
    различаются транспорт (`issues.jsonl` против `bd export`) и путь. Минус текущего решения: два
    соседних раздела разного жанра — «Импорт из beads» описывает свершившийся факт, новый раздел
    будет инструкцией на будущее. Если автор осознанно берёт отдельный раздел — вопрос закрыт.

11. **П.1 чек-листа не докажет «сразу после»**: `grep -n "^## Импорт"` не покажет чужой заголовок,
    вставленный между двумя разделами. Надёжнее `grep -n "^## " README.md` и проверка соседства
    строк.

12. **Фиксированный путь базы в «Как проверить»** (`/tmp/listik-step03c.db`, ТЗ:120): при
    повторном прогоне база не пуста, и «dry-run → база пуста» / «создано: N» перестают
    воспроизводиться. Стоит взять `mktemp`-путь или пометить «путь должен быть новым».

13. **Неточность в Контексте (ТЗ:25)**: «`--json` печатает отчёт целиком (с сырыми
    ненормализованными записями)» — сырая запись прикладывается только к элементам `errors`
    (`raw`, `listik/import_writerllm.py:484-485`), а не ко всему отчёту. В §1 сформулировано
    верно; поправить Контекст, чтобы обобщение не уехало в README.

14. **`--source` в help всё ещё обещает каталог Markdown** (`bin/listik:1020`: «JSON/JSONL файл или
    каталог Markdown»), хотя каталог теперь отвергается как источник
    (`test_12_directory_and_markdown_are_rejected_as_source`). README, естественно, Markdown
    упоминать не должен; полезно попросить исполнителя вынести это расхождение строкой в отчёт —
    правка `bin/listik` за границами порции c.
