# Шаг 04. Маршрутизация и зависимости

## Цель

Сделать выбор harness и порядок порций данными проекта, а вычисление готовности — механическим.
Claude остаётся интерактивным диспетчером; Listik не превращается в автономного оркестратора.

## Требования

1. Хранить в проекте или его конфиге разрешённых harnesses по этапам и default process.
2. Реализовать `ready --harness <name>` и API-фильтр с тем же результатом.
3. `claim` отклоняет задачу с открытым hard blocker и сообщает блокер, holder и варианты действий.
4. На s1 агент может записать dependency suggestions; hard `blocks` появляется только после
   подтверждения человека или явной команды.
5. Проверять циклы при добавлении hard dependency.
6. Поддержать sticky/handoff-переходы и окно возврата после красного verdict в журнале событий.
7. Локировать `(repository, worktree)`; пустой worktree означает основное дерево и конфликтует
   с другим пишущим holder.

## Рекомендованный поток

Claude читает `ready`, выбирает процесс по карточке и проектному routing config, запускает
разрешённый harness с ID задачи. Harness сам делает claim и stage. Claude не переписывает
чужие карточки и не создаёт hard blockers только на основании догадки модели.

## Критерии приёмки

* Независимые порции одновременно появляются в `ready`; зависимая — только после закрытия
  блокера.
* `ready --harness codex` не отдаёт задачу, разрешённую только dsh.
* Красный verdict возвращает задачу исполнителю в установленное окно, затем корректно release.
* Повторный `claim` в том же worktree безопасно отказывает или подтверждает текущего holder.
