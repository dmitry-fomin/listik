## Блокирующие

1. **`taskHealth` никогда не вернёт `dead` для `abandoned`, а чек-лист этого требует.**
   Порядок в ТЗ (стр. 68-71): сначала `unknown`, если `!task.holder`, потом `dead`, если
   `stale || abandoned`. В бэкенде `abandoned = orphan or missing_heartbeat`
   (`listik/store.py:543-548`), где `orphan = running and not holder` — то есть основной случай
   «брошена» это **задача без держателя**. По ТЗ она всегда упадёт в `unknown` (прозрачная точка
   «без держателя»), а чек-лист п. 5 требует `abandoned: true → dead`. Плюс сам ТЗ противоречит
   себе: `healthReason` предписывает для abandoned подпись `брошена · без держателя`, то есть
   автор ожидает `dead`. Что изменить: задать порядок явно — `dead` (stale ∨ abandoned) →
   `unknown` (нет держателя и не abandoned) → `at-risk` → `healthy`; и добавить в чек-лист п. 5
   разделение двух видов abandoned: `{status:'in_progress', holder:null}` → `dead`,
   `{status:'open', holder:null}` → `unknown`.

2. **Здоровье не определено для закрытых задач — и они получат оранжевую точку.**
   ТЗ считает `at-risk` по `idle_hours >= 0.25` для любой задачи с держателем. Закрытие задачи
   держателя не снимает (в `listik/store.py` `holder` обнуляется только на handoff-переходе,
   строка 474; в `done`/`close` — нет), а `idle_hours = holder_hours` (строка 545). Значит любая
   закрытая задача с непустым `holder_at` старше 15 минут — `at-risk`, и вся рельса «Готово · 7 дн»
   (порция c) и панель закрытой задачи будут светиться «под угрозой». Что изменить: в §3 `health.ts`
   дописать, что здоровье считается только для незакрытых задач (`status ∉ {done, cancelled}`), а
   для закрытых `taskHealth` возвращает (предложение) `healthy` c подписью «закрыта» либо отдельное
   значение/`null`, и добавить в чек-лист п. 5 случай `{status:'done', holder:'agent:claude',
   idle_hours: 300}`.

3. **Критерий проверки гамм (чек-лист п. 4) основан на неверном факте и останется «красным» после
   правильной правки.** «Обновить» — это `variant="secondary"` (`web/src/components/AppHeader.vue:118`),
   а `.ui-button--secondary` окрашена в `--surface`/`--ink-1`/`--hairline-strong`
   (`UiButton.vue:213-218`), акцента в ней нет вовсе; primary-кнопки в шапке доски нет. Проверяющий,
   переключив гамму, не увидит изменений и решит, что §2 не сделан. Что изменить в чек-листе:
   проверять (а) `getComputedStyle(document.documentElement).getPropertyValue('--accent-500')`
   принимает четыре разных значения при четырёх значениях `data-color-scheme`, и (б) в витрине
   меняет цвет `UiBadge tone="accent"` (единственный акцентный тон бейджа, `UiBadge.vue:60-63`).
   Формулировку «цвет primary-кнопки „Обновить“» убрать.

## Существенные

4. **Карта отвергает не тех кандидатов из кита.** Для `.tc` ТЗ (стр. 43-44) обосновывает свою
   разметку через `UiEntityCard`, но ближайший кандидат — `UiCard`: у него есть ровно то, чего
   «не хватает» — слоты `header`/default/`footer` и `interactive` (`UiCard.vue:27-42, 73-81`).
   Для `.pmark` не упомянут `UiAvatar` (инициалы, но круглый, градиент `--gradient-mark`, без
   цвета на сущность, инициалы берутся из первых букв **двух слов**). Пункт 3 чек-листа принимает
   любую причину («в ките нет такого блока»), то есть карта с неполным разбором пройдёт.
   Что изменить: в §1 потребовать для каждой «своей» строки называть конкретный отвергнутый
   компонент кита и признак, которого не хватает; в чек-листе п. 3 — «в строках `.tc` и `.pmark`
   названы `UiCard` и `UiAvatar` и сказано, чего в них не хватает».

5. **Проверка границ правки (п. 2 чек-листа и `git -C .. diff --stat HEAD` в §«Как проверить»)
   не увидит новых файлов.** Почти всё, что создаёт порция, — untracked, а `git diff HEAD` untracked
   не показывает; так же не будет виден и «левый» новый файл в `views/` или `store/`. Что изменить:
   в обоих местах заменить на `git -C .. status --porcelain` (или `git add -A -n`), и пункт 2
   сформулировать как «список путей из `status --porcelain` совпадает с разрешённым».

6. **Новые поля smoke меряют доску, закрытую дровером, и чек-лист этого не ловит.**
   `report.drawer` кликает по карточке и дровер не закрывает (`web/scripts/smoke.mjs:130-144`),
   `report.layout` считается уже после этого (строка 146). `columnsVisible` по
   `getBoundingClientRect().right <= innerWidth` посчитает и колонки, спрятанные под 720px-панелью,
   а при узком вьюпорте (правило `app.css:836`, дровер на 100vw) число станет вовсе бессмысленным.
   Чек-лист п. 14 требует только «поля присутствуют» — реализация, всегда возвращающая 0/`null`,
   пройдёт. Что изменить: в §7 добавить «перед измерением layout закрыть дровер (Escape) и убедиться,
   что активна вкладка доски»; в чек-листе п. 14 — конкретные числа: при 1440 `columnsVisible ===
   report.columns` и `boardScrollable === false`, при 1024 — ожидаемое автором значение (например
   `columnsVisible >= 4`).

7. **`HarnessIcon` не собирается из `ListikIcon`, а ТЗ обязывает («новые примитивы используют её»,
   стр. 140).** Токены размеров кита — `--icon-xs|sm|md|lg = 12|14|16|20px`
   (`tokens.css:345-348`), 18px среди них нет; `ListikIcon.vue` пишет размер инлайн-стилем, поэтому
   правилом в `app.css` его не перебить без `!important`; `aria-hidden="true"` и слота под `title`
   у неё нет; сам файл `ListikIcon.vue` не входит в список правимых. Что изменить в §5: сказать
   прямо, что `HarnessIcon` рендерит собственный `<svg viewBox="0 0 16 16">` для всех шести
   харнессов (для `human` — путь `icons.user`), габарит берёт из переменных `--listik-hico-*`
   в `app.css`, а `title` вешается на внешний `<span>`, не внутрь `ListikIcon`.

8. **`healthReason` — требование без единого пункта проверки.** В чек-листе есть только `taskHealth`
   (п. 5). Что изменить: добавить пункт с шестью строками из ТЗ (stale → `брошена {idle_age}`,
   abandoned → `брошена · без держателя`, heartbeat → `молчит {idle_age}`, stage_warn → `на этапе
   дольше порога`, healthy → `hb {holder_age}`, unknown → `без держателя`) — и лучше вывести их
   в витрине рядом с точками здоровья, чтобы проверка была визуальной.

9. **`stages.ts` в этой порции ничем не используется, и проверить его нечем, кроме разовых вызовов
   в консоли.** Витрина по §6.4 собирает `UiSteps` из литералов (`s1 · ТЗ и чек-лист` …), а пороги/
   названия здоровья и харнессов — из констант. Пункты 5-8 чек-листа честно пишут «проверяется в
   консоли или временным вызовом», то есть после приёмки следов не остаётся. Что изменить: в §6.4
   потребовать строить `items` для `UiSteps` из `PIPELINE`, а `description` — из `transitionOut()`;
   в легенде брать подписи из `HEALTH_TITLES`/`HARNESS_TITLES`/`PRIORITY_TITLES`. Тогда п. 8
   становится проверкой глазами, а не консольной.

10. **Два источника одних и тех же подписей — и ТЗ не говорит, какой главный.** Сервер отдаёт
    `stage_title` в виде `1. ТЗ и чек-лист` (`listik/store.py:25-31`), ТЗ вводит `stageTitle` →
    `ТЗ и чек-лист`; сервер отдаёт `priority_title` = `P1 высокий` (`store.py:40`), ТЗ вводит
    `PRIORITY_TITLES` = `критичный` из прототипа. `priority_title` прямо сейчас выводится в
    `components/board/TaskCard.vue:153`, `TaskDrawer.vue:356`, `views/ListView.vue:48`. Без решения
    на одном экране будут обе формулировки. Что изменить: в §3 дописать, что клиентские словари —
    единственный источник для доски и панели, а серверные `stage_title`/`priority_title` в новых
    экранах не используются (и в какой порции убираются из старых).

11. **«Подсказка при наведении» нигде не выбрана между нативным `title` и `UiTooltip`.**
    Все пять примитивов в §5 просят нативный `title`, при этом `UiTooltip` уже используется в
    `AppHeader.vue:98,111`. Что изменить: одной фразой в §5 (и строкой в карте) зафиксировать
    «для примитивов — нативный `title`, `UiTooltip` — только там, где подсказка длиннее строки»,
    иначе порции c/d разъедутся.

12. **`UiChip` не принимает разметку — «с точкой-иконкой в тексте» (§6.2) невозможно.**
    У чипа только `label: string`, слотов нет (`UiChip.vue:40-53`). Что изменить: убрать из §6.2

## Заметки

13. Монограмма проекта в прототипе — `font-size: 10px` (`.pmark` в `Main.dc.html`), а ближайший
    токен `--text-xs` равен 12px (`tokens.css:235`): в квадрате 18px две буквы по 12px сядут впритык.
    Раз px внутри объявления переменной в `app.css` разрешены, проще завести
    `--listik-pmark-size: 10px`, чем принимать расхождение молча.

14. Запрет «`px`-литералы только внутри объявлений переменных в `app.css`» не проверяется ни одним
    пунктом (п. 13 грепает только `#hex`), а сам `app.css` сегодня этому правилу не следует
    (`padding-bottom: 32px` в `.listik-shell`, `width: min(100% - 64px, 1440px)`). Либо ограничить
    запрет новыми правилами и добавить греп по `marks/`+`sheet/`, либо снять формулировку.

15. `step-05.md` (стр. 11) говорит «правится только `web/*`», порция создаёт
    `docs/facet-prototype-map.md`. Стоит поправить фразу в файле шага, иначе следующие порции
    унаследуют противоречие.

16. `harnessOf` отправляет в `human` всё неопознанное, включая ключи вида `agent:<новый-агент>`:
    новый агент получит иконку человека и молча растворится в статистике. Вариант — возвращать
    `null` для ключей с префиксом `agent:`, которые не совпали ни с одной подстрокой.

17. Альтернатива к §7: вместо `--window-size` и перезапуска Chrome под каждую ширину —
    `Emulation.setDeviceMetricsOverride` по CDP; тогда один прогон меряет и 1024, и 1440, и
    `viewport.width` получается точным без зависимости от режима headless. Аргумент CLI при этом
    сохраняется.

18. `src/sheet/main.ts` по ТЗ не вызывает `initTheme()`, хотя `sheet.html` жёстко задаёт
    `data-theme="dark"`: сохранённый выбор светлой темы на витрине не применится при загрузке
    (переключатель при этом работает). Одна строка в §6.
