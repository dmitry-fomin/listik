# Работа с Listik

Полное руководство: протокол работы с задачами, конвейер, зависимости, серверный режим,
доска, поиск и подключение агентов. Установка и общее описание — в [README.md](../README.md),
контракт данных и эндпоинтов — в [docs/API.md](API.md), протокол агента — в
[AGENTS.md](../AGENTS.md).

## Как устроена работа

У задачи есть проект, тип, приоритет P0–P4, статус (`open`, `in_progress`, `review`, `done`,
`cancelled`), **держатель** с heartbeat, **этап** и флаг «нужен человек».

```sh
# агент добавляет к каждой команде: --actor agent:<harness> --harness <harness>
listik ready                                        # что можно брать
listik waves --project X                            # волны запуска: что делать одновременно
listik waves --project X --apply                    # записать ресурсные рёбра resource-blocks под этот расчёт
listik plan --project X --apply                      # LLM-проход роя: грубые blocks между открытыми задачами
listik rescope --project X --apply                   # LLM-проход роя: области read_scope/write_scope из готовых ТЗ, уточнение графа
listik show <id>                                    # вся карточка
listik worktree <id>                                # дерево .worktrees/<id>, ветка task/<id>, от HEAD
listik claim <id> --holder claude --note "беру"
listik heartbeat <id> --holder claude --note "…"    # каждые 10–15 минут
listik comment <id> "решение и почему" -k journal
listik stage <id>                                   # следующий этап
listik needs-owner <id> "вопрос человеку"
listik done <id> -r "что сделано"
```

Конвейер: `s1-spec` (ТЗ) → `s2-review` (критика) → `s3-impl` (реализация) → `s4-judge`
(приёмка, `VERDICT: PASS|FAIL`) → `done`. Переход `s1-spec` → `s2-review` освобождает держателя,
чтобы следующий harness взял карточку через `ready` → `claim`; держателя можно выдать явно
(`stage <id> --holder <кому>`). Карточку с `--route <маршрут>` берёт рой; процесс
вручную поднимает `listik launch <id>`.

**Зависимости.** «Заблокирована» — не статус, а вычисление: жёсткие связи (`dep add <id>
<блокер>`) убирают задачу из `ready`, мягкие (`relates-to`, `parent-child`, `discovered-from`)
только информируют. Жёсткую связь от агента без `--confirm` сервер пишет предложением, его
подтверждает человек (`dep confirm`). Найденное по ходу — `new "…" --discovered-from <id>`.

**Серверный режим: у задачи есть хозяин.** По умолчанию Listik локальный — владельца нет и
спрашивать его никто не будет. Один Listik на несколько человек включается в `config.toml`:

```toml
[server]
mode = "server"          # "local" (по умолчанию) или "server"
users = ["ann", "bob"]   # кто работает с этим Listik
```

Тогда у новой задачи обязательно есть владелец, `claim`/`heartbeat` чужой задачи отказывают,
а `list`/`board`/`ready` показывают свои задачи и ничьи. Представиться можно тремя способами,
в порядке приоритета:

```sh
listik --owner ann new "Заголовок"     # флаг у любой команды
export LISTIK_OWNER=ann                # переменная окружения
```

```toml
[auth]
owner = "ann"                          # у каждого в своём config.toml — удобнее всего для команды
```

Владелец виден в `listik show` («владелец: ann») и меняется как поле: `listik set <id> owner=bob`,
`listik set <id> owner=` снимает его. В локальном режиме всё это не действует.

Подробные правила (`claim`, окно возврата, блокировка дерева, маршруты) — в [docs/API.md](API.md),
протокол агента — в [AGENTS.md](../AGENTS.md).

## Доска

`listik token` даёт ссылку. Вкладки: **Доска** (колонки этапов, «Ты нужен»), **Список**
(фильтры и массовая правка), **Метрики**. Этап меняют команды, перетаскивания нет. Помощник
DeepSeek в окне «Новая задача» включается ключом в `[assistant]` конфига (см. docs/API.md).
Голосовой ввод — запись, расшифровка и черновик задачи — включается ключом в `[deepgram]`
(нужны оба ключа).

## Поиск и память

```sh
listik search "как решали X"          # задачи, комментарии, документы; --mode text|vector
listik remember "факт" -p <проект>
listik memory "про что-то"
```

## Подключение агентов

**Плагины Claude Code** — репозиторий является маркетплейсом:

```
/plugin marketplace add dmitry-fomin/listik
/plugin install listik@listik             # скил listik:listik — протокол задач
/plugin install feature-pipeline@listik   # пресеты конвейера *-pipeline и агенты pipeline-*
/plugin install dsh@listik                # DeepSeek Harness: dsh:dsh-delegate
/plugin install codex@listik              # OpenAI Codex CLI: codex:codex-delegate
/plugin install second-opinion@listik     # критика ТЗ: second-opinion:ask
```

Пресеты `feature-pipeline` зовут внешние харнессы скилами этих плагинов; Grok остаётся отдельным
(`grok@grok-build`). `inherit-pipeline`, `opus-single-pipeline` и `opus-sonnet-pipeline` обходятся
субагентами Claude. При изменении плагина поднимайте `version` в его `plugin.json` и в `marketplace.json`.

**MCP** (инструменты `listik_*`, список — в docs/API.md):

```sh
claude mcp add listik -- listik mcp                                          # локально
claude mcp add --transport http listik https://<домен>/mcp \
  --header "Authorization: Bearer <токен>"                                   # удалённый сервер
```

Удалённо сервер оставляют на `127.0.0.1` и выставляют наружу только через HTTPS-прокси
(Caddy/nginx, `proxy_read_timeout` ≥ 120 с). Отдельного «удалённого режима» у CLI нет: он ходит
на `server.host`/`server.port` из своего `config.toml` — укажите там адрес нужного сервера.

**Правила в проектах**: `listik projects --add <путь>`, затем `listik init-projects` вписывает
протокол в `AGENTS.md`/`CLAUDE.md` проектов и `.worktrees/` в их `.gitignore`.
Блок, чья метка версии протокола (`<!-- listik-protocol: N -->`) новее ставящегося шаблона,
пропускается с предупреждением `! пропущен`; перезаписать его — `listik init-projects --force`.

### Stop-хук Claude Code

`listik lint --stop-hook` не даёт Claude закончить ход, пока в карточках проекта есть
несостыковки (`listik lint`). Хук — локальная настройка, в репозиторий не кладётся
(`.claude/*` в `.gitignore`). Подключить — добавить в `.claude/settings.json` проекта (или в
`~/.claude/settings.json`, чтобы во всех проектах):

```json
{"hooks": {"Stop": [{"hooks": [{"type": "command",
  "command": "listik lint --stop-hook 2>/dev/null || true"}]}]}}
```

Команда — установленный `listik` из PATH, а не `bin/listik` репозитория. Обёртка
`2>/dev/null || true` обязательна: пока глобальный `listik` не обновлён релизом и не знает флага,
argparse выйдет с кодом 2, а код 2 у Stop-хука **блокирует** ход; `|| true` и глушение stderr
делают старую установку безвредной.

При находках команда печатает `{"decision": "block", "reason": …}` — первая строка причины
`listik lint: N несостыковок в проекте <slug> — …`, дальше до 20 находок `<id>  <rule>  <message>`
(остальные — `… и ещё K`), и Claude продолжает ход, чтобы их исправить. Без находок, без проекта
(`--project` → `LISTIK_PROJECT` → каталог), без базы или при любой своей ошибке — пустой вывод и
код 0: хук не блокирует ход из-за собственной поломки. Карточек, комментариев и событий хук не
меняет.

Не зацикливается: если ход уже продолжен этим хуком, Claude Code передаёт на stdin
`"stop_hook_active": true`, и хук молча отпускает ход — второй круг не устраивается.

Проверить руками: `echo '{}' | listik lint --stop-hook --project listik`. Отключить — убрать
блок `hooks.Stop` из `settings.json`.

## Проект по рабочему каталогу

Команды `ready`, `list`, `board`, `stats`, `search`, `blocked`, `new`, `inbox`, `timeline` и `lint`,
если проект не задан явно, определяют его по текущему каталогу. Проект подставляется как
значение `--project`, поэтому вызов из каталога проекта показывает очередь этого проекта,
а не всех сразу.

```
# проект определён по каталогу: listik (все проекты: --project all)
```

Порядок источников: явный `--project`/`-p` → переменная `LISTIK_PROJECT` → каталог → без
фильтра. `LISTIK_PROJECT` трактуется как явный флаг: несуществующий slug не ошибка, просто
пустая выдача. Строка «проект определён по каталогу» печатается только когда сработал
каталог, и только в человеческом режиме — при `--json` её нет, stdout остаётся валидным JSON.

Как ищется проект: сравнивается `projects.path` (колонка «Путь» у `listik projects`) — путь
проекта должен совпасть с каталогом или быть его предком, побеждает самое длинное совпадение
(вложенный проект перебивает объемлющий). Каталог внутри `<path>/.worktrees/<id>` — тот же
проект. Если по путям ничего не совпало, первый сегмент каталога внутри
`[import].projects_root` из `config.toml` берётся как slug проекта. Каталог вне всех проектов —
как раньше: без фильтра, без ошибки.

Значение `all` (`--project all`, `LISTIK_PROJECT=ALL`, регистр не важен) зарезервировано под
«все проекты»: фильтр не подставляется, автоопределение не работает. Поэтому проект со
slug `all` выбрать этим CLI нельзя. Автоопределение есть только у перечисленных команд:
у `memory`, `remember`, `dep suggested`, `import-from-bd` и `projects` тот же `--project`
значит другое.

## Рой: `listik-swarm`

`listik-swarm` — бинарь на Node (только stdlib), который доводит волну задач проекта до конца
без модели и без своего состояния: каждый тик читает проект заново через `bin/listik --json`
(волны, список, маршруты, карточки) и решает жадно по правилам (кто в партии, кто перезапускается,
кто уходит человеку), а весь итог — в Listik (карточки, события, метки, лог). Процесс остаётся
запущенным: когда запустить нечего (вопрос человеку, пустая область, пустая доска, ещё бежит
партия), он спит `--interval` и читает доску снова — сняли флаг или дописался этап, следующий
тик запускает сам. Падение роя переживается перезапуском: он ничего не хранит между запусками
и не задваивает уже бегущую работу — сам видит её по карточкам. Рой не верит отчёту
воркера: перед слиянием — верификатор в дереве и проверка диффа (см. „Барьер волны“).

Перед первой волной: `listik plan --project X --apply` расставляет грубые зависимости `blocks`
между открытыми задачами проекта (модель — только для порядка написания ТЗ, не для точности) —
проверить результат `listik waves`.

После волны ТЗ — руками: `listik rescope --project X --apply` — читает готовые ТЗ
(`spec_path`), пишет `read_scope`/`write_scope` по ним и уточняет граф `blocks` по копилке
расхождений («объявил X, тронул Y» из `listik watch` и барьера). После каждой влитой волны рой
зовёт `listik rescope --project X --apply` сам (см. «Барьер волны», шаг 11); метрика качества
ТЗ — в строке `rescope:` лога роя.

Пока в `config.toml` стоит `[swarm] enabled = true`, рой поднимает сам `listik serve`:
один процесс на все проекты, круг каждые 30 секунд. Установщик спрашивает, включать ли
его, и пишет ответ в этот ключ; то же делают `listik swarm on` и `listik swarm off`.
Сервер перечитывает флаг и поднимает процесс заново, если тот умер. Выключенный рой
карточки не запускает.

Ручной запуск остаётся для одного проекта. Требования: `node` ≥ 22, поднятый сервер
Listik, `listik` в `PATH` (или `--listik`):

```sh
node <репозиторий>/bin/listik-swarm [--project <slug>] [--parallel 3] [--once] [--dry-run]
```

Без `--project` рой сам берёт каждый проект, где есть открытая карточка, вопрос человеку
или закрытая карточка с ещё не снятым деревом.

Флаги (у всех есть значение по умолчанию; `--project` можно не указывать):

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--project <slug>` | все проекты с работой | один проект; без флага рой обходит все |
| `--parallel <N>` | 3 | ёмкость партии в единицах веса |
| `--weights xhigh=3,high=2,medium=1,low=1,xlow=1,direct=1` | см. слева | частичное переопределение весов уровня маршрута |
| `--port-base <N>` | 5170 | начало диапазона портов для `LISTIK_DEV_PORT` |
| `--port-count <N>` | 100 | размер диапазона портов |
| `--interval <сек>` | 30 | пауза между тиками |
| `--stale-minutes <N>` | 20 | окно тишины бегущей задачи до перезапуска |
| `--timeout-minutes <N>` | 0 | предел времени процесса закрытой задачи (0 — без предела) |
| `--max-restarts <N>` | 1 | сколько раз перезапускать одну задачу, прежде чем оставить человеку |
| `--budget-minutes <N>` | 0 | стенное время прогона в минутах (0 — без предела) |
| `--max-launches <N>` | 0 | запуски + перезапуски за прогон (0 — без предела) |
| `--cli-timeout <сек>` | 120 | предел одного вызова `listik` |
| `--once` | — | один тик и выход |
| `--exit-when-idle` | выключен | выйти, когда запустить нечего: код 0, если открытых задач нет, код 2, если они есть. Без флага рой этого не делает и остаётся в процессах |
| `--dry-run` | — | один тик без единой записи — только план и намерения в лог |
| `--listik <путь или имя>` | `listik` | бинарь `listik` |
| `--listik-host <host>` | — | `--host` для вызовов `listik` |
| `--listik-port <port>` | — | `--port` для вызовов `listik` |
| `--log-dir <путь>` | `$LISTIK_HOME/logs`, если задан `LISTIK_HOME`, иначе `logs/` репозитория | каталог лог-файла роя |

Все записи роя в карточки идут от автора `agent:listik-swarm`.

Что рой пишет в карточки: needs-owner с понятным текстом («у задачи нет маршрута», «нет
write_scope», «процесс завершился кодом …», «задача зависла»), рабочее дерево и ветку
(`listik worktree`, `.worktrees/<id>`, `task/<id>`), метку `port:<n>` (см. «Порты» ниже),
события `revoke`/журнал `launch` при запуске и перезапуске.

**Партия.** Проект раскладывается на волны (`listik waves`, см. «Как устроена работа»); рой
берёт первую волну целиком, пока не влезет по `--parallel` (вес по уровню маршрута из
`--weights`), и не трогает следующую, пока текущая партия не закроется — задача следующей волны
не стартует раньше, чем закроется последняя задача текущей.

**Надзор.** Бегущая задача, молчащая дольше `--stale-minutes`, и упавший без `done` процесс —
разные случаи: упавший процесс рой не перезапускает сам (needs-owner и ждёт человека), зависший
перезапускает автоматически (`revoke` снимает процесс, новый `launch` поднимает поколение).
Мягкий вопрос исполнителя (строка `по умолчанию:` в тексте, см. ниже) флаг `needs_owner` не
считает остановкой: надзор за бегущей продолжается. Жёсткий вопрос (без этой строки, или вопрос
самого роя) — как раньше, задача ждёт человека. После предела `--max-restarts` рой снимает
процесс и ставит `needs-owner`, дальше руками: `listik release <id>` (держатель остаётся после
отзыва) и `listik needs-owner <id> --clear "…"` — тогда задача возвращается в партию на
следующем тике.

**Бюджет.** Два предела на процесс роя: `--budget-minutes` (стенное время с момента старта) и
`--max-launches` (запуски + перезапуски за прогон). `0` — без предела. Исчерпан — новых запусков
и перезапусков нет: зависшая, упавшая-с-ответом и отклонённая верификатором уходят человеку с
текстом «бюджет прогона исчерпан», бегущие дорабатывают, барьер продолжает вливать закрытые.
Когда никто не бежит — выход с кодом `5`. Перезапуск роя начинает счёт заново. Деньги на задачу
для маршрутов `claude` — флаги `--max-turns` / `--max-budget-usd` в команде маршрута
(`listik routes`); рой их не подставляет и доллары не считает.

**Порты.** Каждой запущенной задаче — метка `port:<n>` из диапазона `--port-base`…`--port-base
+ --port-count`, и переменная окружения процесса `LISTIK_DEV_PORT=<n>`: харнесс/дев-сервер
внутри дерева задачи обязан слушать именно этот порт (правило 11 `docs/harness-protocol.md`).
Не `LISTIK_PORT` — та переменная занята портом самого сервера Listik. Порт закрытой задачи
освобождается и достаётся следующей задаче партии.

**Коды выхода**: `0` — с `--exit-when-idle` открытых задач не осталось, либо бюджет исчерпан и
бежать уже некому; `1` — цикл в зависимостях на единственном тике `--once` (в длинном прогоне
цикл не останавливает рой, следующий тик читает доску снова); `2` — с `--exit-when-idle` есть
открытые задачи, но запустить нечего, либо второй рой того же проекта в том же `--log-dir`
уже жив (pid в `swarm-<проект>.pid`); `3` — сервер Listik не отвечает на единственном тике
`--once` (в длинном прогоне рой ждёт и повторяет); `4` — необработанная ошибка в `--once`;
`5` — бюджет прогона исчерпан, бегущих не осталось (бюджет — на процесс роя, перезапуск роя
начинает счёт заново); `130`/`143` — `SIGINT`/`SIGTERM`. `SIGHUP` (закрытый терминал) рой не
останавливает: строка в логе и следующий тик. Пока запустить нечего, в лог один раз пишется
`жду:` — повторно только когда набор открытых задач изменился. Перезапуск безопасен: рой
смотрит на реальное состояние карточек, а не на свою память, поэтому не задваивает уже
бегущую работу.

Сводка тика (stdout и лог) всегда печатает сегмент `дефолт N (ids)` — сколько мягких вопросов
рой закрыл автоответом в этом тике; без поля в отчёте — `дефолт 0 ()`.

Лог: `logs/swarm-<project>-<штамп>.log` (или `--log-dir`) — все пишущие вызовы и решения роя,
путь печатается первой строкой в stdout; лог самого воркера — в `launch_log` карточки (`listik
show <id>`).

### Барьер волны

Барьер срабатывает раз в тик, когда никто не бежит (`running` пуст) — партия только что
закрылась или ещё не началась. Он вливает закрытые задачи роя в основную ветку проекта по
одной, разбирает конфликты (сам или через арбитра), гоняет интеграционные тесты и убирает
деревья влитых задач, прежде чем рой возьмёт следующую волну.

Шаги в каждом тике барьера:

1. **Кандидаты** — задачи проекта со статусом `done`, непустым `worktree` (не `main`/`master`)
   и меткой `port:<n>` (признак задачи роя). Кандидат с жёстким открытым `needs_owner` или
   недостающим деревом/веткой не трогается — остаётся «не влита»; при жёстком вопросе барьер
   только пишет в лог «ждёт человека», повторный needs-owner не ставит. Мягкий вопрос слиянию
   не мешает (см. «Мягкий вопрос»).
2. **Порядок** — по времени первой правки в дереве (комментарий `рой: первая правка замечена:`,
   если он есть), иначе по времени запуска, иначе по id.
3. **Слияние по одной**: `git rebase <HEAD>` в дереве задачи, затем `git merge --ff-only <ветка>`
   в основном дереве проекта. Грязное дерево (незакоммиченные правки) — needs-owner, слияние
   этой задачи пропускается, но не останавливает остальных.
4. **Верификатор**: пустой дифф и команды `verify` в дереве задачи; красное — задача переоткрыта
   (`status=open`, `stage=s3-impl`) с журналом `рой: не принята: {reason, attempt, sha, command,
   code, timed_out, log, tail, next}` и в том же тике перезапущена тем же маршрутом в том же
   дереве; после `verify_retries` отклонений подряд — needs-owner, задача остаётся done и не
   влита. После `rebase`, до `merge --ff-only`.
5. **Конфликт ребейза**: без ключа `arbiter` в `swarm.json` — `rebase --abort`, needs-owner
   («разреши сам в дереве … `git rebase <sha>`»). С ключом `arbiter` — арбитр (ниже); не
   справился — тот же откат и needs-owner.
6. **Факт слияния** — после успешного `merge --ff-only` барьер пишет карточке журнал
   `рой: влито: {sha, branch, base, files, declared, outside[, arbiter: true]}` (`sha` — новый
   HEAD основной ветки, `files` — изменённые этим слиянием файлы, `declared` — `write_scope`
   задачи, `outside` — файлы вне него; `arbiter: true`, если конфликт решал арбитр).
7. **Разморозка**: открытые задачи с меткой `frozen-by:<id>`, чей владелец (`<id>`) уже `done` и
   сам влит (или закрыт без коммитов), размораживаются — барьер снимает несохранённую правку
   снимком (`git commit`, автор `listik-swarm`, часть обычной истории задачи, не временный
   объект), перебазирует дерево на новый HEAD и пишет журнал `рой: разморожена:
   {owner, sha, rebased, snapshot, conflicts, next}` (`rebased: false` и непустой `conflicts` —
   исполнитель доразбирает конфликт сам, руками, в своём дереве, и продолжает задачу как обычно;
   `rebased: true` — дерево уже на новом HEAD). Метка `frozen-by:` снимается в обоих случаях.
8. **Интеграция** — после слияний барьер прогоняет команды `integration` из `swarm.json` по
   очереди в основном дереве проекта; лог каждой команды — `logs/integration-<project>-
   <штамп>.log`. Все нулевые коды — деревья влитых задач убираются (`git worktree remove`,
   `git branch -d`, `worktree`/`branch` карточки очищаются). Ключ `integration` не задан
   (`null`, дефолт) — барьер не гадает, ставит карточку-стоп и ждёт, пока в `swarm.json` не
   появится явный список (пустой `[]` — «тестов нет», тоже явный выбор). Любая команда с
   ненулевым кодом (или таймаутом) — тоже стоп-карточка, деревья влитых задач при этом
   остаются нетронутыми до зелёного прогона.
9. **Стоп-карточка** — заводится с меткой `swarm:halt`, типом `question`, связью
   `discovered-from` на первую влитую в этом тике задачу, и текстом needs-owner:
   - «интеграционные тесты не настроены» — что дописать в `swarm.json` (ключ `integration`).
   - «интеграционные тесты красные» — команда, код/таймаут, путь к логу и его хвост, HEAD
     основной ветки; что делать — почини ветку, затем `listik done <стоп-карточка> -r "…"`, рой
     снова прогонит тесты и продолжит с того же места.
   Пока открыта хотя бы одна карточка `swarm:halt`, барьер и запуск новых задач стоят; закрыть
   её может кто угодно, кроме самого роя.
10. **Гейт запусков** — пока есть «не влитые» задачи (needs-owner из шага 1/3/5) или открыта
   карточка-стоп, рой новых задач не запускает (`gate` в сводке тика, `пропущено … гейт`), уже
   бегущие не трогает.
11. **Уточнение областей и графа** — когда в тике влита хотя бы одна задача, рой зовёт
   `listik rescope --project X --apply` (ТЗ → `read_scope`/`write_scope`, копилка
   `рой: вне write_scope:`/`рой: влито:` → уточнение `blocks` от `agent:listik-swarm`). Если
   проход что-то записал — волны и список перечитываются в том же тике, партия собирается по
   уточнённому графу. Ошибка модели (не настроен `[swarm]` в `config.toml`, таймаут) — строка
   `rescope ошибка:` в логе, волна едет по прежнему графу; цикл от модели — области записаны,
   рёбра нет, строка `rescope: цикл …`. В `--dry-run` не зовётся.

**Предел откатов.** Откат — заморозка наблюдателем `listik watch`: процесс снят, на карточке метка
`frozen-by:<владелец>`, в журнале запись `рой: заморожена:`. Счётчик производный, отдельных колонок
нет: это число таких записей от `agent:listik-swarm`. Окно считается с последней парковки роем
(вопрос `рой: предел откатов…`); если парковки не было — за всю жизнь задачи. Общее число заморозок
за жизнь задачи тоже считается и показывается в тексте парковки. Ключ `max_freezes` в `swarm.json`
(дефолт 2, переопределяется в `projects.<slug>`) — сколько заморозок задача переживает штатно.
Паркует заморозка номер `max_freezes + 1`. `max_freezes: 0` — паркует первая же заморозка.

Парковка ставит `needs-owner` с составом: кто вытеснял и по каким файлам, какие файлы разошлись с
объявленным `write_scope` (журнал `рой: вне write_scope:`), сколько минут отработали снятые
поколения. Задача остаётся замороженной; барьер размораживает её штатно после слияния владельца
(дерево перебазируется, метка снимается), но рой не перезапускает её, пока человек не снимет флаг
(`listik needs-owner <id> --clear "…"`).

Гейта запусков парковка не создаёт: остальные задачи волны запускаются и вливаются как обычно.
Оговорка: припаркованная задача с живым деревом по-прежнему владеет своими файлами в `listik watch`
и может заморозить более позднюю задачу с теми же файлами. Известная дыра: сбой `show` или
`needs-owner` в момент парковки не повторяется до следующей заморозки — один лишний перезапуск,
следующая заморозка паркует снова.

Минуты отката — от журнала запуска `автостарт: … поколение N` до записи `рой: заморожена:` снятого
поколения, приблизительно (у доделки заморозки следующим тиком интервал чуть завышен). В сводке
тика это сегменты `откаты · на откаты · по пределу`, в строке `итог:` при выходе — `откатов R (на
откаты M мин), по пределу P (ids)`. `--dry-run` ничего не пишет и печатает `[dry-run] по пределу …`,
если следующая заморозка превысила бы порог.

Сценарий подтверждён сквозным тестом `tests/test_swarm_rollback_e2e.py`.

**Тексты needs-owner «не влита»** — каждый начинается с `рой: не влита — ` и заканчивается
общей подсказкой `после исправления: listik needs-owner <id> --clear "…" — рой вольёт на
следующем тике`. Без этого `--clear` кандидат так и останется с открытым `needs_owner` и барьер
будет молча пропускать его на каждом следующем тике (шаг 1) — карточка не сдвинется сама, снять
её может только человек.

| Когда | Текст (между префиксом и подсказкой) | Что делать |
| --- | --- | --- |
| Каталога дерева нет, а ветка задачи впереди `HEAD` | «каталога дерева … нет, а ветка … ещё впереди HEAD» | верни дерево (`listik worktree <id>`) или убери ветку, затем `--clear` |
| `listik show <id>` не читается | «рой не смог прочитать карточку: …» | почини карточку/сервер, затем `--clear` |
| Незакоммиченные правки или новые файлы в дереве | «в дереве … незакоммиченные правки или новые файлы: …» + хвост `git status` | закоммить в ветку задачи или убери лишнее, затем `--clear` |
| `git rebase` упал с ошибкой (не конфликт) | «`rebase`: …» | разберись в дереве сам, затем `--clear` |
| Конфликт ребейза без `arbiter` в `swarm.json` | «rebase на … конфликтует: …; арбитр не настроен» | разреши конфликт сам в дереве задачи (`git rebase <sha>`, `git add`, `git rebase --continue`), затем `--clear` |
| Конфликт ребейза, арбитр не справился | «rebase на … конфликтует: …; арбитр не справился: …» + лог, если есть | то же самое руками, затем `--clear` |
| `git merge --ff-only` отказал | «`merge --ff-only`: …» | обычно значит, что `HEAD` успел уйти вперёд — разберись в основном дереве, затем `--clear` |
| Отклонена N раз (верификатор красный или пустой дифф сверх `verify_retries`) | «отклонена N раз: тесты красные — …» или «отклонена N раз: пустой дифф относительно …» | задача остаётся `done` и не влита; разбери лог / сделай работу в дереве, затем `--clear` |
| Заморозок в окне больше `max_freezes` | `рой: предел откатов —` задача заморожена …; вытесняли …; вне write_scope …; минуты снятых поколений | развести границы ТЗ или поднять `max_freezes`, затем `--clear` |

Кто разрешает конфликт: для открытой размороженной задачи (шаг 7) — сам исполнитель, руками, в
своём дереве, как обычную правку; для закрытой задачи при финальном слиянии (шаг 5) — либо
человек (без `arbiter` в `swarm.json`), либо модель через ключ `arbiter` — единственное место
во всём барьере, где решение принимает модель, а не жёсткое правило.

**`swarm.json`** — файл настроек барьера, путь `<каталог данных>/swarm.json` (тот же каталог,
что `listik.db`/`config.toml`; `--config <путь>` переопределяет), перечитывается каждый тик.
Полный пример (таймауты и `projects.<slug>` переопределяют верхний уровень для одного проекта):

```json
{
  "integration_timeout": 99,
  "verify": [["python3", "-m", "unittest", "discover", "-s", "tests", "-t", "."]],
  "verify_timeout": 1800,
  "verify_retries": 1,
  "question_timeout": 30,
  "rescope_timeout": 1800,
  "arbiter": ["claude", "--dangerously-skip-permissions", "-p", "{prompt}"],
  "projects": {
    "listik": {
      "max_freezes": 1,
      "rescope": false,
      "arbiter_timeout": 42,
      "integration": [
        ["python3", "-m", "unittest", "discover", "-s", "tests", "-t", "."],
        ["npm", "--prefix", "web", "run", "typecheck"]
      ]
    }
  }
}
```

- `integration` — список команд (`argv`, без шелла); `null` (по умолчанию, ключ не задан) —
  «не настроено», барьер стопорится; `[]` — «тестов нет», интеграция зелёная сразу.
- `verify` — список команд (`argv`, без шелла) в дереве задачи после `rebase` и до слияния;
  ключ не задан (`null`, дефолт) — верификатор команд не гоняет, берётся только интеграция
  после слияния; `[]` — не проверять (то же, что не задан, но явно). Команды `integration` в
  дерево не подставляются.
- `verify_timeout` — секунды на одну команду верификатора (дефолт 1800).
- `verify_retries` — сколько раз подряд задачу можно отклонить и вернуть воркеру (дефолт 1);
  `0` — первое же отклонение уходит человеку.
- `question_timeout` — минуты без ответа на мягкий вопрос, после которых рой сам снимает флаг
  (дефолт 30; `0` — автоответ выключен). Переопределяется в `projects.<slug>`.
- `max_freezes` — сколько заморозок задача переживает штатно (дефолт `2`); паркует заморозка
  номер `max_freezes + 1`. `0` — паркует первая же. Переопределяется в `projects.<slug>`.
- `arbiter` — команда арбитра (`argv`); не задана — конфликт закрытой задачи решает человек.
  Обязательный плейсхолдер — `{prompt}`: не сам текст промпта, а **путь** к файлу
  `arbiter-<id>-<штамп>-<n>.prompt.md`, который команда обязана прочитать сама. Живой
  `claude -p {prompt}` без файловой обёртки прочитает как промпт саму строку-путь, а не её
  содержимое — нужна обёртка, которая читает файл по этому пути и передаёт его текст модели.
  Другие плейсхолдеры: `{task_id}`, `{worktree}` (дерево задачи), `{files}` (конфликтующие
  файлы через запятую).
- `integration_timeout`/`arbiter_timeout` — секунды на команду/на одну остановку арбитра
  (дефолты 1800/1200).
- `rescope` — `true`/`false`, дефолт `true`; `false` выключает проход `listik rescope` после
  влитой волны (например, когда у проекта нет модели роя).
- `rescope_timeout` — секунды на вызов `listik rescope` (дефолт 3600; проход зовёт модель по
  каждому ТЗ, общий `--cli-timeout` роя на него не действует).

`logs/` (`--log-dir`) после барьера: `integration-<project>-<штамп>.log` (вывод команд
интеграции), `verify-<id>-<штамп>.log` (вывод верификатора в дереве задачи),
`arbiter-<id>-<штамп>-<n>.prompt.md` (промпт для остановки `n`),
`arbiter-<id>-<штамп>-<n>.log` (вывод арбитра).

Чего пока нет: счётчики влитых/невлитых по волнам.

### Мягкий вопрос

Вопрос исполнителя со строкой `по умолчанию: <вариант>` (с начала строки, в нижнем регистре) —
мягкий: исполнитель уже принял этот вариант и работает дальше, `needs_owner` только уведомляет
автора. Рой такой вопрос не считает остановкой: надзор за бегущей задачей продолжается, барьер
вливает закрытую задачу с мягким вопросом (флаг при слиянии не снимает). Без ответа человека за
`question_timeout` минут (по умолчанию 30) рой сам снимает флаг:

```
рой: ответа не было <N> мин — действует вариант по умолчанию: <вариант>
```

Это тот же `needs-owner --clear`, что и ответ человека: ни `set`, ни `stage`, ни `launch_route`
автоответ не трогает. После автоответа упавшая задача перезапускается в том же тике, как после
ответа человека (`revoke` с заметкой `рой: перезапуск — ответ по умолчанию`, затем `launch`).

Жёсткими всегда остаются вопросы самого роя (`рой: …`) — в том числе «нет маршрута» — даже если
в тексте есть строка `по умолчанию:`. Маршрут (`launch_route`) рой не подставляет никогда.
Вопрос без дефолтной строки — тоже жёсткий: надзор и барьер ждут человека, автоответа нет.

Правило для исполнителей — правило 7 протокола харнессов (`docs/harness-protocol.md`); для
конвейера — подраздел «Headless» в `plugins/feature-pipeline/references/pipeline-core.md`.

Наблюдатель `listik watch` рой зовёт каждый тик, если у проекта есть каталог и в плане нет
цикла: до `decide` и до барьера, в том числе пока воркеры ещё бегут. Успешная заморозка
(`action: freeze`, `ok: true`) даёт повторный `list`, чтобы `decide` в том же тике увидел
метку `frozen-by:` и не запускал задачу поверх грязного дерева. `--dry-run` передаёт
наблюдателю `--dry-run` и ничего не пишет. Размораживает барьер после слияния владельца.

## Справочник команд

| Группа | Команды |
|---|---|
| Сервер | `serve`, `stop`, `status`, `init`, `token`, `mcp`, `service` |
| Копии | `backup`, `restore` |
| Задачи | `new`, `list`, `show`, `set`, `context`, `board`, `stats`, `timeline`, `portions sync` |
| Работа | `ready`, `worktree`, `claim`, `heartbeat`, `stage`, `release`, `done`, `needs-owner`, `inbox`, `launch`, `revoke`, `lint` |
| Журнал | `comment -k comment\|journal\|review\|verdict\|question\|answer` |
| Связи | `dep add\|confirm\|rm\|suggest\|link\|suggested`, `blocked`, `tree`, `cycles` |
| Поиск | `search`, `memory`, `remember`, `embed` |
| Проекты | `projects`, `actors`, `init-projects`, `import-from-bd` |
| Рой | `listik swarm on\|off\|status`; `node bin/listik-swarm [--project X] [--once] [--exit-when-idle] [--dry-run]` |

`listik <команда> --help` — все флаги.
