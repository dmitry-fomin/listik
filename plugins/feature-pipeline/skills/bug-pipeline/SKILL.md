# Конвейер bug-pipeline

Пресет для бага — поведения, которое расходится с ожидаемым. ТЗ пишет Opus 5.5 medium, и первая порция
начинается с теста, который воспроизводит дефект; критики ТЗ нет; код пишет Sonnet 5.5 high, принимает
коллегия из двух независимых судей — Sonnet 5.5 high и Opus 5.5 high; зелёный — только единогласный,
порцию коммитит оркестратор. Пресет — выбор автора 07.10.2026, а не результат расчёта; обоснование — в
[ROLES.md, «Пресеты по типу задачи — выбор автора»](../../references/ROLES.md).

**Прочитай [pipeline-core.md](../../references/pipeline-core.md) целиком до первого действия.**
Там всё, что у пресетов общее: твоя роль, жёсткие правила, протокол вопросов, шаг 0, треки,
сборка пакета диффа, приёмка коллегией, пределы на порцию, журнал и общие грабли. Ниже —
только то, чем bug-pipeline отличается: кто делает каждый этап и как его позвать.

Скил запускается только по явному имени — маршрутом карточки Listik (`launch_route` или метка
`process:bug-pipeline`) или человеком (`/feature-pipeline:bug-pipeline`); по сходству задачи сам его не
подхватывай. Все роли — Claude-субагенты этой сессии: ТЗ, чек-лист и дифф наружу не уходят. Все команды —
из корня основного дерева.

## Роли

| Этап | Кто | Модель и усилие | Первая строка отчёта |
| --- | --- | --- | --- |
| 1. ТЗ и чек-листы | субагент `feature-pipeline:pipeline-spec-writer-medium` | **`model: opus` в вызове** (frontmatter — opus, effort medium) → Opus 5.5 medium | `готово` или `вопрос` |
| 3. Реализация | субагент `feature-pipeline:pipeline-implementer-high`, **без `model`** | Sonnet 5.5 high из frontmatter | `готово`, `не смог` или `вопрос` |
| 4. Приёмка коллегией | `sonnet` — `Agent` `feature-pipeline:pipeline-judge` **с `model: sonnet`**; `opus` — `Agent` `feature-pipeline:pipeline-judge` **без `model`**; оба одним сообщением | Sonnet 5.5 high; Opus 5.5 high из frontmatter | у каждого судьи `зелёный` или `красный`; коммит и вердикт — твои |

Этапа 2 нет: после `готово` этапа 1 порция идёт сразу на этап 3. Номера этапов оставлены как у остальных
пресетов, чтобы журнал и этапы Listik читались одинаково.

`model` в вызове передаётся там, где модель агента нужна не та, что во frontmatter: автору ТЗ —
`model: opus` (frontmatter и так `opus` + `medium`, параметр держит модель явно, как во всех пресетах с
писателем ТЗ), судье `sonnet` — `model: sonnet` (у `pipeline-judge` во frontmatter `opus`). Не передаётся
исполнителю `pipeline-implementer-high` (frontmatter — `sonnet` + `high`, это и есть Sonnet 5.5 high) и судье
`opus` (frontmatter `pipeline-judge` — `opus` + `high`). `model` перебивает frontmatter, усилие остаётся из
него; нужен другой уровень усилия — это другой агент.

## Нужные скилы

Стоп, если его нет — раздел «Внешние скилы» `pipeline-core.md`. Скрипты из кэша не зови.

- [`listik:listik`](../../../listik/skills/listik/SKILL.md) (`plugins/listik/skills/listik/SKILL.md`) — карточка, этапы, журнал, вопросы автору.

## Префикс

```
STEPS=docs/specs/steps
BASE=<id>        # без карточки — adhoc-<ГГГГ-ММ-ДД>-<слаг>
WT=.             # в треке — абсолютный путь дерева трека
```
`<X>` — буква порции, `<R>` — номер захода приёмки.

## Предполётная проверка

Внешних каналов у скила нет — все роли локальные субагенты, — поэтому предполётной проверки тоже нет.

**Стоп-фактор.** Любая роль недоступна (харнесс не установлен или не залогинен, запуск упал, ответила не та модель) — конвейер стоит: журнал `стоп: <роль> — <харнесс> недоступен: <причина>`, `listik needs-owner <id> "<вопрос>"` и тот же вопрос в чат, и больше ничего. Запасного исполнителя нет: роль не подменяется ни другим харнессом, ни другой моделью, ни локальным субагентом, в headless тоже (`pipeline-core.md`, «Стоп-фактор»). Повтор того же харнесса и той же модели в той же роли — не подмена.

## Этапы

### 1. ТЗ и чек-листы — `pipeline-spec-writer-medium`, `model: opus`, один раз на шаг

`Agent` `feature-pipeline:pipeline-spec-writer-medium`, **`model: opus`** — обязательно, в каждом запуске и в
режиме правки. В задаче:
путь к спеке **или** текст автора; `$STEPS`; имя бумаг `<id>`. В треке добавь **границу этого трека** —
каталог или слой, за который его ТЗ не выходит, словами автора. Последним абзацем задачи — дословно:

```
Это баг: первая порция начинается с теста, который воспроизводит дефект и падает на коде до правки, — он же негативный контроль чек-листа. Чинить в корне: все вызывающие общую функцию, а не только путь из описания.
```

Правила порций, границ и чек-листов агент знает сам — остальное не пересказывай.

`вопрос` — протокол вопросов. `готово` — в журнал `шаг <id>: старт, пресет bug-pipeline,
порций <K>`; допущения агента, если он их назвал, покажи автору одной репликой: молчание —
согласие. Дальше — сразу этап 3 первой порции: критики нет, решения по сводке и правки ТЗ по
замечаниям тоже нет.

### 3. Реализация — `pipeline-implementer-high`, без `model`

`Agent` `feature-pipeline:pipeline-implementer-high`, **без `model`** — Sonnet 5.5 high из его frontmatter. В
задаче — путь к порции `$STEPS/$BASE.<X>.md`, по одной за раз; право записи у агента в определении. В треке
первой строкой абсолютный путь дерева трека. Есть карточка — строка `Listik, карточка <P>` (id буквально) идёт в задачу первой строкой, в треке — второй, сразу после пути дерева трека;
карточки нет (`Listik: карточки нет`) — строки нет (`pipeline-core.md`, раздел `## Listik`). Сессия выдаёт
карточку себе и держит страховочные `claim`/`heartbeat`, а `claim`/`journal` субагент пишет сам по скилу
`listik:listik`. На повторе после красного — **тот же** субагент через `SendMessage` по его agent id, красные
пункты коллегии **дословно**; продолжить нельзя (agent id потерян после `/clear`, `SendMessage` отказал) —
**новый** субагент с текущим текстом задачи и теми же пунктами дословно, строкой в журнал (откат;
`pipeline-core.md`, «Шаг 0 — конфиг»).

`вопрос` — протокол вопросов, агент доделает после ответа через `SendMessage`. `не смог` — повтор **его
формулировкой**, не твоим пересказом, в пределах бюджета. `готово` с непустым разделом «открытые
вопросы и расхождения» — не остановка: покажи их автору одной репликой вместе с итогом этапа
и иди на этап 4.

### 4. Приёмка коллегией — Sonnet + Opus

**Стоп-фактор.** Харнесс этапа недоступен (запуск упал, ответила не та модель) — конвейер стоит: журнал `стоп: <роль> — <харнесс> недоступен: <причина>`, `needs-owner` и тот же вопрос в чат; подмены другим харнессом, моделью или локальным субагентом нет (`pipeline-core.md`, «Стоп-фактор»). Второй негодный ответ судьи, изменённое дерево и секрет в диффе — тоже стоп, по ядру.

Приёмка — коллегия из **двух** судей строго по `pipeline-core.md`, «Приёмка коллегией»: пакет диффа, проверка
дампа на секреты, отпечаток дерева до и после, выдача карточки себе, задание судьям, ожидание, годность
ответа, сведение и счётчики — там. Из видов судей ядра в состав входят только `sonnet` и `opus`; третьего
судьи нет, и на его место никто не встаёт. Судьям подсказок «это не дефект» не давай. Состав и вызовы — как
в таблице «Роли»:

- `sonnet` — `Agent` `feature-pipeline:pipeline-judge` с **`model: sonnet`** (Sonnet 5.5 high), фоном;
- `opus` — `Agent` `feature-pipeline:pipeline-judge` **без `model`** (Opus 5.5 high из frontmatter), фоном.

Оба — одним сообщением, одним заданием из ядра. Судьи прогоняют негативный контроль чек-листа — у бага это
в первую очередь тест, воспроизводящий дефект: он обязан падать на коде до правки — и показывают отказ
выводом команды; каждое число и хеш в ответе — копией из вывода команды этого захода. Судьи не коммитят и в
Listik не пишут.

Вердикт — по ядру, всё делаешь ты, оркестратор:

- **оба `зелёный`** — коммит порции по «Коммит порции приёмкой», вердикт `VERDICT: PASS` в карточку,
  журнал `порция <X>: коллегия — зелёный (sonnet, opus), коммит <hash7>` и `порция <X>: готово (коммит <hash7>)`.
  Дальше следующая порция — с этапа 3;
- **хоть один `красный`** — коммита нет, сводный красный список, вердикт `VERDICT: FAIL` в карточку,
  порция на этап 3 с пунктами дословно, в пределах бюджета; повтор — продолжение того же исполнителя через
  `SendMessage`, новый субагент — только откат (см. этап 3).

Проверь после зелёного, что коммит действительно есть: `git -C "$WT" log --oneline -1` — в нём твой
`<hash7>` и сообщение порции.

## Listik

По `pipeline-core.md`, раздел `## Listik`, с одним отличием: этапа `s2-review` у пресета нет, и
`review_path` не ставится — критики не было.

**Не эпик.** После `готово` этапа 1 — документы первой порции и переход **сразу на реализацию**, вместо
перехода на `s2-review` из подраздела «Не эпик»:

```
listik set <id> spec_path=<абс. путь <id>.md> checklist_path=<чек-лист первой порции> decision_path=<абс. путь журнала> --actor agent:claude --harness claude
listik stage <id> --to s3-impl --holder claude --actor agent:claude --harness claude
listik claim <id> --holder claude --actor agent:claude --harness claude
```

У каждой следующей порции — её чек-лист (`listik set <id> checklist_path=<её чек-лист> …`) и та же выдача
`--to s3-impl --holder claude` с `claim`; `--to s2-review` не встречается. Этап 4 — выдача себе на
`s4-judge` по «Приёмка коллегией», закрытие после зелёного последней порции — `listik done <id> -r …` по
подразделу «Не эпик».

**Эпик.** Карточка типа `epic` ведётся по «Эпик в пресете с писателем ТЗ»: дочерние карточки порций заводит
оркестратор, этапы порции идут на её карточке `<P>`. Этап `s2-review` дочерней карточки пропускается так же:
после `claim <P>` на `s1-spec` — сразу

```
listik stage <P> --to s3-impl --holder claude --actor agent:claude --harness claude
listik claim <P> --holder claude --actor agent:claude --harness claude
```

без `set … review_path=…` и без `comment … -k review`.

## Грабли пресета

| Симптом | Причина | Что делать |
| --- | --- | --- |
| ТЗ написано не той моделью | забыт `model: opus` у автора ТЗ | `model: opus` в каждом запуске автора ТЗ и в режиме правки |
| В первой порции нет теста, падающего до правки | из задачи автору ТЗ выпал абзац «Это баг: …» | абзац — дословно последним в каждой задаче этапа 1; без него — правка ТЗ, а не этап 3 |
| Код написал Opus или судья `opus` оказался другой моделью | передан `model` исполнителю или судье `opus` | у них `model` не передаётся: модель и усилие — из frontmatter |
| Карточка встала на `s2-review` и ждёт критики | выполнен переход из подраздела «Не эпик» ядра как есть | у пресета этапа 2 нет: `listik stage <id> --to s3-impl --holder claude …` |
| Судья коллегии закоммитил или изменил дерево — отпечаток после не совпал с отпечатком до | судья нарушил запрет задания | стоп по ядру: журнал, `needs-owner`, ничего не коммитишь и вердикт не пишешь |
| Зелёный объявлен при одном красном судье | сведение «большинством» вместо единогласия | зелёный только единогласный: один `красный` — красный вердикт порции |
