# Конвейер chore-pipeline

Пресет для мелкой правки — понятной работы в один заход, которой всё же нужна независимая приёмка перед
коммитом. Этапов два: код пишет Opus 5.5 medium, принимает и коммитит один судья Sonnet 5.5 high. Автора ТЗ
и критики нет — исполнителю и судье идёт текст задачи дословно, adhoc-файлом. Пресет — выбор автора
07.10.2026, а не результат расчёта; обоснование — в
[ROLES.md, «Пресеты по типу задачи — выбор автора»](../../references/ROLES.md).

**Прочитай [pipeline-core.md](../../references/pipeline-core.md) целиком до первого действия.** Там всё,
что у пресетов общее: твоя роль, жёсткие правила, протокол вопросов, шаг 0, adhoc-файл, рабочее дерево в
файле порции, сборка пакета диффа, пределы на порцию, журнал, раздел `## Listik` и общие грабли. Ниже —
только то, чем chore-pipeline отличается. Карточка — скил [`listik:listik`](../../../listik/skills/listik/SKILL.md)
(`plugins/listik/skills/listik/SKILL.md`).

Скил запускается только по явному имени — маршрутом карточки Listik (`launch_route` или метка
`process:chore-pipeline`) или человеком (`/feature-pipeline:chore-pipeline`); по сходству задачи сам его не
подхватывай. Все команды — из корня основного дерева.

## Роли

| Этап | Кто | Модель и усилие | Первая строка отчёта |
| --- | --- | --- | --- |
| 3. Реализация | субагент `feature-pipeline:pipeline-implementer` | **`model: opus` в вызове** (frontmatter — sonnet, effort medium) → Opus 5.5 medium | `готово`, `не смог` или `вопрос` |
| 4. Приёмка и коммит | субагент `feature-pipeline:pipeline-judge`, один | **`model: sonnet` в вызове** (frontmatter — opus, effort high) → Sonnet 5.5 high | вердикт; при зелёном — коммит судьи |

`model` обязателен в каждом запуске и повторе обоих: без `model: opus` код напишет Sonnet medium, без
`model: sonnet` примет Opus — и пресет перестанет быть тем, за что выбран. Усилие в вызове не правится:
оно из frontmatter агента.

Внешних каналов у скила нет — обе роли локальные субагенты, — поэтому предполётной проверки тоже нет.

**Стоп-фактор.** Любая роль недоступна (харнесс не установлен или не залогинен, запуск упал, ответила не та модель) — конвейер стоит: журнал `стоп: <роль> — <харнесс> недоступен: <причина>`, `listik needs-owner <id> "<вопрос>"` и тот же вопрос в чат, и больше ничего. Запасного исполнителя нет: роль не подменяется ни другим харнессом, ни другой моделью, ни локальным субагентом, в headless тоже (`pipeline-core.md`, «Стоп-фактор»). Повтор того же харнесса и той же модели в той же роли — не подмена.

## Префикс

```
STEPS=docs/specs/steps
BASE=<id>        # без карточки — adhoc-<ГГГГ-ММ-ДД>-<слаг>
WT=.             # абсолютный путь из строки журнала «дерево»
```
`<X>` — всегда `a`, `<R>` — номер захода приёмки.

## Шаг 0 — карточка, журнал, дерево, adhoc-файл

По `pipeline-core.md`, «Шаг 0 — конфиг, класс задачи, журнал, дерево», с уточнениями:

- **класс задачи.** Таблица «Класс задачи» ядра не применяется: пресет назван, значит ветка adhoc — этапы
  3 → 4 по adhoc-файлу. `$ARGUMENTS` пусто — спроси, что берём.
- **карточка.** `show` и `claim` — по «Шаг 0 — карточка» ядра. Карточка типа `epic` — стоп по «Эпик без
  писателя ТЗ — стоп» ядра: `needs-owner` с текстом оттуда, тот же вопрос в чат, этапы не начинаются.
- **журнал** — `<steps>/<id>.journal.md` (без карточки — `<steps>/adhoc-<ГГГГ-ММ-ДД>-<слаг>.journal.md`),
  первой строкой — что берётся в работу и пресет `chore-pipeline`; дальше строка `дерево <абсолютный путь>`
  по ядру.
- **adhoc-файл.** Текст задачи **дословно** кладётся в `<steps>/<id>.a.md` по «Adhoc-файл для широкой
  правки» ядра (без карточки — `<steps>/adhoc-<ГГГГ-ММ-ДД>-<слаг>.a.md`): разделы «Требования» — текст
  автора как есть, «Границы правки» — что автор назвал, не назвал — «только названные файлы и слой,
  остальное не трогать». Своих требований не добавляешь. **Первой строкой** файла ты ставишь
  `Рабочее дерево: <путь из строки журнала «дерево»>` — иначе предстартовая проверка ядра («Рабочее дерево в
  файле порции») не пустит этап 3. Перед созданием — `ls <steps>/<id>.*` по правилу 7 «Имена бумаг и
  деревьев» ядра.
- **готовый файл автора.** Автор дал путь к файлу с задачей — берётся он, второй файл не сочиняется, если
  его первая строка — верная строка `Рабочее дерево:` (та же проверка ядра проходит). Иначе его текст
  дословно копируется в `<steps>/<id>.a.md` под этой строкой, и дальше работа идёт по копии.

Порция одна — `a`; adhoc-файл служит и порцией, и чек-листом приёмки. При карточке — документы по ветке
«Пресет без писателя ТЗ» подраздела «Не эпик» ядра; `review_path` не ставится, критики не было:

```
listik set <id> spec_path=<абс. путь <id>.a.md> checklist_path=<абс. путь <id>.a.md> decision_path=<абс. путь журнала> --actor agent:claude --harness claude
```

## Этапы

### 3. Реализация — `pipeline-implementer`, `model: opus`

Перед **каждым** запуском — первым и любым повторным — предстартовая проверка из «Рабочее дерево в файле
порции» ядра на `<steps>/<id>.a.md`. Напечаталось сообщение о стопе — этап 3 не запускается: строка в журнал
и вопрос автору (автора ТЗ, который поправил бы файл, здесь нет).

Карточка: сессия выдаёт её себе и берёт —
`listik stage <id> --to s3-impl --holder claude --actor agent:claude --harness claude` и
`listik claim <id> --holder claude --actor agent:claude --harness claude`, heartbeat — по «Всегда» ядра,
пока субагент работает (`pipeline-core.md`, «Локальный субагент на этапах 3–4»).

`Agent` `feature-pipeline:pipeline-implementer`, **`model: opus`**. В задаче — первой строкой путь дерева из
строки `Рабочее дерево:`, второй — `Listik, карточка <id>` (id буквально; без карточки строки нет), дальше
путь к `<steps>/<id>.a.md` и больше ничего. Формат отчёта и запрет на выход за границы агент знает сам —
не пересказывай.

- **`готово`** — на этап 4; непустой раздел «открытые вопросы и расхождения» — покажи автору одной
  репликой и иди дальше.
- **`вопрос`** — протокол вопросов ядра: ответ автора дословно тому же субагенту через `SendMessage` по
  его agent id.
- **`не смог`** — повтор **его формулировкой** в пределах бюджета (`M ≤ 2`), тем же субагентом через
  `SendMessage`; `M = 3` — остановка и доклад автору.
- **повтор после красного** — тот же субагент через `SendMessage`, красные пункты судьи **дословно**.

Продолжить нельзя (`SendMessage` отказал, agent id потерян после `/clear`) — **откат**: новый субагент с
текущим текстом задачи и теми же ответами или пунктами дословно, строкой в журнал (`pipeline-core.md`,
«Шаг 0 — конфиг»).

### 4. Приёмка и коммит — один `pipeline-judge`, `model: sonnet`

Обычный режим приёмки, не коллегия: судья один, он сам выносит вердикт, сам коммитит порцию при зелёном и
сам пишет вердикт в карточку.

1. Пакет диффа — по «Пакет диффа для приёмки» ядра, путь дампа — в журнал.
2. Карточка: `listik stage <id> --to s4-judge --holder claude --actor agent:claude --harness claude` и
   `listik claim <id> --holder claude --actor agent:claude --harness claude`; heartbeat, пока судья работает
   (`pipeline-core.md`, «Локальный субагент на этапах 3–4»).
3. `Agent` `feature-pipeline:pipeline-judge`, **`model: sonnet`**. В задаче — первой строкой путь дерева,
   второй — `Listik, карточка <id>` (без карточки строки нет), дальше пути: adhoc-файл `<steps>/<id>.a.md` —
   он же порция и чек-лист приёмки, — и дамп диффа этого захода; на повторном заходе ещё дамп прошлого.
   Своего задания с правилами коммита не пишешь — они в агенте. Подсказок «это не дефект» не давай.

Чек-листа от автора ТЗ здесь нет, поэтому негативный контроль в adhoc-ветке судья строит сам
(`pipeline-core.md`, «Негативный контроль»): правка добавляет или чинит проверку — он придумывает сценарий,
на котором она обязана отказать, и показывает отказ выводом команды.
Числа и хеши в его отчёте — копией из вывода команды этого захода.

После возврата судьи — вердикт этого захода в карточке по «Вердикт локального судьи пишет он сам; сессия —
только страховка» ядра: есть — не дублируешь, нет — пишешь из первой строки его отчёта.

- **зелёный** — проверь коммит: `git -C "$WT" log --oneline -1`; журнал `порция a: готово (коммит <hash7>)`;
  закрытие — `listik done <id> -r "коммит <hash7>" --actor agent:claude --harness claude` по «Не эпик» ядра.
- **красный** — порция на этап 3 с пунктами дословно (выдача `--to s3-impl --holder claude` и `claim`
  заново), продолжением того же субагента. Пределы — по «Пределы на порцию» ядра, но полного круга нет:
  автора ТЗ у ветки нет, поэтому третье красное — **остановка и доклад автору**.

## Грабли пресета

| Симптом | Причина | Что делать |
| --- | --- | --- |
| Код написал Sonnet | забыт `model: opus` у исполнителя | `model: opus` в каждом запуске и повторе |
| Принял Opus | забыт `model: sonnet` у судьи | `model: sonnet` в каждом запуске судьи |
| Этап 3 не пускает предстартовая проверка | в adhoc-файле нет первой строки `Рабочее дерево:` или путь не тот | строку ставит оркестратор из строки журнала «дерево»; готовый файл автора без неё — копия под этой строкой |
| Задача разрослась: исполнитель просит решения, которого в тексте нет | класс определён по описанию, а не по работе | стоп, пресет с писателем ТЗ, сделанное — материалом этапу 1, строка в журнал |
| Карточка — эпик | пресет без писателя ТЗ | стоп по «Эпик без писателя ТЗ — стоп» ядра |
| Третье красное, а оркестратор ищет автора ТЗ для полного круга | правило полного круга применено к adhoc-ветке | полного круга нет: остановка и доклад автору |
