# Конвейер dsh-grok-pipeline

**Прочитай [pipeline-core.md](../../references/pipeline-core.md) целиком до первого действия.** Там всё, что
у пресетов общее: твоя роль, жёсткие правила, протокол вопросов, шаг 0, adhoc-файл, сборка пакета диффа,
пределы на порцию, журнал, раздел `## Listik` и общие грабли. Ниже — только то, чем этот пресет отличается:
кто делает каждый этап и как его позвать.

Пресет для **короткой задачи без ТЗ и критики**: этапов у него два, писателя ТЗ нет вовсе. Код пишет
DeepSeek Harness (dsh) на своей модели, принимает и коммитит Grok 4.6 с усилием high; основной контекст
только маршрутизирует, носит вопросы автору и ведёт журнал. Скил вызывается только вручную —
`/feature-pipeline:dsh-grok-pipeline`, и запуск скила — согласие автора на отправку **требований и кода
порции** наружу: исполнителю уходит рабочий каталог целиком (dsh ходит по коду сам), судье — дифф. Секреты
в adhoc-файл не пропускает шаг 0, в дифф — границы правки порции; все команды — из корня основного дерева.

## Роли

| Этап | Кто | Модель и усилие | Первая строка отчёта |
| --- | --- | --- | --- |
| 3. Реализация | `dsh-run.sh` плагина dsh, фоновой задачей | модель из настроек dsh, флаги модели не передаются | `готово`, `не смог` или `вопрос` |
| 4. Приёмка и коммит | `grok-companion.mjs` плагина grok, фоновой задачей | `--model grok-4.6 --effort high` | `зелёный` с хешем или `красный` |

**Чем пресет платит за скорость.** У **всей** линейки DeepSeek `hallucinationRate` ≥ 0.878, у
`deepseek-v4-1-flash` — **0.96**: склонность выдумать вместо «не знаю» предельная. Отсюда два следствия,
и оба не смягчаются: **судья не опционален** — без приёмки пресет не запускается вовсе, а недоступный
канал судьи это **стоп**, а не «пойдём без приёмки», потому что «готово» без независимой проверки не значит
ничего; и **`не смог` — редкое исключение, а `готово` — заявление, не факт**: модель почти никогда
не скажет «не смог», её заявление проверяет судья.

## Когда не подходит

Пресет берёт короткую задачу целиком и в один прогон. Не подходит, и это стоп с вопросом автору:

- **эпик** — определяется фактом, а не догадкой: на шаге 0 `show <id> --json` и `issue_type == "epic"`;
- **задача на несколько порций** — её пришлось бы резать, а резать здесь нечем: писателя ТЗ у пресета нет;
- **просьба «спроектируй»** — проектирование живёт на этапе 1, которого у пресета нет;
- **несколько независимых частей** — им нужны треки и своё ТЗ на каждый, а не один adhoc-файл.

В этих случаях — стоп и вопрос автору с предложением `low-pipeline` или `high-pipeline`. Эпик идёт через
`needs-owner` по разделу `## Listik` `pipeline-core.md`, и этапы после него не начинаются. Решение автора:
«выбрать эпик и выбрать пайплайн без ТЗ-писателя — НЕЛЬЗЯ».

## Шаг 0 — adhoc-файл, карточка, дерево

Шаг 0 общий, из `pipeline-core.md`: конфиг, класс задачи, журнал, дерево. Отличие одно: класс задачи здесь
всегда **широкая механическая правка** — текст автора дословно ложится в
`<steps>/adhoc-<ГГГГ-ММ-ДД>-<слаг>.a.md` с разделами «Требования» и «Границы правки», порция у ветки одна
(`<X>` — `a`), своих требований ты не добавляешь. Правила adhoc-файла — в `pipeline-core.md` («Adhoc-файл
для широкой правки»), здесь они не пересказываются.

Карточка Listik ведётся по разделу `## Listik` того же файла, ветка «Пресет без писателя ТЗ (adhoc-ветка,
`dsh-grok-pipeline`)»: карточка одна, `spec_path` и `checklist_path` — сам adhoc-файл, `review_path`
не ставится, критики не было. Дочерних карточек нет: задача на порции не делится. Перед этим — проверка
эпика из «Когда не подходит»:

```
$L show <id> --json --actor agent:claude --harness claude
```

## Префикс команд

Соберите один раз на шаг и держите в журнале — пути в кэше плагинов переезжают с каждой версией:

```
DSH=$(ls -d ~/.claude/plugins/cache/dsh-plugin-claude-code/dsh/*/scripts/dsh-run.sh | sort -V | tail -1)
GROK=$(ls -d ~/.claude/plugins/cache/grok-build/grok/*/scripts/grok-companion.mjs | sort -V | tail -1)
STEPS=<paths.steps из конфига>
BASE=adhoc-<ГГГГ-ММ-ДД>-<слаг>
WT=.             # в треке — абсолютный путь дерева трека
```

`<X>` — буква порции, `<R>` — заход приёмки, `DJOB` и `JOB` — id фоновых задач dsh и судьи. Вызов dsh —
`dsh-run.sh run [--write] [--model pro|flash|vision|<id>] [--effort <level>] [--provider <маршрут>] [--cwd
<dir>] [--timeout <сек>] [--background] [--label <текст>] < prompt.txt`; права **read-only по умолчанию**,
`--write` на этапе 3 обязателен. **`--model` и `--effort` не передавай**: активная модель харнесса — локальный
id `deepseek-flash`, это DeepSeek-V4.1 с контекстом 1M и `reasoningEffort: max` в настройках. Обвязка флагами
не пользуется, `--effort` требует `--model`, а переключение модели хрупкое — user-слой `settings.yaml`
ложится поверх overlay.

## Предполётная проверка — до этапа 3

Оба канала проверяются здесь, а не когда понадобятся; правило остановки — в `pipeline-core.md`.

```
"$DSH" check          # код 0; в выводе строки `готовность`, `модель`, `учётные данные`
node "$GROK" status --all --cwd "$PWD" | head -3
```

`"$DSH" check` вернул не 0 — исполнителя нет: стоп и `/dsh:dsh-check`. В строке `модель` ждёшь
`deepseek-flash`; другое — строка в журнал и вопрос автору. Судья — самый хрупкий канал: `grok models`
и авторизация могут быть в порядке, а прогон всё равно упадёт на `API error (status 402 Payment Required):
Grok Build usage balance exhausted`. Баланс по статусу не виден, поэтому проверяй судью **настоящим
прогоном**, а не только статусом:

```
node "$GROK" task --cwd "$PWD" --no-web --effort high "Ответь ровно одним словом: ok"
```

Вернулось `ok` — канал живой. Вернулся 402 или другая ошибка — **стоп и вопрос автору** с текстом ошибки
дословно, и остановка здесь жёстче, чем в остальных пресетах: исполнителя с `hallucinationRate` 0.96 без
приёмки проверить нечем, без судьи нельзя даже на одну порцию. Замена судьи — решение автора, строкой
в журнал.

## Этапы

### 3. Реализация — dsh фоновой задачей

Три вызова через `$DSH`, все **из одного каталога** либо с одним `--cwd`: реестр задач привязан к каталогу
запуска, и `status` из другого места job не найдёт. **Запуск** — фоном, порция легко выходит за лимит одного
вызова Bash; `--write` обязателен. Карточку Listik выдаёшь до запуска, а `claim` за dsh не пишешь — он сам:
`$L stage <P> --to s3-impl --holder dsh --actor agent:claude --harness claude`:

```
cd "$WT" && "$DSH" run --background --write --cwd "$WT" --label "$BASE <X>" <<'TASK'
Реализуй порцию ТЗ из файла <путь $STEPS/$BASE.<X>.md подставь буквально>. Прочитай его целиком; раздел «Границы
правки» — жёсткое условие, не пожелание. Разберись в коде, который правишь, прежде чем править. Прогони то, чем проект
проверяется (тесты, линтер, типы). Не коммить и не делай git add/stash/checkout/reset. Не трогай .env, *.key, *.pem,
credentials.json. Не правь тесты под реализацию и не глуши гарды. Требование непонятно или противоречиво — не выбирай
за автора: сделай то, что от ответа не зависит, и верни ответ с первой строкой `вопрос` и списком вопросов, у каждого
варианты, один помечен словом «предпочитаю». Ответ — не длиннее 30 строк, первая строка `готово`, `не смог` или
`вопрос`; дальше: сделано по пунктам требований / не сделано с причиной / открытые вопросы и расхождения / изменённые
файлы списком / проверки одной строкой каждая. Хоть одно требование не выполнено — первая строка `не смог`. Листинги и
логи в ответ не клади.

Listik, карточка <P> (подставь её id буквально): отчитывайся по ней, а не только в дереве. Писать в трекер
не запрещено — это твоя карточка, и claim в ней и есть доказательство, что ты запустился.
L=~/Projects/Listik/bin/listik
Первым действием возьми её сам: $L claim <P> --holder dsh --actor agent:dsh --harness dsh
Дальше каждые 10–15 минут работы — heartbeat с тем, что идёт сейчас:
  $L heartbeat <P> --holder dsh --note "<что делаешь>" --actor agent:dsh --harness dsh
Перед ответом — итог в журнал:
  $L comment <P> "<первая строка отчёта и суть: файлы, проверки>" -k journal --actor agent:dsh --harness dsh
Не смог или вопрос — тот же journal и release <P>: не держи карточку, если по ней не работаешь.
TASK
```

Heredoc-маркер закавычен, `$` внутри задачи не раскрывается — путь к порции пишется буквально. В stdout — job
id, в журнал сразу: `порция <X>: dsh <job-id>`, он же дальше в `DJOB=`. **Задача уходит одним аргументом, и
промпт длиннее 256 КиБ скрипт отклоняет** — ограничения, которого нет у codex; раздутый текст значит, что
в задачу попало содержимое ТЗ вместо пути. **Любой повторный прогон** по той же порции получает тот же текст
плюс в конце: «Правки предыдущего захода уже лежат в рабочем дереве — не откатывай и не переписывай их, работай
поверх» и один из разделов: «Ответы автора» (после `вопрос`) или «Красные пункты приёмки» дословно (после
красного). dsh **не возобновляется**. **Ожидание** — одним вызовом Bash с `run_in_background`, уведомление
о завершении и есть сигнал; **забор** — `result` из того же каталога:

```
cd "$WT" && until ! "$DSH" status "$DJOB" | grep -q '^actual_status=running'; do sleep 20; done
cd "$WT" && "$DSH" result "$DJOB"
```

Ответ dsh дословно — отчёт этапа. Код 2 — job id неверный, сверь с журналом и `"$DSH" status`. Код 6 или статус
`failed|timeout|orphaned` — считай `не смог` с текстом из `"$DSH" logs "$DJOB" --tail 20`. Пустой `DJOB` —
`status` без аргумента перечислит все задачи каталога, цикл ожидания выйдет сразу, а `result` упадёт: заполняй
из журнала. `вопрос` — протокол вопросов, ответы уходят в текст нового прогона; `не смог` — повтор **его
формулировкой** в пределах бюджета; `готово` идёт на этап 4 без обсуждения.

### 4. Приёмка и коммит — Grok 4.6 high фоновой задачей

Судья единственный видит требования и код одновременно, поэтому вердикт и коммит — его; здесь он же
и единственная проверка работы исполнителя. Чек-листом приёмки служит **сам adhoc-файл**: разделы
«Требования» и «Границы правки» — это и порция, и её чек-лист. Подсказок «это не дефект» ему не давай:
находку разрешаешь ты по отчёту. Собери пакет диффа по `pipeline-core.md` («Пакет диффа для приёмки»),
выдай карточку судье (`$L stage <P> --holder grok --actor agent:claude --harness claude`; `claim`
и вердикт он пишет сам, за него — нельзя) и запусти судью. `--write` обязателен — без него он
не закоммитит; `--cwd` задаёт и рабочий каталог, и каталог реестра задач, поэтому **тот же `--cwd`**
идёт в `status` и `result`:

```
cd "$WT" && node "$GROK" task --background --write --no-web \
  --model grok-4.6 --effort high --cwd "$WT" --label "приёмка $BASE.<X> r<R>" <<'TASK'
Ты — приёмка одной порции ТЗ и последняя инстанция по ней. Кода ты не правишь никогда: твой результат — вердикт и,
если он зелёный, коммит.

Пути (подставлены буквально): порция и чек-лист — один и тот же adhoc-файл, и ещё пакет диффа; при повторном заходе —
ещё дамп предыдущего захода, тогда смотри разницу, а не всю порцию заново.

Порядок: прочитай порцию и чек-лист. Прогони каждый пункт чек-листа по факту — открой код, запусти команду, посмотри
вывод; «выглядит сделанным» не считается. Прочитай пакет диффа и ищи срезанные углы: правку тестов под реализацию,
ослабленные ассерты, скипы и xfail, отключённые правила линтера, заглушенные гарды, выход за границы правки порции,
правки не по теме порции. Прогони то, чем проверяется проект (тесты, линтер, типы) — команды ищи в самом проекте.

Чек-лист — разделы adhoc-файла «Требования» и «Границы правки»: по каждому требованию и каждой границе предъяви
конкретный наблюдаемый исход — команду и её вывод, состояние тестов, ответ API. Пересказ кода без попытки
не считается проверкой.

Вердикт первой строкой:
- `зелёный` — все пункты чек-листа закрыты, проверки зелёные, срезанных углов нет. Тогда сам закоммить порцию:
  `git add` явными путями того, что входит в порцию, и `git commit`. Не добавляй `-A` и `.`: в дереве может лежать
  чужое. Не коммить бумаги шага (каталог ТЗ и файлы `*.journal.md`). Не пушить. Не делать reset, stash, checkout
  файлов, clean, rebase, amend и --no-verify. Не трогать .env, *.key, *.pem, credentials.json.
- `красный` — коммита нет. Дальше нумерованный список: пункт чек-листа или найденный срезанный угол, каждый — что
  не так и что именно доделать. Находку про выход за границы правки порции ставь первым словом строки
  `ГРАНИЦЫ:` — дальше её иначе маршрутизирует оркестратор. Остальные формулировки уйдут исполнителю дословно,
  поэтому они про дефект, а не про впечатление.

Ответ — не длиннее 40 строк. Первая строка `зелёный` с хешем коммита или `красный`; дальше: пункты чек-листа с исходом
по каждому / найденные срезанные углы / проверки одной строкой каждая / что отложено или перенесено. Листинги и логи в
ответ не клади.

Listik, карточка <P> (подставь её id буквально): судья берёт её сам и сам пишет вердикт — за тебя его не напишут.
L=~/Projects/Listik/bin/listik
Первым действием: $L claim <P> --holder grok --actor agent:grok --harness grok
Вердикт — сразу после ответа, первой строкой аргумента ровно `VERDICT: PASS` или `VERDICT: FAIL`
(сервер читает только её), дальше хеш коммита или красные пункты дословно, по одному в строке:
  $L comment <P> $'VERDICT: PASS\n<hash7>' -k verdict --actor agent:grok --harness grok
  $L comment <P> $'VERDICT: FAIL\n<пункты дословно>' -k verdict --actor agent:grok --harness grok
Красный вердикт — ещё и release <P>: карточку снова возьмёт исполнитель.
TASK
```

Ожидание — отдельным вызовом Bash в фоне, забор — `result` с тем же `--cwd`; вердикт разбирается так:

```
n=0
cd "$WT" && until node "$GROK" status "$JOB" --cwd "$WT" | grep -qE '^ *Phase: (done|failed|cancelled) *$'; do
  n=$((n + 1))
  [ "$n" -ge 540 ] && { echo "судья не отдал финальную фазу за 540 итераций по 20 с — стоп, вопрос автору"; exit 1; }
  sleep 20
done
```

Ждать исчезновения `running` нельзя: до финальной фазы `status` печатает `queued`, `starting` и `finalizing`,
а строки `Phase:` может не быть вовсе (нет фазы или job не найден) — такой цикл выходит в самом начале.
Предел — 540 итераций по 20 с (3 часа); исчерпан — стоп, строка в журнал и вопрос автору, `result` вердиктом
не считается.

Забор — после выхода по финальной фазе:

```
cd "$WT" && node "$GROK" result "$JOB" --cwd "$WT"
```

- **зелёный** — судья уже закоммитил, в отчёте хеш. В журнал `порция <X>: готово (коммит <hash7>)`, отложенное
  и перенесённое — отдельными строками. Порция у пресета одна, следующей нет: на этом шаг закрыт.
- **красный** — коммита нет, порция на этап 3 с пунктами дословно, в пределах бюджета; на **третий красный**
  вердикт — остановка и доклад автору (этапа 1 нет).
- **`failed`, `402` или пустой ответ** — это не красное: вердикта не было. Строка в журнал и вопрос автору;
  порция остаётся незакрытой.

Проверь после зелёного, что коммит действительно есть: `git -C "$WT" log --oneline -1`. Судья работает с
автоодобрением своих инструментов, и его «закоммитил» стоит одной команды проверки.

## Грабли пресета

| Симптом | Причина | Что делать |
| --- | --- | --- |
| dsh вернул разбор порции вместо правки, дерево чистое | забыт `--write` — dsh работает только на чтение | перезапуск с `--write`; предыдущий ответ отчётом этапа не считается |
| Скрипт dsh отклонил задачу по размеру | промпт длиннее 256 КиБ — в задачу попало содержимое ТЗ | исполнителю идёт путь к порции, а не её текст |
