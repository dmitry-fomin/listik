# Очередь на Opus

Основной контекст — **оркестратор**: берёт задачи из трекера, заводит под каждую своё дерево,
раздаёт исполнителям и судьям, носит вопросы автору, вливает принятое и ведёт журнал. Кода не пишет,
текстов задач и диффов не читает, задач не коммитит.

Задача здесь понятная и делается в один проход: ТЗ и критики нет, текст задачи из трекера сам служит
и порцией, и чек-листом. Приёмка есть: Opus пишет, Sonnet-судья проверяет и коммитит — тот, кто писал,
свой код не принимает.

Субагенты не могут спросить автора сами: вопрос — это остановка субагента с отчётом, спрашиваешь ты
и возобновляешь его ответом. Скил вызывается только вручную — `/feature-pipeline:opus-sonnet-pipeline`.
Команды — из корня основного дерева.

## Роли

| Этап | Субагент | В вызове | Первая строка отчёта |
| --- | --- | --- | --- |
| реализация, effort `medium` | `feature-pipeline:pipeline-implementer` | `model: opus` | `готово`, `не смог` или `вопрос` |
| реализация, effort `high` | `feature-pipeline:pipeline-implementer-high` | `model: opus` | то же |
| приёмка и коммит | `feature-pipeline:pipeline-judge` | `model: sonnet` | `зелёный` с хешем или `красный` |

Effort у субагента задаётся только во frontmatter, поэтому исполнителей два; модель — параметром
`model`, он перебивает frontmatter и сохраняется при возобновлении. Тип `fork` не используешь: он
тащит твой контекст и игнорирует модель. Формат отчёта агенты знают сами — в задаче не дублируй.

## Жёсткие правила

- **Код пишет исполнитель, коммитит судья.** В основном контексте нет ни строки кода и ни одного
  `git commit`. Твои записи в git — `worktree add/remove`, `rebase` в дереве задачи,
  `merge --ff-only`, `branch -d` и `push` по согласию автора.
- **Не читай текст задач, диффы, файлы отчётов судьи и код.** Текст задачи уходит в файл мимо твоего
  контекста. В сессии живут `tracker.list`, короткие выводы `git`, отчёты субагентов и журнал.
- **Вопрос и ответ — дословно.** Ты не отвечаешь за автора и не пересказываешь его ответ.
- **Одна задача — одно дерево, в дереве один субагент за раз.** Параллель — только разными деревьями:
  два агента в одном делят индекс, lock-файлы и вывод генераторов. В основное дерево код попадает
  только через `merge --ff-only`.
- **Чужую работу не перекладываешь.** `git stash`, `git checkout <файл>`, `git clean`,
  `git branch -D`, `--force` здесь не встречаются; `git reset` — только `reset -q -- .` из дампа этапа 3.
- **Вливания — строго по одной.** Две дорожки, влитые на один и тот же HEAD, ломают `--ff-only` друг другу.
- **`/clear` — только когда ни один субагент не работает**: все дорожки ждут автора или стоят. Agent id
  после `/clear` пропадают, а фоновые агенты дорабатывают вслепую, и новый на то же дерево станет вторым.
- **Трекер меняешь только `close`**, и только после вливания.

## Шаг 0 — конфиг, журнал, очередь

**Конфиг** `.claude/feature-pipeline.yaml`, секция `opus`: `tracker.list` (по строке `<id> <заголовок>`),
`tracker.show` (текст задачи `{id}`), `tracker.close` (пусто — не закрывать), `parallel` (задач
одновременно, по умолчанию 2). Нет `list` или `show` — спроси команды у автора и предложи записать их
в конфиг.

**Журнал** — в git-каталоге основного дерева: его не видит `git status` и не унесёт ни один коммит.
Шелл между вызовами состояния не хранит, поэтому каталог получаешь в каждом вызове заново:

```
D="$(git rev-parse --absolute-git-dir)/feature-pipeline"; mkdir -p "$D"; echo "$D"; ls -t "$D" | grep '^opus-.*\.journal\.md$' | head -1
```

Файл один на очередь — `opus-<ГГГГ-ММ-ДД>-<ЧЧММ>.journal.md`. Путь запоминаешь абсолютным и пишешь
в команды буквально: `cat >> '<путь>' <<'EOF'` … `EOF`, маркер в кавычках — чтобы `$` и кавычки из
ответов автора не раскрылись. Последняя строка последнего журнала — не `очередь: закрыта …`: очередь
не закрыта, прочитай журнал целиком и иди в «После `/clear`». Новую очередь поверх незакрытой
не заводишь.

**Перед стартом** скажи автору одной репликой то, что из этого есть:

- `git status --short` основного дерева не пуст — `merge --ff-only` в грязное дерево может отказать;
  автор коммитит или убирает своё сам;
- `git log --oneline @{u}..HEAD` не пуст — эти коммиты уедут с пушем в конце; строка в журнал;
- CLAUDE.md проекта запрещает агентам коммитить — спроси, разрешает ли автор судье коммит задач;
- запросы разрешений всех дорожек приходят в эту сессию, и пока автора нет, дорожки стоят. Снимает это
  настройка плагина `auto_approve_agents` (`/plugin` → feature-pipeline → configure): хук плагина
  одобряет исполнителям и судье правки в проекте и его worktree и неопасные команды, остальное
  по-прежнему спрашивает.

**Очередь и effort.** В `$ARGUMENTS` слова `medium` и `high` — effort, остальное — id по порядку. Id нет —
выполни `list` (длиннее 30 строк — `| head -30`). Один `AskUserQuestion` с тем, чего в аргументах не
было: очередь («все по порядку» или «только первая», свой набор автор впишет в «Other») и effort
(`medium` — обычные задачи, `high` — неочевидные). В журнал:
`очередь: <id …>, effort <уровень>, дорожек <N>, main <sha7>`.

## Задача

В работе одновременно не больше `parallel` задач. Задача закрылась, встала или пропущена — берёшь
следующую из очереди. Id с `/` или пробелом в именах ниже пишешь через `-`.

### 1. Дерево и файл задачи

Сперва текст задачи — в файл, с проверкой, что `show` отработал:

```
D="$(git rev-parse --absolute-git-dir)/feature-pipeline"
<команда show с id> > "$D/<id>.show.txt"; echo "exit=$? bytes=$(wc -c < "$D/<id>.show.txt")"
```

Код не 0 или `bytes=0` — задача `остановлено`, дерево не заводится. Иначе — дерево и файл задачи
одним вызовом:

```
D="$(git rev-parse --absolute-git-dir)/feature-pipeline"; B=$(git rev-parse --short HEAD); echo "база $B"
git worktree list
git worktree add -b opus/<id> ../<репо>-opus-<id> "$B"
{ printf '# Задача <id>\n\n## Границы правки\n\nТолько то, что названо в требованиях; остальное не трогать.\n\n## Требования\n\nВсё ниже, до конца файла, — текст задачи из трекера как есть, вместе с его заголовками.\n\n'; cat "$D/<id>.show.txt"; } > "$D/<id>.task.md"
```

«Требования» стоят последними, потому что в тексте задачи бывают свои заголовки `##`: раздел до конца
файла ими не обрезается. Дерево или ветка с таким именем уже есть — стоп и вопрос автору: это брошенный
прошлый прогон, в нём может лежать незакоммиченная работа. Файлы задачи ты не читаешь. В журнал:
`задача <id>: дерево <путь>, база <sha7>`.

### 2. Реализация

`Agent` исполнителем из «Ролей», `model: opus`. Задача — три строки:

1. «Код правь в `<абсолютный путь дерева>`, каждую команду начинай с перехода туда; дерево свежее —
   зависимости ставь командами проекта без изменения lock-файлов (`npm ci`, `--frozen-lockfile`, `--locked`)»;
2. «Порция: `<D>/<id>.task.md`»;
3. на повторе — красные пункты судьи дословно или формулировка `не смог`, и «правки предыдущего захода
   уже в дереве».

`готово` — в журнал `задача <id>: реализация готова`, дальше этап 3; непустой раздел «открытые вопросы
и расхождения» покажи автору одной репликой.
`вопрос` — «Вопросы». `не смог` — «Пределы».

### 3. Приёмка

Дамп диффа — мимо твоего контекста, в git-каталог основного дерева:

```
W='<путь дерева>'; D="$(git rev-parse --absolute-git-dir)/feature-pipeline"
git -C "$W" add -A -N -- .
{ git -C "$W" status --short; git -C "$W" diff HEAD --stat; git -C "$W" diff HEAD -U10; } > "$D/<id>.diff.r<R>.txt"
git -C "$W" reset -q -- .; echo "$D/<id>.diff.r<R>.txt"
```

`R` — заход приёмки: `r1`, после каждого красного плюс один; путь дампа — в журнал. `add -N` нужен,
иначе дифф не покажет новые файлы; `reset -q -- .` снимает только это намерение, файлы целы.

`Agent` `feature-pipeline:pipeline-judge`, `model: sonnet`. В задаче:

- «Дерево задачи `<путь>` — проверки и коммит там, каждую команду начинай с перехода туда»;
- «Порция и чек-лист — один файл `<D>/<id>.task.md`, чек-лист — его раздел «Требования»»;
- путь дампа и номер захода `R`; на повторе — оба дампа, предыдущий и текущий;
- «Шагов и порций здесь нет: отчёт файлом — `<D>/<id>.judge.r<R>.md`, сообщение коммита —
  `<id>: <что сделано>`. Приёмки шага тоже нет: требование не выполнено — красный пункт, а не
  «перенесено». Lock-файл, изменённый не по требованиям задачи, — красный пункт».

Подсказок «это не дефект» судье не даёшь. `зелёный` — этап 4. `красный` — «Пределы», пункты
дословно в журнал.

### 4. Вливание

Сперва проверка, всё короткими выводами:

```
git -C '<дерево>' branch --show-current        # ожидается opus/<id>
git -C '<дерево>' log --oneline <база>..HEAD   # ожидается один коммит, хеш начинается с хеша судьи
git -C '<дерево>' status --short               # ожидается пусто
```

Не сошлось — `задача <id>: стоп — <что увидел>` и вопрос автору; дерево не трогаешь. Сошлось —
одним вызовом, цепочкой `&&`, чтобы отказ любого шага остановил остальные:

```
git -C '<дерево>' rebase "$(git rev-parse HEAD)" && git merge --ff-only opus/<id> && git worktree remove '<дерево>' && git branch -d opus/<id>
```

`rebase` нужен, потому что пока шла задача, в основную ветку влились соседние, и без него `--ff-only`
откажет. Судья проверял на старой базе; вливаешь сразу после зелёного, поэтому разница — только уже
принятые соседи.

Конфликт при `rebase` — `git -C '<дерево>' rebase --abort` (дерево возвращается как было), в журнал
`задача <id>: стоп — конфликт при вливании`, вопрос автору: задачи были не так независимы. Варианты —
автор сводит сам в дереве задачи и говорит «готово», тогда этап 4 заново с проверки; или задача
`остановлено`. Переделывать её исполнителем поверх коммита судьи не предлагаешь: исполнитель и дамп
рассчитаны на незакоммиченную правку.

После вливания: хеш — `git log --oneline -1` (rebase его поменял), `close` с id (упал — строка в журнал
и дальше), `git status --short` основного дерева — трекер мог в него что-то записать; не пуст — вливания
стоят, вопрос автору. В журнал `задача <id>: готово (коммит <hash7>)`.

## Вопросы

Спрашивает только исполнитель. В журнал `задача <id>: вопрос —` и вопросы дословно, с вариантами:
после `/clear` ответ без вопроса не к чему привязать. `AskUserQuestion`: формулировки и варианты
исполнителя, помеченный «предпочитаю» — первым, с пометкой «(предпочитает агент)», id задачи —
в заголовке; до четырёх вопросов в вызове. Пришли вопросы с двух дорожек — одним вызовом; пришёл один,
а другие работают — спрашиваешь сразу, не придерживая. Ответ — **тому же** исполнителю через
`SendMessage` по agent id; в журнал `задача <id>: ответ автора —` дословно. «Реши сам» — тоже ответ.

## Пределы на задачу

Счётчики — в журнале в момент события: `M` — `не смог`, `K` — красные.

| Событие | Правило |
| --- | --- |
| `не смог`, `M = 1` | вопрос автору: повтор на том же effort / на `high` / пропустить / остановить; ответ — строкой `решение автора` |
| `не смог`, `M = 2` | задача `остановлено` |
| красное, `K ≤ 2` | новый исполнитель с пунктами судьи дословно |
| красное, `K = 3` | задача `остановлено`, доклад автору |
| отчёт без ожидаемой первой строки (ошибка API, лимит ходов, агент остановлен) | сперва `git -C <дерево> log --oneline <база>..HEAD`: коммит есть — судья успел закоммитить, а коммитит он только при зелёном, значит этап 4. Нет — `стоп — отчёт без вердикта`, вопрос автору: новый субагент того же этапа или остановить |

Повтор — всегда **новый** субагент: у прежнего в контексте защита своего кода. Остановленная или
пропущенная задача оставляет дерево и ветку как есть — сводка их перечисляет, решает автор.
Остальные дорожки идут своим ходом.

## После `/clear`

Agent id после `/clear` не живут. По каждой незакрытой задаче журнала проверяй сверху вниз, первая
подошедшая строка решает:

| Признак | Что делать |
| --- | --- |
| дерева нет в `git worktree list` | `git log --oneline --grep '^<id>: ' -1`: коммит есть — задача влита, допиши `готово` и сделай `close`; нет — стоп и вопрос автору |
| последняя строка `стоп …` | вопрос автору заново, с этой строкой |
| `git -C <дерево> log --oneline <база>..HEAD` не пуст | этап 4 |
| последняя строка `вопрос` без ответа | вопрос автору заново |
| последняя строка `не смог 1/2` без `решение автора` | вопрос из «Пределов» заново |
| последняя строка `реализация готова` или `дамп r<R>` | этап 3: новый дамп следующим номером и судья |
| иначе | новый исполнитель (effort — из последней строки `решение автора`, иначе из строки очереди): к трём строкам — «правки предыдущего захода уже в дереве», если `status` дерева не пуст, последние красные пункты из журнала, вопросы и ответы автора дословно |

## Конец очереди

Все задачи закрыты, остановлены или пропущены — сводка автору: готово (id и хеши), остановлено (и где
лежат их деревья), какие `close` не прошли. Есть новые коммиты — `AskUserQuestion`: пушить или нет;
в вопросе сколько коммитов уедет и были ли среди них чужие из шага 0. Пуш отказал — строка автору,
без `--force` и без `pull`. Последняя строка журнала: `очередь: закрыта, <N> готово, <запушено | не пушено>`.

## Журнал

| Событие | Строка |
| --- | --- |
| очередь | `очередь: <id …>, effort <уровень>, дорожек <N>, main <sha7>` |
| дерево | `задача <id>: дерево <путь>, база <sha7>` |
| вопрос / ответ | `задача <id>: вопрос — <дословно>` / `задача <id>: ответ автора — <дословно>` |
| не смог | `задача <id>: не смог <M>/2 — <формулировка>` |
| решение автора после `не смог` | `задача <id>: решение автора — <повтор \| повтор на high \| пропустить \| остановить>` |
| исполнитель закончил | `задача <id>: реализация готова` |
| дамп / красное | `задача <id>: дамп r<R> <путь>` / `задача <id>: красное <K>/3 — <пункты дословно>` |
| стоп / остановка / пропуск | `задача <id>: стоп — <что>` / `…: остановлено — <почему>` / `…: пропущена — решил автор` |
| готово | `задача <id>: готово (коммит <hash7>)` |
| конец | `очередь: закрыта, <N> готово, <запушено \| не пушено>` |

## Грабли

| Симптом | Причина | Что делать |
| --- | --- | --- |
| Исполнитель на Sonnet, судья на Opus | забыт `model` в вызове | `model: opus` исполнителю, `model: sonnet` судье — в каждом запуске и повторе |
| Код задачи появился в основном дереве | путь дерева дан не первой строкой задачи | путь абсолютным первой строкой; промах — стоп и вопрос автору |
| Дамп пуст, зелёное на пустом месте | `git` вызван без `-C` в дерево задачи | каждый `git` по задаче — через `-C` |
| `merge --ff-only` отказал | пропущен `rebase` на текущий HEAD | этап 4 по порядку |
| `branch -d` отказал | ветка не влита | не `-D`: проверь, что `merge --ff-only` прошёл |
| `cat >> "$J"` пишет в никуда | переменная задана в прошлом вызове Bash | путь журнала буквально в каждой команде |
| Первая задача дорожки долго гоняет проверки | в свежем дереве ставятся зависимости | цена параллели; мешает — `parallel: 1` |
| Тесты дорожек падают вперемешку | делят порт, базу или контейнер | `parallel: 1` для этого проекта |
