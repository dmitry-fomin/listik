Человек вызывает скил режима — /listik-pipeline:high, /listik-pipeline:nano, … — оркестратор это сессия Claude Code, роли — локальные субагенты и внешние харнессы по раскладке режима.

с линзами
xhigh high medium low

Полный цикл: ТЗ → критика → код → линза → судья, каждый этап на своём харнессе по references/lineups.md. Судья — если линза нашла FIXES или писатель дал RISK: YES.

без линз
xlow nano

Без ТЗ, критики и линз: сразу код, дальше судья — он единственная проверка. Флаг RISK: не читается. Третий заход без PASS — стоп, вопрос человеку.

петли возврата · всегда в ту же сессию исполнителя
↺ линза FIXES → та же сессия
↺ судья FIXES → та же сессия → снова судья
нижняя строка — что уходит в карточку Listik new, если нет id
stage s1-spec stage s2-review
set · worktree stage s3-impl
stage s4-judge done

Находки линзы или «RISK: YES» → судья: приёмка — его роль. FIXES → судья снимает себя с карточки (release), оркестратор снова выдаёт s3-impl тому же исполнителю и передаёт замечания дословно; красное правит исполнитель, не судья; третий заход без PASS — стоп, вопрос человеку.

02

Финал и карточка Listik

два пути к коммиту

Кто коммитит

  • Коммит всегда у оркестратора: git -C .worktrees/<id> add -A, commit -m "listik-pipeline: <id> <заголовок карточки>" — и после PASS судьи, и когда судьи не было
  • Закрытие — всегда оркестратор: done (держателя снимает сам), удаление worktree и ветки; на стопе по needs-owner дерево не трогает
  • Worktree создаёт оркестратор после READY: listik worktree <id> — дерево .worktrees/<id> на ветке task/<id>, путь и ветка пишутся в карточку; коммит и вливание ветки в основную — тоже оркестратор, как у роя: rebase ветки на основную в worktree, затем merge --ff-only в основном дереве; --ff-only отказал — rebase заново; конфликт — rebase --abort и стоп с вопросом человеку, сам не разрешает. На стопе по needs-owner дерево не удаляется: там ещё будут править
  • Судья не запускается, если линза чиста и RISK: NO; линза дала FIXES хотя бы раз — судья зовётся
  • Пункт чек-листа блокирует, только если назван file:line или покрыт командой проверки
  • В xlow и nano линзы нет: судья — единственная проверка, поэтому он зовётся всегда
  • FIXES → возврат в ту же сессию исполнителя; других путей к коммиту нет

Карточка Listik (без id её заводит оркестратор)

  • claim в начале, heartbeat каждые 10–15 минут
  • Пишет тот, кто взял: оркестратор выдаёт карточку, дальше claim, журнал и вердикт — того, кому выдали
  • comment -k journal после каждого этапа
  • stage двигает карточку: s1-spec — ТЗ, s2-review — критика, s3-impl — код и линза, s4-judge — судья
  • done в конце

Последовательность вызовов

listik new "<заголовок>" -p <проект> -d "<описание>"   # нет id
listik stage <id> --to s1-spec --holder <писатель>     # ТЗ и критика → READY
listik stage <id> --to s2-review                       # двигает писатель перед критикой; s1→s2 липкий
listik set <id> spec_path=<абс> checklist_path=<абс>
listik worktree <id>
listik stage <id> --to s3-impl --holder <исполнитель>  # код и линза
listik stage <id> --to s4-judge --holder <судья>       # приёмка
listik done <id> -r "коммит <hash7>"                  # закрытие

# команды оркестратора: --actor agent:claude --harness claude
# claim, heartbeat, journal, вердикт — сама роль: --actor agent:<харнесс> --harness <харнесс до «-»>
