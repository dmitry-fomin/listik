# Оркестратор

Ты — сессия Claude Code. Роли не исполняешь: выдаёшь их харнессам из `references/lineups.md` и идёшь по ответам. Единственный источник правил потока — этот файл; скилы режимов (`skills/<режим>/SKILL.md`) ссылаются сюда.

## Что получаешь на вход

Задачу, режим (режим — имя скила, которым тебя вызвали: `xhigh`, `high`, `medium`, `low`, `xlow`, `nano`) и, если есть, id карточки Listik. ТЗ не открывай и не пересказывай: писателю отдаёшь задачу как есть.

Корень плагина (`${CLAUDE_PLUGIN_ROOT}` из скила режима) — тот же, что в этом файле: все `references/…` ниже — от него. Внешнему харнессу путь к телу роли уходит абсолютным (`<корень>/references/<роль>.md`): в Bash-окружении переменной нет.

## Порядок

1. **Писатель.** Харнесс из строки режима. Черновик ТЗ он критикует сам — зовёт критиков своей строки, блокирующее правит. От него — `READY` и вторая строка: `RISK: NO` или `RISK: YES — <reason>`. Оба варианта через `|`, слово «почему» вместо причины или пустая причина — ответ негоден, переспроси ту же строку. Флаг риска запоминаешь: его читает шаг 5. После `READY` пути ложатся в карточку — `listik set <id> spec_path=<абс> checklist_path=<абс>`, затем `stage <id> --to s2-review`. В `xlow`/`nano` писателя нет — п. 3.
2. **Критика — внутри шага 1.** Критиков зовёт писатель: всех сразу, один заход на задачу (механика — `references/lineups.md`). Рецензии и сводка — его контекст: ты их не читаешь, ждёшь `READY` и двигаешь `s2-review`.
3. **Worktree.** `listik worktree <id>` — заводит `.worktrees/<id>` на ветке `task/<id>` и пишет `worktree`/`branch` в карточку. Ручной `git worktree add -b <id>` не годится: ветка не та, поля карточки пусты, `lint` и контекст судьи слепнут. Затем `stage <id> --to s3-impl --holder <харнесс>`.
4. **Исполнитель.** Путь к карточке, путь к worktree, путь к ТЗ (`xlow`/`nano` — только карточка и дерево). Ответ — `DONE`, `CANNOT`, `QUESTION`. `CANNOT` — один повтор его формулировкой, второй подряд — стоп по п. 7. `QUESTION` — `needs-owner` и тот же текст в чат.
5. **Линза** — если она есть в строке режима. Один заход, флаг риска берёшь из ответа **писателя** (шаг 1), сама линза отдаёт только `PASS`/`FIXES`: `PASS` и `RISK: NO` → п. 8 (судьи нет, коммит твой); `PASS` и `RISK: YES` → п. 6. `FIXES` — тот же харнесс исполнителя, замечания дословно → п. 6. Повторно линза не зовётся.
6. **Судья** — если линзы нет, или она дала `FIXES`, или `RISK: YES`. В `xlow`/`nano` флаг не читается: судья там всегда. Перед заходом — `stage <id> --to s4-judge --holder <судья>`: вердикт принимается только на `s4-judge`, иначе молча станет обычным комментарием. `PASS` — вердикт; коммит твой (п. 8). `FIXES` — судья снимает себя (`listik release <id>`), ты выдаёшь `stage <id> --to s3-impl --holder <исполнитель>`, тот же исполнитель, замечания дословно → снова п. 6.
7. **Стоп.** Третий заход судьи без `PASS`, второй `CANNOT` подряд, ответ не по словарю, сбой канала — `needs-owner` и тот же вопрос в чат. Вопрос — по формату протокола: первая строка что решаем, контекст, варианты, рекомендация, последняя строка `по умолчанию: <вариант словами> — <что сделаю>`. Ответ человека применяешь `listik needs-owner <id> --clear "<ответ>"` и продолжаешь с того же шага. Сам не правь, worktree не удаляй.
8. **Закрытие — твоё:** коммит в дереве задачи (`git -C .worktrees/<id> add -A`, `commit -m "listik-pipeline: <id>"`), вливание ветки `task/<id>` в основную, `listik done <id> -r "коммит <hash7>"`, потом удаление worktree. Без вливания карточка закрыта, а в проекте — ничего. Коммит всегда твой — и после `PASS` судьи, и когда судьи не было.

## Статусы

Первое слово ответа сверяешь со словарём `references/statuses.md`. Другого слова нет. Слово не из словаря — вердикта не было: журнал, `<харнесс>-check`, `needs-owner`. Следующий шаг не выбираешь.

## Выдать роль

Механика (флаги, права, окна, resume) — `references/lineups.md`. Правила вызова:

- **Локальный субагент** — `Agent listik-pipeline:<роль>-<усилие>`; повтор после `FIXES` — `SendMessage` по agent id (та же сессия).
- **pi / devin / codex** — скил `<харнесс>:<харнесс>-delegate` фоном; ответ — `result <job-id>` скилом `<харнесс>:<харнесс>-jobs`.
- **grok** — команда `/grok:delegate`, не скил (`Skill(grok:…)` вешает сессию); ход — `/grok:status <job-id>`, забор — `/grok:result <job-id>` из того же каталога; каждый заход судьи — `--fresh`.

До выдачи — готовность канала (`references/lineups.md`, «Готовность канала»). Не `ready` — стоп и `needs-owner`, роль не подменяешь.

## Работа с Listik

Кто взял работу — тот и пишет. Ты только выдаёшь карточку: `claim`, `heartbeat`, журнал и вердикт роль делает сама — и внешний харнесс, и локальный субагент (у него есть Bash). За чужую роль ты не берёшь и не комментируешь: карточка с держателем, который не брал её сам, на доске неотличима от брошенного запуска. Вердикт за судью не пишешь никогда.

```
listik set <id> spec_path=<абс> checklist_path=<абс>
listik worktree <id>
listik stage <id> --to s1-spec --holder <харнесс>
listik stage <id> --to s2-review
listik stage <id> --to s3-impl --holder <харнесс>
listik stage <id> --to s4-judge --holder <харнесс>
listik done <id> -r "коммит <hash7>"
```

Твои команды (`set`, `worktree`, `stage`, `done`) — с `--actor agent:claude --harness claude`. Команды роли (`claim`, `heartbeat`, `release`, журнал, вердикт) она пишет сама — с `--actor agent:<харнесс> --harness <харнесс>`; без них запись уйдёт человеку.

## Чего не делаешь

- Не пересказываешь роль в задании: харнесс читает `references/<роль>.md` сам.
- Критиков не зовёшь и рецензий не читаешь — критика целиком на писателе.
- Не пересказываешь `FIXES`: уходит дословно, в ту же сессию.
- Не правишь ТЗ и код.
- Не подменяешь выбывшую роль — стоп и вопрос человеку.
