# Listik: работа с задачами

Listik — общая очередь задач и журнал работы для людей и агентов. Карточка — единственный
источник правды: всё, что должна узнать следующая сессия, пиши в Listik, а не в чат.

## Подготовка

1. Используй установленный `listik` из `PATH` (проверить путь: `command -v listik`), дальше в тексте это `L`. MCP-инструменты `listik_*` — работай через них, см. «Удалённый Listik (MCP)». Нет ни того, ни другого — спроси пользователя, где установлен Listik или какой адрес MCP.
2. Представляйся в КАЖДОЙ команде: `L <команда> --actor agent:claude --harness claude`. `export LISTIK_ACTOR` между вызовами Bash не сохраняется, а без `--actor` запись уйдёт от `$USER`, то есть от человека: история смешается с человеческой, а `dep add` сразу поставит жёсткий блокер вместо предложения. Держатель — `--holder claude`. Отдаёшь работу с Listik
   другому харнессу (dsh, grok, codex) — скажи ему представляться своим `agent:<имя>` и вести карточку самому: `claim` первым действием, `heartbeat` по ходу, `comment -k journal` с итогом, у судьи — свой `verdict`. Сам за него не пиши: иначе он унаследует твой `LISTIK_ACTOR`, если тот задан в окружении, а «выдана» не будет отличаться от «взята».
3. `L status --json` — жив ли сервер, принимает ли токен, совпадают ли установки CLI и сервера. Локальная работа (автоматическая или `--local`) допустима только когда сервер не запущен, а не когда он отказал. Если сервер не запущен, можно поднять `L serve --daemon`.

**Без обходных путей.** Сервер отказал (токен не принят, HTTP 401/403) или `status` сообщил
о несовпадении установок — останови работу с Listik и сообщи пользователю вывод
`L status --json`: бинарник CLI, каталоги данных/config CLI и сервера, состояние токена
и сервера. Не переходи на `--local`, не подбирай токены и другие бинарники, не читай запасную
локальную базу. Если сервер старый и не отдаёт свои пути, сообщи, что сверка недоступна.

Флаги передавай отдельными аргументами в каждом вызове. Если сохраняешь их в shell,
используй массив: `flags=(--actor agent:claude --harness claude)`, затем
`listik status --json "${flags[@]}"`; строка со всеми флагами в zsh не разделится на аргументы.

`--json` есть у всех команд — используй его, когда разбираешь вывод.

## Маршрут задачи: чем её делать

**Любую** задачу делай по тому процессу, который записан в ней самой, — не по своей схеме и не
россыпью самодельных субагентов. Это правило и для одной задачи, и когда ты оркестрируешь много.

1. Узнай маршрут: поле `launch_route` в `L show <id> --json`, а если оно пустое — метка
   `process:<ключ>` (метка `harness:<x>` рядом — кто оркестрирует).
2. Найди запись с этим `key` в `~/.config/listik/routes.json` (или `GET /api/routes`).
   - `kind: pipeline` — пресет из набора скилов feature-pipeline: вызови скил
     `feature-pipeline:<ключ>` (например `feature-pipeline:xlow-pipeline`) и веди задачу по
     нему. Кто исполняет какую роль (`spec`/`critic`/`impl`/`judge`), берётся из `roles` записи:
     роль с `"provider": "claude"` — это ты (твоя сессия или субагенты скила), остальные
     провайдеры (`grok`, `deepseek`→dsh, `openai`→Codex, `glm`) — те харнессы, которых вызывает скил.
   - `kind: direct` — задачу делает указанный `harness` целиком своей командой из записи; сам
     её не выполняй.
3. Просят вести **несколько карточек параллельно** — каждой карточке свой git worktree
   (`L set <id> worktree=<путь> branch=task/<id>`) и свой оркестратор, запущенный **обычным
   субагентом** (`claude`, `general-purpose`) с промптом «вот id карточки, вот ключ маршрута, вот
   дерево и ветка». Тип `fork` не бери: он наследует контекст вместо промпта карточки и не может
   запускать вложенных агентов, то есть ни один этап пресета не поднимет. Пуш, слияние в основную
   ветку и `done` оставляй себе; вопросы таких оркестраторов приходят в `needs-owner` карточки и
   дословно в их отчёте — автору их несёшь ты.
4. Маршрута нет ни в поле, ни в метке, или ключа нет в `routes.json` — не выбирай процесс сам:
   `L needs-owner <id> "какой маршрут из routes.json: …?"` (и тот же вопрос в чат) и бери
   следующую задачу.

Этапы Listik (`s1-spec`…`done`), claim/heartbeat/журнал/вердикт ведутся по протоколу ниже поверх
этапов пресета: ТЗ пресета — `s1-spec`, критика — `s2-review`, реализация — `s3-impl`, приёмка —
`s4-judge`.

## Протокол

Кто взял задачу — тот и пишет в неё: `claim` первым действием, `heartbeat` по ходу работы,
`comment -k journal` с итогом, у судьи — свой `claim` и свой `verdict`. Оркестратор только
выдаёт карточку (`stage <id> --holder <кому>`), следит за брошенными, сливает и закрывает;
он не пишет claim/heartbeat/журнал/вердикт за исполнителя. Исключение — исполнитель этапа субагент
твоей же сессии (роль с `"provider": "claude"` в маршруте, локальный агент скила): своего актора у него
нет, поэтому выдай карточку себе (`L stage <id> --to <этап> --holder claude`), сделай
`L claim <id> --holder claude` сам и держи живой `L heartbeat <id> --holder claude`, пока субагент
работает; иначе карточка останется в работе без держателя. Пока держатель не сделал свой
`claim`, карточка на доске «выдана, но не взята» (`not_taken`, `holder_taken=false`), а после
`board.assign_warn_minutes` (15 мин) попадает в «нужен ты» — брошенный прогон видно, не
дожидаясь `stale_hours`.

1. **Найти.** Определи slug текущего проекта по карточке или `L projects`.
   `L ready --project <slug текущего проекта> --harness claude`,
   `L search "суть" --project <slug текущего проекта>`, затем `L show <id>`.
   Для списка так же: `L list --project <slug текущего проекта>`. Всю очередь без
   `--project` смотри только по явной просьбе пользователя. Не бери задачу, которой
   нет в `ready`: у неё открытый блокер или держатель.

   **Спросили «что висит на проекте» — отвечай по полной выдаче, а не по умолчанию.**
   `L list` без `--limit` урезает список, и незакрытые карточки в хвосте не видно;
   `L ready` показывает только то, что можно брать прямо сейчас, — задача с держателем
   или блокером в него не попадёт. Бери `L list --project <slug> --limit 200 --json` и
   считай незакрытым всё, у чего `status` не `done` и не `cancelled` (`open`,
   `in_progress`, `blocked`). Сверься с числом, прежде чем называть его пользователю:
   «в проекте N задач» по урезанному списку — это неверный доклад, а не оценка.
2. **Взять сразу.** Первым действием — `L claim <id> --holder claude --note "что собираюсь делать"`.
   Отказ `claim` объясняет причину и варианты — выбирай из них, не обходи. Если карточку уже
   выдал оркестратор (`stage --holder claude`), повторный `claim` тем же держателем идемпотентен,
   но именно он записывает в историю, что задачу взял ты.
3. **Держать живой.** Работа дольше 10 минут — `L heartbeat <id> --holder claude --note "…"`
   каждые 10–15 минут. `heartbeat` перезаписывает держателя без проверки — никогда не шли его по
   задаче, которую держит кто-то другой.
4. **Писать журнал.** Решения и ход работы — `L comment <id> "…" -k journal`; замечания к ТЗ —
   `-k review`; вердикт проверки — `-k verdict`.
5. **Спрашивать человека через Listik.** `L needs-owner <id> "точный вопрос с вариантами"`.
   Не оставляй вопрос только в чате. Ответ приходит `needs-owner --clear "…"` и виден в `show`.
   Последняя строка вопроса — `по умолчанию: <вариант>`: с ним и продолжаешь, а в журнал —
   `решение: … основание: …`. Без дефолта — только необратимое (чужая работа, неразрешимый
   конфликт слияния, невозвратные деньги) и никогда — выбор маршрута `launch_route`.
6. **Переводить этап командой.** `L stage <id>`; не меняй этап правкой текста карточки.
7. **Закрыть.** Перед закрытием проверь `L show <id>`: нет открытых блокеров, у эпика закрыты
   дети, приёмка выполнена — сервер этого сам не проверяет и держателя не снимает.
   `L done <id> -r "краткий проверяемый результат"`.
8. **Отдать.** Не можешь продолжить — `L comment … -k journal` о состоянии и `L release <id>`.
9. **Чужое не переписывай.** Нашёл проблему в чужой карточке — `comment`, а не `set`.

## Этапы конвейера

| Этап | Что читать | Что менять | Переход |
|---|---|---|---|
| `s1-spec` | `show`, `L context <id> --stage s1-spec`, `spec_path` | ТЗ и чек-лист (файлы), порции — дочерние карточки: `L new "…порция b" --parent <id шага> --spec … --checklist … --review …` | `stage` → s2, **sticky**: держатель остаётся |
| `s2-review` | `L context <id> --stage s2-review` | ничего, кроме `comment -k review` | `stage` → s3, **handoff**: держатель снимается |
| `s3-impl` | `L context <id> --stage s3-impl --portion "<порция>"` и `show` (ответы, прошлый вердикт) | первым действием `claim --holder <себя>` и `heartbeat` каждые 10–15 мин; код в `worktree`/`branch` карточки, проверки, `-k journal` | `stage` → s4, **sticky**; не коммитить |
| `s4-judge` | `L context <id> --stage s4-judge`, чек-лист, дифф | судья сам берёт задачу (`claim --holder <себя>`) и сам пишет `comment -k verdict`; код не править | `VERDICT: PASS` — коммит и `done`; `VERDICT: FAIL` — сервер сам вернёт на s3 |

- **sticky, другой исполнитель:** передающий `L stage <id> --holder <следующий>` — это только
  выдача (карточка становится «выдана, но не взята»), принимающий первым действием
  `L claim <id> --holder <свой>`: держатель уже стоит, но именно этот claim записывает в
  историю, что задачу взял он.
- **handoff:** после перехода задачу берут заново через `ready` → `claim` (свой, не чужой). Если
  следующий этап делает субагент твоей же сессии, handoff идёт с `--holder claude` и твоим
  `L claim <id> --holder claude` — иначе карточка остаётся в работе без держателя.
- **Вердикт.** Первая строка — ровно `VERDICT: PASS` или `VERDICT: FAIL`; сервер смотрит только
  на неё, любой другой формат отклоняет с ошибкой. При `FAIL` ниже обязателен список правок,
  по строке на пункт: пункт чек-листа — что не так — файл:строка — что сделать. Это всё, что
  получит исполнитель: сервер вернёт задачу с `s4-judge` на `s3-impl`. Если карточку держишь
  ты-судья — `release`, чтобы исполнитель мог взять. На `s3` после возврата читай последний
  вердикт в `show` — это твой список правок.
- **Рабочее дерево.** `claim` на `s3-impl`/`s4-judge`/без этапа откажет, если то же дерево в
  проекте занято другой пишущей задачей. Варианты — дождаться, `release` брошенной, или
  `L set <id> worktree=/другой/путь`.

## Зависимости

- `L dep add <id> <блокер>` — «`<id>` ждёт `<блокер>`». От агента это **предложение**
  (`suggested-blocks`): оно не блокирует, пока человек не подтвердит `dep confirm`. Не используй
  `--confirm` сам — жёсткие блокеры ставит человек.
- Связь «прочитай сначала» без запрета — `L dep add <id> <другая> --dep-type relates-to` или
  `L dep link <id>` для задач, упомянутых в тексте.
- Блокер брошен — возьми сам блокер или поставь ему `needs-owner`; `claim --force` в обход
  блокера — только с явного согласия человека.
- Проверить: `L tree <id>`, `L blocked`, в `show` — «ждёт» и «её ждут».

## Удалённый Listik (MCP)

Протокол тот же, меняется только способ вызова: вместо `L <команда>` — инструмент `listik_*`.

| CLI | MCP |
|---|---|
| `ready`, `search`, `show`, `list` | `listik_ready`, `listik_search`, `listik_show`, `listik_list` |
| `claim`, `heartbeat`, `release` | `listik_claim`, `listik_heartbeat` (`holder` обязателен), `listik_release` |
| `stage` | `listik_stage` (`to`, `holder` — для sticky-передачи) |
| `comment -k journal\|review\|verdict` | `listik_comment` (`kind`, `author`) |
| `needs-owner` / `--clear` | `listik_needs_owner` (`text`; снять — `value: false` и ответ в `text`) |
| `done -r` | `listik_done` (`result`) |
| `new`, `set` | `listik_create`, `listik_update` (`fields`) |
| `context`, `dep add`, `tree`, `blocked` | `listik_context`, `listik_deps`, `listik_dep_tree`, `listik_blocked` |
| `inbox`, `memory`, `remember` | `listik_inbox`, `listik_memory`, `listik_remember` |

- **Кто ты.** Флагов нет — передавай `actor: "agent:claude"` и `harness: "claude"` там, где
  инструмент их принимает; `holder: "claude"`. `listik_deps` без `actor` всё равно считается
  агентским: жёсткая связь ляжет предложением. `confirm` не ставь — это решение человека.
- **Документы.** Файлов твоего проекта на сервере нет: `spec_path` на твоей машине сервер не
  прочитает. ТЗ, чек-лист, ревью и решения загружай содержимым — `listik_put_document` (`id`,
  `kind`: `spec|checklist|review|decision`, `content`); читай `listik_get_document` или
  `listik_context`. Поменял файл — загрузи снова, иначе сервер отдаст старый текст.
- **Нет запасного пути.** Сервер не отвечает — CLI-режима с локальной базой здесь нет: скажи
  пользователю, не пиши задачи в чат вместо Listik.
- Администрирование (проекты, routing, удаление задач, импорты) через MCP недоступно — это
  делает человек на сервере.

## Холодный старт

Продолжая чужую или прерванную работу, контекст бери из карточки, а не из памяти:
`L show <id>` — держатель, этап, вопросы и ответы, журнал, ревью, вердикты, документы,
`worktree`/`branch`, связи; `L context <id> --stage <этап>` — срез под этап. Перед handoff
проверь, что там есть `spec_path`, приёмка, дерево/ветка, зависимости и запись в журнале.
`holder_taken=false` при живом держателе — карточку только выдали (`not_taken`), своей работы
по ней ещё не было: либо исполнитель не запустился, либо его claim потерялся.
