# Listik: работа с задачами

Listik — общая очередь задач и журнал работы для людей и агентов. Карточка — единственный
источник правды: всё, что должна узнать следующая сессия, пиши в Listik, а не в чат.

## Подготовка

1. Найди CLI: `$LISTIK_BIN`, иначе `listik` в `PATH`, иначе спроси пользователя путь к
   `bin/listik`. Дальше в тексте — `L`.
2. Представься агентом, иначе твои связи станут жёсткими, как у человека:
   `export LISTIK_ACTOR=agent:claude`. Держатель — `--holder claude` (или имя сессии).
3. `L status` — жив ли сервер. Если нет, CLI сам работает с базой напрямую; можно поднять
   `L serve --daemon`.

`--json` есть у всех команд — используй его, когда разбираешь вывод.

## Протокол

1. **Найти.** `L ready` (или `L ready --harness claude`), `L search "суть"`, затем
   `L show <id>`. Не бери задачу, которой нет в `ready`: у неё открытый блокер или держатель.
2. **Взять сразу.** `L claim <id> --holder claude --note "что собираюсь делать"`.
   Отказ `claim` объясняет причину и варианты — выбирай из них, не обходи.
3. **Держать живой.** Работа дольше 10 минут — `L heartbeat <id> --holder claude --note "…"`
   каждые 10–15 минут. `heartbeat` перезаписывает держателя без проверки — никогда не шли его по
   задаче, которую держит кто-то другой.
4. **Писать журнал.** Решения и ход работы — `L comment <id> "…" -k journal`; замечания к ТЗ —
   `-k review`; вердикт проверки — `-k verdict`.
5. **Спрашивать человека через Listik.** `L needs-owner <id> "точный вопрос с вариантами"`.
   Не оставляй вопрос только в чате. Ответ приходит `needs-owner --clear "…"` и виден в `show`.
6. **Переводить этап командой.** `L stage <id>`; не меняй этап правкой текста карточки.
7. **Закрыть.** Перед закрытием проверь `L show <id>`: нет открытых блокеров, у эпика закрыты
   дети, приёмка выполнена — сервер этого сам не проверяет и держателя не снимает.
   `L done <id> -r "краткий проверяемый результат"`.
8. **Отдать.** Не можешь продолжить — `L comment … -k journal` о состоянии и `L release <id>`.
9. **Чужое не переписывай.** Нашёл проблему в чужой карточке — `comment`, а не `set`.

## Этапы конвейера

| Этап | Что читать | Что менять | Переход |
|---|---|---|---|
| `s1-spec` | `show`, `L context <id> --stage s1-spec`, `spec_path` | ТЗ и чек-лист (файлы), порции `L new … --spec … --checklist …` | `stage` → s2, **sticky**: держатель остаётся |
| `s2-review` | `L context <id> --stage s2-review` | ничего, кроме `comment -k review` | `stage` → s3, **handoff**: держатель снимается |
| `s3-impl` | `L context <id> --stage s3-impl --portion "<порция>"` и `show` (ответы, прошлый вердикт) | код в `worktree`/`branch` карточки, проверки, `-k journal` | `stage` → s4, **sticky**; не коммитить |
| `s4-judge` | `L context <id> --stage s4-judge`, чек-лист, дифф | код не править; `comment -k verdict` | зелёный — коммит и `done`; красный — сервер сам вернёт на s3 |

- **sticky, другой исполнитель:** передающий `L stage <id> --holder <следующий>`, принимающий
  начинает с `L claim <id> --holder <свой>`.
- **handoff:** после перехода задачу берут заново через `ready` → `claim`.
- **Вердикт.** Сервер считает вердикт красным, если **в любом месте текста** есть «красн», «red»,
  «fail», «не прой» или «❌», и возвращает задачу с `s4-judge` на `s3-impl`. Зелёный вердикт
  пиши без этих слов даже в отрицаниях («тесты не падают», а не «нет fail»). Если после красного
  вердикта карточку держишь ты-судья — `release`, чтобы исполнитель мог взять.
- **Рабочее дерево.** `claim` на `s3-impl`/`s4-judge`/без этапа откажет, если то же дерево в
  проекте занято другой пишущей задачей. Варианты — дождаться, `release` брошенной, или
  `L set <id> worktree=/другой/путь`.

## Зависимости

- `L dep add <id> <блокер>` — «`<id>` ждёт `<блокер>`». От агента это **предложение**
  (`suggested-blocks`): оно не блокирует, пока человек не подтвердит `dep confirm`. Не используй
  `--confirm` сам — жёсткие блокеры ставит человек.
- Связь «прочитай сначала» без запрета — `L dep add <id> <другая> --dep-type relates-to` или
  `L dep link <id>` для задач, упомянутых в тексте.
- Блокер брошен — возьми сам блокер или поставь ему `needs-owner`; `claim --force` в обход
  блокера — только с явного согласия человека.
- Проверить: `L tree <id>`, `L blocked`, в `show` — «ждёт» и «её ждут».

## Холодный старт

Продолжая чужую или прерванную работу, контекст бери из карточки, а не из памяти:
`L show <id>` — держатель, этап, вопросы и ответы, журнал, ревью, вердикты, документы,
`worktree`/`branch`, связи; `L context <id> --stage <этап>` — срез под этап. Перед handoff
проверь, что там есть `spec_path`, приёмка, дерево/ветка, зависимости и запись в журнале.
