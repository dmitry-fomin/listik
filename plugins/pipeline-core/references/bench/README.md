# Стенд судей

Воспроизводимая проверка моделей-судей: разные судьи принимают одни и те же порции работы, в часть
которых подложен дефект. Этап приёмки воспроизводится как настоящий: порция лежит незакоммиченной
поверх базы, бумаги шага — в `docs/specs/steps/`, пакет диффа собран блоком «Пакет диффа для
приёмки» из `../pipeline-core.md`, задание судье — блок из `../../../feature-pipeline/skills/low-pipeline/SKILL.md`
(после строки ``Задание, которое уходит в `/grok:delegate`:``, без хвоста про карточку Listik) плюс
стендовая часть с путями.

`BENCH` ниже — этот каталог (`plugins/pipeline-core/references/bench`).

## Кейсы — ключ ответов

`cases.json` — список кейсов: `name` (`case-01` … `case-NN`), `class` (класс дефекта или `чистый`),
`step`/`portion` (бумаги шага), `commit` (коммит порции, база — `<commit>^`), `tests` (цели
`python3 -m unittest`), `defect` (где и что сломано; у чистого `null`), `defect_path` (файл дефекта;
у чистого `null`). В `cases/<name>/` — `papers/` (три файла бумаг, плейсхолдер `{{TREE}}` — путь
дерева), `mutation.patch` и `probe.py` (оба или ни одного).

`cases.json` и `cases/` — **ключ ответов, судье не показываются**: в дерево кейса они не попадают,
судью в репозиторий с ними не пускать. Имена кейсов нейтральные: ни класс, ни слово «clean» не
появляются в путях деревьев, отчётов и в тексте задания.

## Сборка

```sh
python3 BENCH/judge_bench.py prepare --judge <метка> [--out <каталог>] [<кейс>…]
```

По дереву на пару (судья, кейс): `<out>/<метка>/<кейс>/` — отдельный git-репозиторий с одним
коммитом базы на `main`, реализация и мутация поверх незакоммичены; задание — в
`<out>/<метка>/<кейс>.task.md`. На каждый готовый кейс печатается блок `<кейс>: готов` / `дерево:` /
`задание:` / `отчёт:` и текст задания между `---`. Провал — строка `<кейс>: <причина>`, код 1.

- Скрипт **ничего не удаляет**: упавшее дерево остаётся на месте. Упавший или повторный прогон —
  в новый `--out` (или после ручного удаления старого дерева).
- `--no-mutation` — только для подбора мутации в порциях кейсов (дерево «база + реализация», без
  мутации и пробы), **не для прогонов судей**.
- Исходный репозиторий не меняется; `listik` не вызывается.

## Серия

Метки — ровно `sonnet-5.5-high` и `grok-4.7-high` (от них зависят пути отчётов). По одному прогону
на пару (судья, кейс); повтор упавшего прогона — на свежем дереве.

**Sonnet 5.5 high** — отдельный процесс, **не** субагент сессии оркестратора (у той рабочий каталог —
репозиторий с ключом ответов). Из каталога дерева кейса:

```sh
cd <дерево кейса>
claude -p --agent pipeline-core:pipeline-judge --model sonnet --effort high \
  --output-format json --permission-mode bypassPermissions "$(cat <файл задания>)"
```

- Имя агента — полное имя `pipeline-judge` в установленном плагине (`pipeline-core:pipeline-judge`);
  сверь перед серией по списку агентов Claude Code.
- Во frontmatter `pipeline-judge` стоит `model: opus` — модель задаётся **в вызове** (`--model
  sonnet`) и перекрывает его. Что ответил именно Sonnet, сверяй по полю модели в JSON-выводе
  (`modelUsage`/`model`) и пиши это значение в `модель:` шапки отчёта.
- Режим прав: `--permission-mode bypassPermissions` — судье нужны Bash и запись в дереве кейса
  (прогон чек-листа, коммит при зелёном); дерево — одноразовый отдельный репозиторий.
- Флаги `--agent`, `--model`, `--effort`, `--output-format`, `--permission-mode` сверены по
  `claude --help`.

**Grok 4.7 high** — `/grok:delegate --background --write --no-web --model grok-4.7 --effort high`,
рабочий каталог — дерево кейса, текст задания тот же (из файла `задание:`). Ждать и забирать —
`/grok:status` и `/grok:result`.

## Отчёт

Путь — строка `отчёт:` из вывода `prepare` (`BENCH/runs/<метка>/<кейс>.md`). Формат:

```
судья: <метка>
модель: <что запускалось>
начало: <ISO-время>
конец: <ISO-время>
секунд: <целое>
---
<ответ судьи дословно>
```

- Ответ — **дословно**: у Sonnet — поле результата JSON (`result`), у Grok — вывод `/grok:result`.
- Время — от запуска до финального ответа, меряет оркестратор.
- После сохранения проверь, что первая строка ответа распознаётся `summarize` как вердикт
  (`зелёный`/`красный`). Не распознаётся — в отчёт ничего не дописывать и не править: это
  `нет вердикта`.

После всех прогонов — файл сумм отчётов (пути от корня рабочего дерева):

```sh
shasum -a 256 plugins/pipeline-core/references/bench/runs/*/*.md \
  > <основное дерево>/docs/specs/steps/listik-ep3s.runs.sha256
```

По нему приёмка таблицы сверяет, что отчёты не правились.

## Сводка

```sh
python3 BENCH/judge_bench.py summarize
```

Таблица `| судья | кейс | класс | ожидается | вердикт | секунд | файл дефекта назван |`, строка на
пару, судьи по алфавиту, кейсы в порядке `cases.json`:

- `ожидается` — `красный` у кейса с дефектом, `зелёный` у чистого;
- `вердикт` — первая непустая строка ответа без `*`, `_`, `#`, пробелов и префикса `вердикт:`:
  `зелёный`, `красный`, `нет вердикта`; нет файла — `нет отчёта`;
  если первая строка склеена с комментариями харнесса (так бывает у вывода `/grok:result`), вердикт
  берётся из её конца — слово сразу после знака конца фразы, в конце строки, с необязательным хешем;
- `секунд` — из шапки или `?`;
- `файл дефекта назван` — есть ли `defect_path` в тексте ответа (`да`/`нет`, у чистого `—`).

Под таблицей по строке на судью: `красный на дефектах N из M, ложный красный на чистых K из L,
медиана S с`; отчёт кейса не из `cases.json` — строка `лишний отчёт: <путь>`.

«Поймал ли судья дефект» решается **чтением отчёта против `defect`**, а не колонкой «файл дефекта
назван»: красный по другой причине — не поимка, а названный файл ещё не значит, что назван дефект.
