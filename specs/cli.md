# CLI (`bin/listik`)

Одна программа — и командная строка, и клиент API. Ею работает и человек, и агент; через неё же
говорит с Listik рой.

## Решения

- **Два пути на каждую команду, и это главное правило файла.** Если сервер поднят — запрос идёт по
  HTTP (одна точка записи, доска обновляется сама). Если нет — команда уходит в базу напрямую, чтобы
  агент не вставал из-за незапущенного сервера. Новая подкоманда обязана иметь оба пути; расхождение
  между ними — дефект, а не оптимизация.
- **`--json` есть у каждой команды,** и ошибка в этом режиме приходит объектом
  `{"error": {"code", "message", "hint"}}` в stdout: агент ветвится по `code`, а не разбирает текст.
- **Куда ходит команда, решается по цепочке:** `--local` → `--host/--port` → `.listik.toml`
  ближайший вверх до корня git-репозитория → свой `[server]`. Проект по умолчанию тоже берётся из
  файла проекта; из каталога проекта очередь показывает этот проект, `--project all` снимает фильтр.
- **Общий сервер важнее локальной базы.** Если `.listik.toml` ведёт на удалённый сервер, а тот не
  отвечает, команда отказывает кодом `unreachable` и локальную базу не трогает: две правды хуже
  отказа.
- **Представление о себе — флаги, а не окружение.** `--actor`/`--harness` передаются в каждой
  команде: каждый вызов — новый процесс, и унаследованная переменная может принадлежать чужому
  агенту. Без них запись приписывается человеку.

## Граница

Может: ядро, хранилище, ограждение, маршруты, дерево задачи, наблюдатель роя. Не может: HTTP-слой
(ходит в него по сети, а не импортом). Правила, по которым движется карточка, — `listik-protocol`;
контракт полей и кодов — `listik-api`.
