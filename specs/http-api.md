# HTTP API, доска и SSE

`server.py` — весь HTTP-слой на `http.server.ThreadingHTTPServer` (без фреймворка и зависимостей):
JSON API `/api/*`, раздача собранной доски `web/dist` со SPA-фолбэком, поток событий `/api/stream`,
приём MCP по HTTP (`POST /mcp`) и несколько фоновых потоков на процесс.

## Что здесь живёт кроме роутов

- **Соединение на поток.** У каждого потока своё соединение с SQLite (`threading.local`),
  закрывается вместе с потоком запроса.
- **Смена базы под работающим сервером.** Счётчик поколений переоткрывает все соединения после
  `DatabaseError` или когда поток-наблюдатель видит, что у `listik.db`/`-wal` сменился inode.
  Признак виден в `/api/health` и `listik status` (`_db_replaced`).
- **Фоновые потоки:** досчёт эмбеддингов раз в 45 с (`search-memory`) и надзор за процессом роя
  (`launch-swarm`).
- **События доски.** Любая запись публикует событие в `/api/stream`; удалённая запись (stdio-MCP
  пишет в базу мимо сервера) приходит через `POST /api/notify`.

## Инварианты

- **Никакой семантики задач.** Правила этапов, держателя и зависимостей — в `listik-card-core`;
  слой только разбирает запрос, проверяет токен и владельца и зовёт ядро.
- **Ошибка наружу — тот же `code`/`hint`,** что у CLI: сервер ловит только `NotFound` (иначе 500
  `internal`), остальные отказы отдаёт теми кодами, которые подняло ядро.
- **Публикация по факту записи,** а не по факту запроса: событие уходит после успешной записи и
  только для неё.
- **Один процесс на порт.** Второй `serve` на занятом порту не поднимается — на этом же правиле
  стоит `service install` (см. `listik-install-ops`).

Контракт эндпоинтов, полей и кодов ответа — `listik-api`; здесь только то, чего в контракте нет.
