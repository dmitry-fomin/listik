# Установка и обслуживание

`install.sh` — установщик одной строкой (ставит версию в `~/.listik/app/<версия>`, обёртку в
`~/.local/bin`, данные в `~/.listik`), `service.py` — автозапуск через launchd/systemd, `backup.py` —
согласованные копии базы, `scripts/release.sh` — сборка архива релиза.

## Решения

- **Данные и код живут отдельно,** и обновление данные не трогает: повторный запуск установщика
  ставит новую версию рядом со старой.
- **Что попадает в релиз — белый список.** В архив идут `bin/`, `listik/`, `swarm/`, `alembic/`,
  `web/dist` (собранная доска), `install.sh`, `VERSION`, `routes.json` (затравка таблицы маршрутов),
  `config.example.toml`, `alembic.ini` и обязательные документы (`README.md`, `docs/API.md`,
  `AGENTS.md`, `docs/harness-protocol.md`, скил протокола) — и ровно четыре файла справки по ролям
  конвейера. Всё остальное в архиве не появляется, а отсутствие обязательного файла в git роняет
  релиз: неполная поставка не должна собираться.
- **Копия базы — только через backup API.** База живёт в WAL, поэтому `cp`/`mv`/`rm` недопустимы;
  `restore` отказывает на работающем сервере без `--stop`, держит страховочную копию и убирает
  протухшие `-wal`/`-shm`.
- **Автозапуск не спорит с ручным сервером.** `service install` отказывает, если сервер уже поднят
  вручную (иначе два процесса на одном порту); `--stop` снимает ручной и ставит сервис на его место.
  Поддерживаются launchd и systemd `--user`; остальные платформы получают явный отказ.
- **Установщик спрашивает только там, где ответ меняет данные:** перезаписать ли таблицу маршрутов
  из `routes.json` (с бэкапом) и править ли конфиг Codex ради доступа к локальному серверу. В
  неинтерактивном режиме действует безопасное «нет».

## Граница

Может: пути, конфиг, базу через backup API, системные команды через одну точку подмены (тесты
никогда не зовут настоящие `launchctl`/`systemctl`). Не может: семантику задач, HTTP-слой.
