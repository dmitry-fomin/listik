# Поиск, память и документы

`search.py` — гибридный поиск по задачам, комментариям и документам: FTS5 (BM25) и векторная
близость сливаются через RRF. `embed.py` считает векторы через локальный Ollama (`bge-m3`, 1024
измерения). `documents.py` — Markdown-документы карточки по путям, их структурные чанки и
компактный контекст этапа.

## Решения

- **Слияние по рангам, а не по скорам.** Скор — сумма `1/(k + rank)` при `k = 60`: ранги устойчивее
  сырых скоров, а `k` гасит влияние хвоста. Никаких ручных весов.
- **Вектор считается по хешу текста.** Изменился текст — нужен новый вектор; не изменился —
  пересчёт не нужен. Досчёт идёт фоном раз в 45 с.
- **Деградация молчаливая и намеренная.** Ollama не запущена — поиск остаётся лексическим и не
  падает. Это не ошибка конфигурации, а нормальный режим.
- **Документ — это путь плюс загруженный текст.** Читать чужие файловые системы сервер не умеет:
  на общем сервере `spec_path`/`checklist_path` показывается отсутствующим, пока текст не положат
  вручную. Разбор на чанки — по структуре Markdown, чтобы «контекст этапа» отдавал нужный кусок,
  а не весь файл.
- **Память — это те же карточки и заметки,** а не отдельное хранилище: `remember`/`memory` идут
  через тот же поиск, поэтому «где уже решали такую задачу» и «что мы решили тогда» ищутся одинаково.

## Граница

Может: ядро (для чтения карточек), util, actors, Ollama по HTTP. Не может: поверхности, запуск,
маршруты. Формат индексов и эндпоинтов поиска — `listik-api`.
