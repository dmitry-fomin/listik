# Хранение, пути и конфиг

`db.py` держит схему и подключение, `paths.py` — где лежит код, где данные (`LISTIK_HOME`, а без
него корень репозитория), `config.py` — `config.toml` (хост/порт, токен доски, режим сервера и
люди, маршрутизация, разделы внешних ключей). База — единственный источник истины: SQLite в WAL.

## Решения

- **Две схемы миграций, намеренно.** `db.SCHEMA`/`db.SCHEMA_VERSION` — мягкая миграция в процессе:
  она выполняется на каждом `init`/`serve` и держит базу пользователя живой без зависимостей.
  `alembic/` — отдельный путь: читаемая история изменений и опора для тех, кто держит схему сам
  (подтверждено автором). Любое изменение схемы делается в обеих; Alembic требует явного
  `LISTIK_DB` и без него отказывается открывать боевую базу.
- **Засев, а не синхронизация.** Сиды таблиц (`routes.json`, каталог харнессов) ввозятся один раз
  `INSERT … ON CONFLICT DO NOTHING` при `db.init`: правки человека не затираются, и никто потом
  файл с таблицей не сверяет. Разовая миграция данных может идти по meta-флагу (например
  `seed_bridge_channels`) — тогда она тоже выполняется ровно один раз.
- **Токен создаётся сам** при первом запуске сервера и пишется с правами `0600`: без токена доска и
  `/api/*` отвечают 401, но чтение с токеном и без владельца разрешено.

## Граница

Не знает о задачах: ни этапов, ни держателей, ни зависимостей. Знает только «как открыть базу»,
«где что лежит» и «что написано в конфиге». Копирование базы файлом запрещено контрактом WAL —
этим занимается `listik-install-ops`.
